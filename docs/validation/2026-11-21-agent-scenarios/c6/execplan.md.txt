## Purpose / big picture

A deployed binary currently writes records through a private source API in a
persisted format that is being reshaped. After this work, the application uses a
single new source interface, writes only the new persisted format, and can
still read every record the deployed binary wrote. The old source interface is
gone: it is replaced and every caller changes with it, rather than kept alive
behind an alias, facade, deprecated entrypoint or shim. The persisted records
are handled separately, because deployed data is not the same obligation as a
released source contract.

A caller observes the change as follows. Before the change, a read looks like
this:

```plaintext
caller -> A1 (old private API) -> legacy record type -> store
```

After the change, the same logical read looks like this:

```plaintext
caller -> A2 (new private API) -> new record type -> store
store  -> codec -> v1 or v2 stored bytes
```

The important observable outcomes are:

1. Reading a record written by the deployed binary returns the same logical
   value as before, under the approved mapping.
2. All writes produce the new format.
3. Running the migration a second time changes no bytes and reports zero
   changes.
4. Restoring the pre-migration snapshot lets the deployed binary read its
   records again.
5. A search of the source tree finds no reference to the old private API and no
   compatibility machinery for it.

Terms used in this plan: a **private API** is an application-internal source
interface, even if its declarations are marked `public`; a **deployed record**
is persisted data written by a binary that has run outside development; the
**legacy decode path** is the v1 decoder used only to read deployed records;
the **migration window** is the period during which v1 and v2 records may both
be read.

Preserved behaviour: record identity, record logical values under the approved
mapping, the storage backend, and the operator's ability to restore a snapshot.
Deliberately changed behaviour: the source interface, the stored bytes, and the
fail-closed error for an unknown or malformed record, which must never be
reported as an absent record.

This plan closes no roadmap decision. It advances `TOR-GOAL-001` to
`TOR-GOAL-003` and resolves the gaps listed in `Conformance basis`.

## Constraints

Hard invariants that must hold throughout implementation. Violation requires
escalation, not a workaround.

- The private source API `A1` must not receive a compatibility layer. No alias,
  facade, deprecated entrypoint, wrapper, adapter or dual interface may remain
  after `EP-M1`. Every caller changes in that milestone.
- The v1 decode path exists only for persisted data. It takes stored bytes,
  returns the new logical record, is confined to the storage codec, and is not
  reachable from domain code. It is not a source-API shim.
- No record may be deleted, truncated or silently stripped of a field. Every
  v1 field is mapped or listed as an approved drop.
- Unknown versions, missing versions, truncated envelopes and checksum
  mismatches fail closed with typed errors. They are never decoded with
  defaults and never reported as absent records.
- Migration must be preceded by a snapshot that has been restored successfully
  in a scratch environment.
- No writer may run during snapshot and migration. The stop must be verified,
  not assumed.
- No new runtime dependency, external interface or storage backend is
  authorised by this plan.
- Implementation begins only after the user explicitly approves this plan.
  Silence is not approval.
- This ExecPlan file is excluded from every size count below.
- Completed historical ExecPlans must not be modified.

## Risks

- Risk: The API is not actually private and has an external consumer.
  Severity: high. Likelihood: low. Mitigation: `EP-M0` records consumer and
  release-lineage evidence; if one is found, stop and reconcile the terms of
  reference before any code changes.
- Risk: The v1 field mapping changes meaning or drops a field.
  Severity: high. Likelihood: medium. Mitigation: a total mapping table
  approved by the data owner, a corpus that exercises every field class, and a
  seeded mapper fault that the tests reject.
- Risk: The storage backend does not provide atomic replacement.
  Severity: high. Likelihood: medium. Mitigation: cite the platform guarantee
  and run a focused probe in `EP-M0`; if the guarantee is absent, redesign
  before migration.
- Risk: An interrupted migration corrupts or loses records.
  Severity: high. Likelihood: medium. Mitigation: snapshot-first, temporary
  writes, atomic replace, crash-injection tests at each named step, and a
  restore rehearsal.
- Risk: The deployed binary keeps writing after the snapshot.
  Severity: medium. Likelihood: medium. Mitigation: verified quiesce and an
  exclusive-writer precondition; abort on a failed lock.
- Risk: The corpus is unrepresentative.
  Severity: medium. Likelihood: high. Mitigation: a provenance manifest,
  coverage classes, and an explicit statement that the corpus cannot prove
  completeness.
- Risk: Rollback takes longer than the window or loses post-snapshot writes.
  Severity: medium. Likelihood: medium. Mitigation: a defined rollback point
  before the first new write, a timed rehearsal, and incident handling after
  that point.
- Risk: The legacy decoder is removed before the retention window ends.
  Severity: medium. Likelihood: medium. Mitigation: a dated retention decision
  and a separate decommission change.

## Decision log

- D1. Decision: no source-API compatibility layer for `A1`.
  Rationale: `A1` is private and has no evidenced external consumer. A facade
  or alias would create a second source interface with no owner or removal
  criterion. The strongest alternative, keeping `A1` as a deprecated wrapper,
  was rejected because it would preserve exactly what the work exists to
  remove. Date/Author: 2026-11-21, authoring agent (draft).
- D2. Decision: handle deployed records with a versioned codec, a bounded v1
  read window and an explicit migration.
  Rationale: persisted data is a separate obligation from source
  compatibility. A permanent dual reader was rejected because it leaves two
  representations alive indefinitely. Date/Author: 2026-11-21, authoring agent
  (draft).
- D3. Decision: offline, stop-the-world, snapshot-first, one-way migration.
  Rationale: it gives a verifiable before and after state and a restore-based
  rollback. Lazy upgrade, dual write and big-bang rewrite were rejected for
  the reasons in the design. Date/Author: 2026-11-21, authoring agent (draft).
- D4. Decision: stateless full scan rather than a mutable progress cursor.
  Rationale: a cursor can disagree with the store after a crash; a rescan
  converges and the report is advisory. Date/Author: 2026-11-21, authoring
  agent (draft).
- D5. Decision: fail closed on unknown or malformed data.
  Rationale: a default can silently change meaning and cannot be distinguished
  from legitimate data. Date/Author: 2026-11-21, authoring agent (draft).
- D6. Decision: no formal prover or model checker; property tests and crash
  injection carry the obligations.
  Rationale: the state space is small and the dominant risks are I/O atomicity,
  mapping and corpus coverage, which an abstract proof would not settle.
  Date/Author: 2026-11-21, authoring agent (draft).
- D7. Decision: keep the plan at `DRAFT` and perform no implementation.
  Rationale: the user has not approved it and `EP-M0` has not closed the
  intake gaps. Date/Author: 2026-11-21, authoring agent (draft).
- D8. Decision: no diagram and therefore no nixie validation for this plan's
  design companion.
  Rationale: the component topology is linear and the design prose and tables
  already state every relationship. A diagram would restate them without
  resolving a concern. Date/Author: 2026-11-21, authoring agent (draft).
- D9. Decision: Red-Green-Refactor is not used for `EP-M0`, which is read-only
  discovery, or for the documentation portion of `EP-M4`.
  Rationale: neither produces production behaviour to drive with a failing
  test. The substitutes are an evidence checklist for `EP-M0` and a rehearsal
  transcript for `EP-M4`. Every code-bearing milestone uses
  Red-Green-Refactor. Date/Author: 2026-11-21, authoring agent (draft).

## Verification plan

### Abstract model

A store `S` maps record IDs to stored bytes. A bytes value is either a v1 record
or a v2 record. `decode_any(b)` returns a logical record or a typed error. `M`
maps the v1 logical shape to the v2 logical shape. `encode_v2(r)` returns
canonical v2 bytes. `migrate_all(S)` returns a new store and a report.
`crash(S, p)` models process death at step `p`. `restore(snapshot)` returns the
snapshotted store.

Preconditions: the store is quiescent, every record is valid or the preflight
abort policy stops the run, the mapping is total, and the snapshot is
restorable. Malformed records violate the preflight precondition and are
handled by the failure policy, not by the migration relation. The expected
result is a store
containing only canonical v2 bytes, with the same domain and the mapped logical
values.

### Invariants and lemmas

- `INV-READ-CORPUS` (`TDD-INV-001`): for every fixture in the captured v1
  corpus, `decode_any` returns the recorded expected value.
- `INV-PRESERVE` (`TDD-INV-002`): for every record, after migration,
  `decode_any(S'[id]) = M(decode_any(S[id]))`.
- `INV-NO-LOSS` (`TDD-INV-003`): migration preserves the ID set and the
  multiset of mapped logical values; it adds and deletes nothing.
- `INV-IDEMPOTENT` (`TDD-INV-004`): a second migration is byte-identical and
  reports zero changes.
- `INV-RESUME` (`TDD-INV-005`): for every crash point, re-running converges to
  the uninterrupted final state.
- `INV-FAIL-CLOSED` (`TDD-INV-006`): unknown versions and malformed records
  return typed errors, never values or defaults.
- `INV-WRITE-V2` (`TDD-INV-007`): every successful write produces v2 bytes.
- `INV-SOURCE` (`TDD-INV-008`): no `A1` reference and no compatibility
  machinery remains.
- `INV-ROLLBACK` (`TDD-INV-009`): a restored snapshot decodes under the
  baseline binary for every sampled record.

Lemmas:

- `L-DECODERS` (`TDD-LEMMA-001`): the v1 and v2 decoders are independent;
  neither delegates its own format to the other. This makes corpus
  expectations an oracle rather than a self-comparison.
- `L-COMPOSE` (`TDD-LEMMA-002`): if `decode_v1` is total on the corpus, `M` is
  total and v2 round-trips, the migration composition preserves the value.
- `L-ATOMIC` (`TDD-LEMMA-003`): under atomic replacement, a crash leaves each
  record wholly v1 or wholly v2.
- `L-SCAN` (`TDD-LEMMA-004`): a stateless scan visits every record and skips
  only after successful v2 validation.

### Axioms (trusted, not verified here)

- `AXIOM-STORAGE` (`TDD-AXIOM-001`): the storage platform replaces one record
  atomically. Source: platform documentation captured at `EP-M0`.
- `AXIOM-DURABILITY` (`TDD-AXIOM-002`): flush and durability calls behave as
  documented. The repository-owned calls are checked against that contract.
- `AXIOM-EXCLUSIVE-WRITER` (`TDD-AXIOM-003`): no writer runs during snapshot and
  migration. Enforced and verified operationally.
- `AXIOM-BASELINE` (`TDD-AXIOM-004`): the deployed binary or a pinned baseline
  build is available and faithful for corpus capture and rollback rehearsal.
- `AXIOM-CORPUS` (`TDD-AXIOM-005`): the corpus represents the deployed record
  classes. This is claimed and documented, not proven.
- `AXIOM-SERIALIZATION` (`TDD-AXIOM-006`): the chosen serialization implements
  its documented canonical form. Third-party internals are not verified; the
  repository's configuration of them is.

### Methods per obligation

- Obligation: `INV-READ-CORPUS`.
  Method: table-driven golden corpus test plus a property test over v1 fixtures
  produced by the frozen baseline.
  Rationale: the corpus is direct evidence of deployed readability; generated
  cases cover field classes.
  Domain: every corpus record and every optional, absent, boundary and unicode
  class.
  Artefact: `tests/codec/v1_corpus.*` with an expected-value table.
  Evidence: the focused command fails before the decoder exists and passes
  after; the corpus manifest is retained.
  Non-vacuity: at least one witness per class; a mutated byte must fail with a
  typed error or a wrong-value assertion; an all-empty corpus is rejected.
- Obligation: `INV-PRESERVE`.
  Method: property test over generated stores and the corpus, with
  `M(decode_v1(b))` as the oracle.
  Rationale: preservation is a value relation independent of the v2 encoder.
  Domain: stores of zero, one and many records; every mapping row.
  Artefact: `tests/migrate/preserves_value.*`.
  Evidence: red before the migrator, green after; saved regression seed.
  Non-vacuity: every mapping row is exercised; a seeded mapper that swaps two
  fields must be rejected.
- Obligation: `INV-NO-LOSS`.
  Method: before/after ID set and multiset digest.
  Rationale: directly detects deletion, addition and value drift.
  Domain: generated stores plus the corpus.
  Artefact: `tests/migrate/no_loss.*` and the migration report.
  Evidence: digest equality in the report.
  Non-vacuity: include an empty-optional record that a collapse would change; a
  migrator that drops one ID must fail.
- Obligation: `INV-IDEMPOTENT`.
  Method: property test over two consecutive runs, comparing bytes.
  Rationale: canonical encoding makes byte idempotence observable.
  Domain: generated stores and the corpus.
  Artefact: `tests/migrate/idempotent.*`.
  Evidence: second report records zero changes.
  Non-vacuity: a non-canonical encoder or a migrator that rewrites different
  bytes must fail; a zero-record store is not sufficient.
- Obligation: `INV-RESUME`.
  Method: crash-injection state-machine test at each named step.
  Rationale: models the actual interruption points and is exhaustive within
  those steps.
  Domain: crash before write, after temp write, before flush, before replace,
  after replace, before report.
  Artefact: `tests/migrate/resume.*`.
  Evidence: final state equals the uninterrupted run.
  Non-vacuity: every crash point reachable; a truncated destination left by a
  faulty migrator must fail.
- Obligation: `INV-FAIL-CLOSED`.
  Method: parameterized matrix of versions and malformations.
  Rationale: finite partition; exhaustive enumeration is practical.
  Domain: versions 0, 1, 2, 3, maximum integer; missing field; short header;
  bad checksum; ambiguous prefix.
  Artefact: `tests/codec/fail_closed.*`.
  Evidence: every case returns the expected typed error.
  Non-vacuity: every case has a witness; a decoder that defaults unknown
  versions to v1 must fail.
- Obligation: `INV-WRITE-V2`.
  Method: codec property test and store inspection.
  Rationale: the write path has one observable output.
  Domain: every generated logical record.
  Artefact: `tests/codec/writes_v2.*`.
  Evidence: no v1 bytes after any write.
  Non-vacuity: at least one write witness; any v1 output fails.
- Obligation: `INV-SOURCE`.
  Method: source search plus build, with a red stage before `EP-M1`.
  Rationale: absence of a symbol is directly observable.
  Domain: the source tree, excluding generated and vendor trees.
  Artefact: the `rg` command and compiler output.
  Evidence: before the change the search finds `A1`; afterwards it finds zero.
  Non-vacuity: a scratch reintroduction of an alias must be caught.
- Obligation: `INV-ROLLBACK`.
  Method: rehearsal transcript.
  Rationale: restore is an operational property, not an in-process one.
  Domain: one scratch environment and a sample across field classes.
  Artefact: the runbook rehearsal log.
  Evidence: at least one rewritten record is restored and read by the baseline.
  Non-vacuity: restoring only untouched records is not sufficient. A negative
  control with a second binary is impractical here; the independent witness is
  the baseline binary reading the restored record.

### Formal verification decision

No prover or model checker is adopted (`D6`). The per-record state space is
small, and the dominant risks are platform atomicity, field mapping and corpus
coverage. A bounded model check of the scan/resume state machine could add
confidence in `INV-RESUME`, but would leave `AXIOM-STORAGE`, `AXIOM-CORPUS` and
the mapping review untouched. Property tests with crash injection are
proportionate. Revisit this if the migration becomes concurrent or the storage
guarantee is weaker than assumed.

### Suggested BDD features

Proposed feature path: `tests/features/record_migration.feature`. These are
proposed acceptance scenarios; if the repository has no BDD runner, exercise
them through the tests named above and do not add a framework.

```gherkin
Feature: Read and migrate records written by the deployed binary
  Scenario: A legacy record survives the upgrade
    Given a store containing a record written by the deployed binary
    When the new binary reads the record
    Then the record is returned with its original logical value

  Scenario: An interrupted migration resumes
    Given a store containing legacy and migrated records
    When the migration process stops after replacing one record
    And the migration is run again
    Then every record is stored in the current format
    And no record value changed

  Scenario: An unknown format version is rejected
    Given a record with an unknown format version
    When the new binary reads the record
    Then a typed unsupported-version error is returned
    And no default value is produced
```

## Idempotence and recovery

The migrator is safe to re-run. A partial run leaves each record either fully
v1 or fully v2; a rescan converges. Temporary files may remain after a crash
and are removed or replaced on the next run. The snapshot is the recovery
anchor: restore it, start the deployed binary and verify a sample. A migration
must never begin without a snapshot that has been restored successfully in
scratch. Clean up temporary files and scratch stores after the rehearsal; do
not leave production credentials or payloads in the rehearsal environment.

## Interfaces and dependencies

At the end of `EP-M1`, the source tree must define the new record type and the
store interface, and must not define or re-export `A1`. The intended shape,
independent of language, is:

```plaintext
RecordStore:
  get(record_id) -> Result<Option<Record>, StoreError>
  put(Record) -> Result<(), StoreError>
  list_ids() -> Result<Vec<RecordId>, StoreError>

Record:
  record_id: RecordId
  <reshaped fields>
```

At the end of `EP-M2`, the codec must expose one decode entry point and one
encoder, internal to the store:

```plaintext
Codec:
  decode_any(bytes) -> Result<Record, CodecError>
  encode_v2(Record) -> Result<bytes, CodecError>
```

The codec owns version dispatch; the domain never sees bytes, format tags or
legacy types. The migrator uses the codec and must not reimplement mapping.
Exact names and paths are recorded at `EP-M0`.

Authorised dependencies: none beyond the existing storage and serialization
stack. A new runtime dependency, a new external interface, or a published
package change requires escalation. The deployed binary and the corpus are
internal dependencies: the operator provides the binary or a pinned baseline
build, and the corpus is captured with recorded provenance.
