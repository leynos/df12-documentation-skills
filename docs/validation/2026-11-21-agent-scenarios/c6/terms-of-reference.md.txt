## 1. Background and motivation

`[KNOWN]` The sponsor has requested that the private API and the storage
representation be reshaped. Source: the supplied brief.

`[KNOWN]` A binary has already been deployed and has written records that must
remain readable. Source: the supplied brief. The brief does not name the reader
or the period, so the resulting obligation is recorded as
`TOR-CONSTRAINT-001` with an open scope.

`[OPEN]` Why the reshape is requested now, and what deficiency the current
representation causes. Resolution: maintainer interview (`TOR-OPEN-011`). A
change request is evidence of intent, not evidence that the current
representation is defective.

Deployment of a binary creates an obligation to read the data it wrote. It does
not convert a private source interface into a released external contract. This
distinction governs the whole document: the source API and the persisted
records are assessed separately.

## 2. Domain

The work belongs to internal application evolution and persisted-format
migration. Established conventions in that field include explicit format
versioning, a migration step before decommissioning an old format, backup and
restore before destructive rewrites, fail-closed handling of unknown data, and
a rehearsed rollback. These conventions inform the constraints below; they do
not select an implementation.

Prior art was not inspected. Relevant prior art would be the existing storage
codec, its tests, fixtures written by the deployed binary, prior migrations and
any ADR governing persistence. Their absence is an intake gap, not evidence
that they do not exist.

`[OPEN]` Whether the records carry regulatory, contractual or audit retention
obligations beyond remaining readable. If they do, the retention window and
rollback requirements may be externally imposed rather than discretionary.

## 3. Market context

Not applicable. This is an internal representation change, not a product
entering a market. No competitor analysis is invented.

The alternatives that occupy the space are: leave the representation unchanged;
change the code without migrating stored records; or change the code and
migrate the records. The second alternative fails `TOR-CONSTRAINT-001`. The
first preserves readability but leaves the maintainability deficiency
unaddressed. The third is the only alternative consistent with both the request
and the readability constraint. Choosing among migration techniques belongs in
the technical design.

## 5. Job to be done

When the internal representation no longer fits the domain, the maintainer
wants to replace the private API and the persisted representation together, so
that the codebase stays coherent without making records written by the deployed
binary unreadable.

The functional dimension is the whole job. The emotional dimension is
confidence that a failed cutover is recoverable; it is not a separate job. The
social dimension does not apply to an internal change.

Competing alternatives are the status quo, a code-only change that abandons old
records, and a migration. The status quo leaves the job undone; the code-only
change violates the readability constraint.

### Problem-space scenario

Trigger: the representation change is approved. Actors: the maintainer who
changes the code, the operator who performs the cutover, the deployed binary
that wrote the existing records, and the new binary. Preconditions: a
restorable snapshot, a representative corpus of deployed records, and an
exclusive writer during migration. Normal flow: the operator quiesces the
writer, takes and verifies a snapshot, runs the migration, checks the report,
starts the new binary, and confirms that records read back with their previous
logical values. Important exceptional flows: migration is interrupted; a
record is malformed or has an unknown version; the snapshot cannot be restored;
rollback is required after a new-format record has been written. Observable
outcome: every pre-existing record is readable with the same logical value, and
the store contains only the current format when the window closes. Measure: the
corpus pass rate, the before/after digest, and the restore rehearsal result.

This scenario tests the job statement. It does not prescribe the migration
mechanism.

## 6. Scope

### 6.1 Goals

- `TOR-GOAL-001` Replace the private API with the reshaped interface and update
  every in-application caller in the same coherent change.
- `TOR-GOAL-002` Keep every record written by the deployed binary readable,
  with its logical value preserved, through and after the change.
- `TOR-GOAL-003` Leave the codebase with one source interface and one current
  storage representation once the transition required to make existing records
  readable has completed.

Each goal is falsifiable by a source search, a corpus test, or a store
inspection.

### 6.2 Non-goals

- `TOR-NONGOAL-001` Preserving the old private API for any caller. No alias,
  facade, deprecated entrypoint, wrapper, adapter or shim. Callers are updated
  together. There is no external consumer to redirect; if one is found, this
  non-goal must be revisited explicitly.
- `TOR-NONGOAL-002` Rewriting record semantics. The change is structural unless
  a semantic change is separately approved (`TOR-OPEN-003`).
- `TOR-NONGOAL-003` Permanent support for two stored representations. Support
  for reading an earlier representation may exist only for a defined period
  with a removal condition.
- `TOR-NONGOAL-004` Replacing the storage product or backend as part of this
  work. If the current backend cannot satisfy the migration requirements, that
  is a separate change with its own terms of reference.
- `TOR-NONGOAL-005` Building an external migration service or supporting
  arbitrary old binaries indefinitely. Users needing pre-migration archives
  beyond the retention window must have those archives converted while the
  earlier representation is still readable.

| --- | --- | --- | --- | --- | --- |

| `TOR-SUCCESS-003` | Rollback restores a state the deployed binary can read | Rollback untested `[OPEN]` | Restore rehearsal succeeds for every sampled record; time within the window `[OPEN]` | Rehearsal transcript with commands and output | Operator |

Operational success requires the migration to finish within the approved window
without unplanned downtime. Strategic success does not apply to an internal
change. Implementation acceptance is separate from later operational outcome;
no adoption metric exists.

## 8. Constraints and assumptions

### 8.1 Hard constraints

- `TOR-CONSTRAINT-001` Records written by the deployed binary must remain
  readable. Source: the supplied brief. The reader, scope and duration are
  unresolved (`TOR-OPEN-001`). This is a persisted-data obligation.
- `TOR-CONSTRAINT-002` The API is private. This document creates no source-API
  compatibility requirement and authorises no compatibility machinery for it.
  Every in-application caller changes together. Source: the brief's description
  of the API as private, and the df12 policy in the installed
  `terms-of-reference-doc` skill
  (`105046d0309f13a6a5e3c5bdf6d75be73f70adeee0aff6ff93d6f2464ee956d4`).
  Even a declaration marked `public` is covered when it is application-internal.
- `TOR-CONSTRAINT-003` No compatibility theatre: no aliases, facades,
  deprecated entrypoints, dual source interfaces, wrappers, migration wrappers
  or temporary shims whose purpose is to keep the old source interface alive.
  A compatibility layer must name the real consumer or commitment it serves.
- `TOR-CONSTRAINT-004` No record may be destroyed, truncated or silently have a
  field dropped. Source: `[ASSUMED]` data-integrity requirement implied by the
  readability constraint; failure consequence: irreversible data loss. If the
  sponsor explicitly accepts loss for named fields, this constraint must be
  revised before migration, not after.

### 8.2 Assumptions

| ID | Assumption | Consequence if false | Verification route | Expiry trigger |
| --- | --- | --- | --- | --- |
| `TOR-ASSUMPTION-001` | The API has no external consumer and no released external contract | The compatibility classification is wrong; work stops for a sourced reassessment and possibly a deliberate migration commitment | Evidence of consumers, published packages, ABI use and release lineage (`TOR-OPEN-002`) | Any consumer, package or contract discovered |
| `TOR-ASSUMPTION-002` | A single writer can be stopped for cutover | Snapshot-and-rewrite is unsafe; the design must change to a concurrency-safe strategy or stop | Confirmed maintenance window and writer inventory (`TOR-OPEN-005`, `TOR-OPEN-009`) | Fleet or deployment model changes |
| `TOR-ASSUMPTION-003` | The reshape is structural and preserves record semantics | Value equality is the wrong success test; field mapping needs product decisions and may not be lossless | Confirmed field mapping (`TOR-OPEN-003`) | A semantic change is approved |
| `TOR-ASSUMPTION-004` | The storage medium supports atomic replacement of one record, or an equivalent transaction | A crash can tear a record; the migration needs a journal or two-phase design | Platform documentation and a focused probe (`TOR-OPEN-004`) | Backend change |
| `TOR-ASSUMPTION-005` | A representative corpus of deployed records can be captured | Readability cannot be demonstrated; `TOR-SUCCESS-001` is undischargeable | Corpus manifest and provenance (`TOR-OPEN-007`) | Corpus becomes unavailable |
| `TOR-ASSUMPTION-006` | A snapshot can be taken and restored within the window | No rollback path exists after the first rewrite; migration is one-way | Rehearsed restore (`TOR-SUCCESS-003`) | Backup policy changes |

### 8.3 Dependencies

- The deployed binary or a pinned baseline build is needed to capture fixtures
  and rehearse rollback. Provider and consumer are internal; the unblock
  condition is a captured corpus with recorded provenance.
- The storage platform's documented atomicity and durability guarantees are
  needed before the migration mechanism is fixed. The unblock condition is a
  cited version of that documentation and a focused probe.
- No external service dependency was identified. If one exists, it needs a
  provider, consumer, version, evidence and unblock condition before it gates a
  milestone.

### 8.4 Compatibility classification

| Surface | Classification | Evidence | Decision |
| --- | --- | --- | --- |
| The reshaped API | Private, application-internal | Brief; consumer evidence `[OPEN]` | No source-API compatibility requirement; all callers change together; no shim |
| Records written by the deployed binary | Persisted deployed data | Brief | Readability obligation to be met by an explicit data migration, assessed separately from the source API |
| Wire format or deployed peer | Unknown | Not mentioned in the brief | Separate assessment if found (`TOR-OPEN-009`); no assumption of compatibility |
| Released 1.0+ external contract | None identified | `[OPEN]` | If one exists, record the conflict and stop; do not convert this document into a compatibility authorisation |

### Glossary

- **Private API** – an application-internal source interface. It may be
  declared `public` for module visibility; it is not a released external
  contract.
- **Deployed record** – a persisted record written by a binary that has run
  outside the development environment.
- **Readability** – the ability of a named reader to obtain a record's logical
  value from its stored representation.
- **Transition period** – the bounded period during which records in the
  earlier representation must remain readable.
- **Rollback** – restoring a prior state that the deployed binary can read.
