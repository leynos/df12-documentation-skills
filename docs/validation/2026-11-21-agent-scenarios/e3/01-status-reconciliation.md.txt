## Why this is not a full terms of reference or design

The input supplies no problem-space brief and requests no design decision.
Manufacturing a terms of reference would invent intent, users, and success
criteria. Manufacturing a technical design would invent architecture for a
deployment-state question. No approved implementation slice exists from which
to author an ExecPlan. The work the governing skills actually direct here is
evidence reconciliation and a traceable correction handoff.

## Purpose and boundary

Three signals conflict: a programme record that still blocks work, an
implementation reported merged months ago, and a daily summary asserting
completion while deployment evidence is absent. This record separates the
signals rather than letting the most recent summary win. It does not edit the
programme record, the summary, any deployment system, or any repository file.

## Evidence separated by delivery state

Approval, evidence, and delivery state are independent. A merged change
establishes what implementation landed. It does not establish verification,
release, deployment, or an outcome.

| State | Established here | Needed to establish it |
| ----- | ---------------- | ---------------------- |
| Approved | Nothing. | Approval record, if material. |
| Implemented | Merge reported, unverified. | Merge record, revision, date. |
| Verified | Nothing. | Verification record and revision. |
| Released | Nothing. | Release record naming revision. |
| Deployed | Nothing; evidence absent. | Deployment record, or deferral. |
| Outcome-validated | Nothing. | Baseline, measure, result, owner. |

A merge does not supply approval retroactively. A deployment record must name
the environment, revision, time, actor, result, and acceptance evidence. Its
absence is not proof of failure; it means the deployed state is not
established.

## Blocker register and proposed dispositions

`B1` and `B2` are local labels for this reconciliation, not programme
identifiers. Preserve the existing programme identifier when one is available.

### B1: implementation-scoped blocker

The programme record is reported to keep blocking work on an implementation
whose merge is reported. B1 gates implementation-scoped work. The proposed
disposition is removal, conditional on two checks: the merge record must be
verified at the required revision and capability scope, and the blocker's
actual unblock condition must be that merge.

A merged implementation satisfies an implementation-level prerequisite.
Keeping the edge because a tracker or summary still displays it is the
stale-blocker failure the problem contract prohibits. Recheck the edge against
its actual unblock condition, not against a recent activity window or the
summary's wording. Resolve the edge with linked evidence; do not delete the
blocker's history.

### B2: deployment-validation dependency

B2 gates work that consumes the deployed capability: release, deployment, and
later outcome validation. The proposed disposition is retention as an open
dependency, reclassified away from the implementation edge.

Deployment evidence is absent. A merge is not a deployment, and repository
delivery is not host convergence. The unblock condition must name the
deployment record or an authorized deferral. Retaining B2 is not the same as
retaining B1; the gated scope differs.

When recorded, B2 must name the provider, consumer, required capability and
revision, linked evidence, last check, and the work it gates. The brief
supplies none of these, so they remain open rather than invented.

### B3: unsupported completion claim

The daily summary's "complete" is not a blocker. It is a status claim that
supports no state beyond a reported implementation merge. Reject it as status
evidence and correct its source.

### Conditions that change these dispositions

If the blocker's actual unblock condition is deployment rather than merge, B1
is not removable. Retain it and reclassify it as B2. If the merge record fails
verification at the required revision, B1 remains. The daily summary is
neither the reason to remove B1 nor the reason to retain it.

## Treatment of the daily summary

The daily summary is a discovery aid, not a status authority. The governing
contract directs using summaries to locate evidence, then inspecting the
underlying merge, release, or deployment record. Generated documents and agent
summaries do not approve themselves by repetition.

The summary's "complete" claim conflates separate states. Completion must be
named at a boundary: implemented, verified, released, deployed, or
outcome-validated. The available evidence supports at most a reported
implementation merge. It does not support deployment, and therefore does not
support an unqualified completion claim.

The contradiction is recorded rather than smoothed. If the underlying records
show a deployment the programme record missed, the programme record is the
artefact to correct. If they do not, the summary is wrong and its source must
be corrected. If the summary is generated, fix its source data and regenerate
it; do not hand-edit a derived artefact and assume the edit survives the next
run. Do not copy "complete" into a terms of reference, design, roadmap, or
ExecPlan.
