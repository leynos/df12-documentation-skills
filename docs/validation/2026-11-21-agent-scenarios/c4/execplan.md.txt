## Purpose / big picture

The library is at major version 2. According to the brief, it exports a
function that was introduced after its latest formal release tag. The sponsor
wants that function renamed before the next release, so the release publishes
the intended name instead of freezing a provisional one.

Before the change, a caller writes:

```plaintext
value = library.OLD_NAME(input)
```

After the change, the same caller writes:

```plaintext
value = library.NEW_NAME(input)
```

`OLD_NAME` is the current exported name and `NEW_NAME` is the approved final
name; both are unresolved intake facts (`TOR-OPEN-001`). The function's
parameters, return type, visibility, errors, and observable behaviour do not
change. The deliberate observable difference is that `OLD_NAME` no longer
resolves and `NEW_NAME` does.

The change closes the naming decision before the next formal release. It does
not close any roadmap item, and no roadmap item was supplied.

## Constraints

- Do not add source-API compatibility machinery for `OLD_NAME`. That includes
  an alias, deprecated entrypoint, re-export, facade, wrapper, dual
  implementation, or migration shim. The brief states that the function was
  introduced after the latest formal release tag; `EP-M0` must verify that
  lineage before editing. On that premise the function is an unreleased API
  change and the compatibility prohibition applies. Even a named
  development-branch consumer does not create an exception.
- Rename the definition, every re-export, and every in-repository caller in one
  atomic change. Do not create a milestone in which both names exist.
- Preserve the function's signature, visibility, error behaviour, and
  observable behaviour. The only intended public change is the name.
- Do not modify any other exported symbol, any released contract, or any
  persisted-data or wire format. If an incidental public change appears, stop.
- Record the baseline before editing: the latest formal release tag of the
  applicable package, its commit, and evidence that the function is absent from
  that tag's exported surface. If the function appears in any formal release
  tag, stop: the change is then a released-contract change, not an
  unreleased-surface rename.
- Do not modify, rewrite, or retag historical release notes, release tags, or
  published artefacts. Current documentation and the unreleased changelog may
  change.
- Do not change the package version or release schedule. The release manager
  owns both.
- Do not add or change a dependency.
- Implementation begins only after the user explicitly approves this plan. Do
  not interpret silence as approval.
- Do not perform a production edit while `OLD_NAME`, `NEW_NAME`,
  `BASELINE_TAG`, or the repository gate commands are unresolved. Read-only
  reconnaissance at `EP-M0` may resolve them. Guessing any of them violates
  this constraint.

## Risks

- Risk: a reference in an example, doctest, generated file, or feature-gated
  export is missed.
  Severity: medium. Likelihood: medium. Mitigation: whole-repository search
  over tracked and generated sources, plus the build and API-surface checks.
- Risk: the tag believed to be the latest formal release is not the latest for
  the applicable package, or no tag is identifiable.
  Severity: high. Likelihood: medium. Mitigation: list tags and their commits,
  identify the applicable package, and record the evidence. If uncertain, stop
  rather than guess.
- Risk: the function was in fact published in a formal release, falsifying the
  brief's lineage claim.
  Severity: high. Likelihood: low. Mitigation: inspect the tag's exported
  surface at `EP-M0`; stop and reassess if present.
- Risk: `NEW_NAME` collides with an existing symbol.
  Severity: medium. Likelihood: medium. Mitigation: search before editing;
  escalate for a different name rather than shadow or alias.
- Risk: a formal release tag is cut before the rename merges.
  Severity: high. Likelihood: medium. Mitigation: coordinate with the release
  manager; recheck tag state before merge; stop if already tagged.
- Risk: a development-branch consumer breaks.
  Severity: low. Likelihood: medium. Mitigation: communicate if the consumer is
  known. Do not add an alias.
- Risk: generated documentation or code reintroduces the old name after the
  search.
  Severity: medium. Likelihood: medium. Mitigation: regenerate from updated
  inputs and repeat the search after generation.
- Risk: no API-surface extraction tool is available.
  Severity: low. Likelihood: medium. Mitigation: use a compile-based consumer
  fixture as the contract-level boundary and record the substitution.

## Verification plan

This change introduces no algorithmic, concurrency, or state-machine
invariant. Its obligations concern the exported name set, signature
preservation, and reference completeness. The surface is finite and observable,
so API comparison plus compile-based and search checks are proportionate.

### Abstract model

`S(T)` is the public export set at formal release tag `T`. `S_w` is the export
set in the working tree before the change, and `S_t` is the export set after
the change. `sig(f)` is the declared signature of symbol `f`, including
parameter and return types, generic constraints, defaults, and visibility.
`beh(f)` is observable behaviour over the existing test corpus.

Precondition: `OLD_NAME` is in `S_w`, `OLD_NAME` is absent from `S(T)` for
every formal release tag `T`, and `NEW_NAME` is absent from `S_w`. Target:
`S_t = (S_w \ {OLD_NAME}) ∪ {NEW_NAME}`, with
`sig(NEW_NAME) = sig(OLD_NAME)` and `beh(NEW_NAME) = beh(OLD_NAME)`.

### Invariants and lemmas

- `INV-API-SWAP`: the public export set loses exactly `OLD_NAME` and gains
  exactly `NEW_NAME`.
- `INV-SIGNATURE`: `NEW_NAME` has the same signature as `OLD_NAME` had.
- `INV-BEHAVIOUR`: the existing test corpus observes the same behaviour
  through `NEW_NAME` as it did through `OLD_NAME`.
- `INV-NO-ALIAS`: `OLD_NAME` is absent from the export set, and no alias,
  deprecated entrypoint, facade, wrapper, or dual export preserves it.
- `INV-LINEAGE`: `OLD_NAME` is absent from every formal release tag, and the
  latest tag and commit are recorded.
- `L-CALLERS`: if a whole-repository search over tracked current sources finds
  no `OLD_NAME` and the tree builds, every in-repository reference has been
  updated. This relies on the search covering generated sources and on the
  build exercising every export path.
- `L-SURFACE`: if the API comparison shows `NEW_NAME` present, `OLD_NAME`
  absent, an unchanged signature, and no other delta, then `INV-API-SWAP`,
  `INV-SIGNATURE`, and `INV-NO-ALIAS` hold for the compared surface.

### Axioms (trusted, not verified here)

- `AXIOM-API-TOOL`: the selected API dump or compile-based consumer check
  reflects the package's actual public exports, including re-exports.
- `AXIOM-SEARCH`: the search covers all tracked text and generated source
  files, excluding version-control metadata and historical release notes
  deliberately.
- `AXIOM-COMPILER`: the compiler or interpreter rejects unknown symbols and
  reports duplicate or ambiguous exports.

If no API-extraction tool exists, replace `AXIOM-API-TOOL` with a
compile-based consumer fixture that calls `NEW_NAME` and fails on `OLD_NAME`,
and record the substitution in `Decision log`.

### Methods per obligation

Each obligation records the method, rationale, domain, artefact, evidence, and
non-vacuity check. Exact commands are recorded at `EP-M0`; the placeholders are
intentional.

`INV-API-SWAP`:

- Obligation: the export set loses `OLD_NAME` and gains `NEW_NAME`.
- Method: API comparison before and after, plus a consumer fixture.
- Rationale: the export surface is finite and directly observable, so a
  complete comparison is stronger and cheaper than sampling.
- Domain: the public export set at the parent commit and at the change.
- Artefact: `<api-surface>` output and the fixture path recorded at `EP-M0`.
- Evidence: `<api-surface>` at both revisions shows one removal and one
  addition, and the fixture compiles. Discharge: both hold.
- Non-vacuity: the pre-change output contains `OLD_NAME`; the post-change
  output contains `NEW_NAME`.

`INV-SIGNATURE`:

- Obligation: `NEW_NAME` has the signature `OLD_NAME` had.
- Method: signature comparison, or parameterized fixture calls covering every
  parameter and the return type.
- Rationale: each parameter and the return type form a finite partition, so
  compile-time calls exercise every class.
- Domain: all parameters, generic constraints, defaults, and the return type.
- Artefact: API output or fixture recorded at `EP-M0`.
- Evidence: signatures compare equal and every call compiles. Discharge: both
  hold.
- Non-vacuity: at least one call exercises each parameter and the return
  value; a fixture that omits a parameter fails the coverage check.

`INV-BEHAVIOUR`:

- Obligation: existing behaviour is unchanged through the new name.
- Method: existing focused tests, run before and after.
- Rationale: the existing corpus defines current behaviour, so it is the
  independent oracle for "nothing else changed".
- Domain: the existing tests that call the function.
- Artefact: the existing test files.
- Evidence: the same pass count and results before and after. Discharge:
  identical results.
- Non-vacuity: at least one test calls the function and asserts an output; a
  zero-test run fails the check.

`INV-NO-ALIAS`:

- Obligation: no compatibility machinery preserves `OLD_NAME`.
- Method: API output plus whole-repository search.
- Rationale: an alias can appear as an export name or as a deprecated wrapper,
  so the export set and the source text both need checking.
- Domain: the export set and tracked current sources, excluding historical
  release notes.
- Artefact: API output and search log.
- Evidence: `OLD_NAME` is absent from exports and current sources. Discharge:
  zero current-source hits and no alias export.
- Non-vacuity: the pre-change search finds at least one `OLD_NAME`; a
  zero-hit pre-change search fails. The pre-change API output also contains it.

`INV-LINEAGE`:

- Obligation: the function is unreleased, and the baseline is recorded.
- Method: tag listing, commit resolution, and export inspection at the tag.
- Rationale: the policy depends on the surface's release lineage, which is a
  historical fact requiring the tag's actual export set.
- Domain: every formal release tag, with the latest resolved to a commit;
  pre-releases are recorded separately.
- Artefact: the recorded tag list, commit, and export output.
- Evidence: the latest formal tag is identified and `OLD_NAME` is absent from
  its export output. Discharge: recorded evidence.
- Non-vacuity: the tag's export output is non-empty and covers the module
  that later gained the function.

`L-CALLERS`:

- Obligation: every in-repository reference is updated.
- Method: whole-repository search plus build.
- Rationale: the compiler catches reachable references; the search catches
  non-compiled references such as documentation, examples, and feature-gated
  code.
- Domain: tracked text and generated sources, excluding version-control
  metadata and historical release notes.
- Artefact: search log and build result.
- Evidence: zero current-source hits and a passing build. Discharge: both
  hold.
- Non-vacuity: seed a scratch reference to `OLD_NAME`, confirm the search
  finds it, delete it, and record the deletion.

`L-SURFACE`:

- Obligation: the only public delta is the rename.
- Method: API comparison against the known delta.
- Rationale: a whole-surface diff proves no unrelated public movement, which a
  single symbol lookup would miss.
- Domain: the full public export set at the parent commit and at the change.
- Artefact: the API diff.
- Evidence: exactly one removal and one addition, with no other delta.
  Discharge: the diff matches.
- Non-vacuity: an unrelated public symbol still appears in the output, proving
  it is not empty; a diff against an empty dump fails.

### Non-vacuity and negative control

The pre-change API output is a witness that extraction sees the module and the
old symbol. The post-change output is a witness that it sees the new symbol. The
search must have a pre-change hit; otherwise its post-change zero is vacuous.
After the rename, a scratch consumer that calls `OLD_NAME` must fail to
resolve; that is the negative control. Delete the scratch file afterwards and
record the deletion. If the language cannot produce a compile-fail check,
record why and use the API output's absence of `OLD_NAME` plus the search log
as the independent counterexample.

### Formal verification decision

No model checking or formal proof is needed. The obligations are set equality,
signature equality, and reference completeness over a finite observable
surface. Stronger methods would not cover the residual risk, which is a
consumer outside the repository; the release-lineage classification and
release timing address that boundary.
