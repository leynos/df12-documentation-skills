## Purpose / big picture

A released version 2 application exposes an internal public method: a
declaration marked `public` (or the language's equivalent) whose only consumers
are three modules of the same application. A term of art used throughout this
plan, "application-internal interface", means exactly that: visible outside its
own file or package, but not published to any consumer outside the application.
The method owner wants its signature replaced and the three calling modules
updated.

Today the method has one signature, and the three modules call it in that form.
After the change, the declaration carries the approved new signature, every
call site in those three modules uses it, the project builds and its tests pass,
and no compatibility construct keeps the old call form alive. Illustratively,
and only illustratively, a call that reads `service.lookup(key)` might become
`service.lookup(key, options)`; the real signatures are recorded at `EP-M0` and
approved by the method owner. The example is not a design proposal.

The observable acceptance is behavioural, not structural: a full build against
the new signature succeeds, the three modules' tests pass with the same
observable results as the recorded baseline, a repository-wide search finds no
call site using the old parameter list outside deliberate historical records,
and the diff contains none of the following: alias, overload, deprecated
entrypoint, facade type, adapter, wrapper, dual implementation, or temporary
shim.

Why no compatibility layer: the surface is an application-internal interface,
and the governing policy prohibits source-API compatibility machinery for that
class of surface. The three internal callers update in the same change, so the
compatibility question, "compatible with whom or what?", has no external
answer. The full reasoning and its provenance are recorded in the adjacent
`api-surface-compatibility-assessment.md`, in the same directory as this plan.

Implementation begins only after the user explicitly approves this plan and the
concrete new signature. Silence is not approval.

## Constraints

- The declaration change and all three caller updates land as one coherent
  change set. After the milestone, no old-signature path remains in the source
  tree. There is no dual-interface plateau.
- No source-API compatibility machinery: no alias, overload preserving the old
  parameter list, deprecated entrypoint, facade, adapter, wrapper, dual
  implementation, runtime detection of the old form, or temporary shim. The
  policy basis is recorded in `api-surface-compatibility-assessment.md`.
- The change is a signature replacement, not a behaviour change. If the
  approved new signature changes semantics, or if adapting a caller cannot be
  done without choosing new semantics, stop and escalate under `D5`.
- The consumer set is exactly the three modules confirmed at `EP-M0`. A fourth
  caller, a consumer outside the application, or any persisted or wire-format
  use of the signature stops the work and reopens the classification.
- No new dependencies. No unrelated refactoring, renaming, formatting sweep, or
  drive-by cleanup.
- The method's visibility and error contract stay as they are unless the
  approved signature explicitly changes them.
- Persisted data and wire formats are untouched. They are a separate obligation
  from source-API compatibility; a discovery that the signature participates in
  one is an escalation, not a reason to preserve the old source interface.
- Commit gates follow the target repository's own guidance, read at `EP-M0`
  (prefer its Makefile targets). Gates run sequentially, never in parallel, and
  each commit is gated. Do not weaken, skip, or exclude a gate to make the
  change pass.
- Work happens on a non-main branch. Commits use the repository's conventions.
- This ExecPlan file is excluded from all file-count and line-count budgets,
  including when it is added or updated in the same change.
- Implementation begins only after explicit user approval, unless the user has
  already given standing instructions that authorize this exact work.

## Risks

- Risk: a reflective, dynamic, or dependency-injected invocation bypasses
  compile-time checking and is missed when the signature changes.
  Severity: high. Likelihood: medium, language-dependent. Mitigation: the
  `EP-M0` audit searches the method name as a string, framework registration or
  binding sites, serialization attributes, and reflection use, and records the
  result as an axiom with evidence; tests exercise each module's call path.
- Risk: the "only three modules" premise is false, or an external consumer
  exists through a published package or documented extension point.
  Severity: high. Likelihood: low, but the scenario statement is the only
  evidence. Mitigation: repository-wide consumer audit plus package/publication
  review at `EP-M0`; escalation and reclassification on discovery.
- Risk: the new signature smuggles a semantic change, so behaviour diverges
  while the build stays green.
  Severity: high. Likelihood: medium. Mitigation: characterization tests before
  the change; explicit confirmation of the signature's intended semantics
  (`D5`); escalation if semantics are unclear.
- Risk: one or more of the three modules lacks test coverage of its call path,
  so a regression escapes.
  Severity: medium. Likelihood: medium. Mitigation: baseline characterization
  tests in `EP-M1`, with a seeded-fault negative control.
- Risk: live documentation, examples, or generated reference material still
  show the old signature after the change.
  Severity: low. Likelihood: medium. Mitigation: search documentation at
  `EP-M0` and update live material in `EP-M3`; list deliberate historical
  records rather than editing them.
- Risk: gate failures from the host build queue or a missing optional tool are
  mistaken for code failures.
  Severity: low. Likelihood: medium. Mitigation: follow host build policy,
  record raw gate logs, and distinguish environment failures from regressions;
  never bypass admission or weaken a gate.
- Risk: the atomic commit is split for convenience, leaving a commit or a
  released state that exposes both call forms.
  Severity: medium. Likelihood: low. Mitigation: one commit for the declaration
  and the three callers; if history must differ, a squashed merge so no usable
  state contains the split.

## Decision log

- D1. Decision: classify the method as a private API under the
  application-internal exclusion, regardless of the application's release 2
  status, because the release number belongs to the application, not to a
  published contract for this method. Rationale: the policy instructs
  evaluating the surface and its release lineage, not merely the branch's
  position relative to a tag; an internal declaration does not become external
  by shipping. Rejected option: treating version 2 as a semantic-versioning
  commitment for an internal method. Date/Author: 2026-11-21, authoring agent;
  approval pending.
- D2. Decision: propose no compatibility machinery of any kind. Rationale: the
  surface is in a prohibited category, the three consumers are internal and
  change with the interface, and no external consumer, deployed peer, persisted
  record, or wire format is known. Rejected option: an alias or deprecated
  overload to smooth the transition; it is prohibited for this surface and
  would leave an obsolete source interface in the tree. Date/Author:
  2026-11-21, authoring agent; approval pending.
- D3. Decision: one atomic milestone for the declaration plus all three
  callers. Rationale: compatibility is unnecessary for an atomic change, and a
  coherent plateau requires correctness, not parallel old and new interfaces.
  Rejected option: staged migration with a temporary overload to keep every
  intermediate commit green. Date/Author: 2026-11-21, authoring agent.
- D4. Decision: do not author a terms of reference or a technical design
  document for this change. Rationale: the change alters neither problem-space
  intent nor architecture. A terms of reference would have to invent users,
  goals, or stakeholders, which its own rules forbid; a technical design has no
  architecture to choose. The compatibility assessment is the design-level
  record this change needs. Rejected option: ceremonial upstream documents that
  would manufacture content. Date/Author: 2026-11-21, authoring agent.
- D5. Decision: treat semantics as unresolved. The plan assumes a mechanical
  signature replacement that preserves observable behaviour; a semantic change
  reopens scope and requires explicit approval. Rationale: the request does not
  state whether behaviour changes, and silence is not evidence of no change.
  Rejected option: assuming semantics from the wording. Date/Author: 2026-11-21,
  authoring agent.
- D6. Decision: use the compiler rejection as the red stage and characterization

## Verification plan

### Abstract model

Model the application as a set of modules containing one declaration `M` with
signature `S_old`, and three modules `A`, `B`, and `C` containing call sites
that use `S_old`. The signature is replaced by `S_new`.

States:

- Baseline: `M` declares `S_old`; every call site uses `S_old`; build valid.
- Red: `M` declares `S_new`; at least one call site still uses `S_old`; build
  invalid. This state is a diagnostic checkpoint, never a commit or release.
- Target: `M` declares `S_new`; every call site uses `S_new`; exactly one
  declaration; build valid; tests show baseline behaviour.

Preconditions: exactly three internal consumers; no external consumer; no
persisted or wire-format encoding; the build and tests include all three
modules. `EP-M0` audits every precondition; AXIOM-no-external-consumers and
AXIOM-build-complete record the resulting evidence, and the persistence check
is recorded in E-M0-audit. Violating a precondition moves the work to
`BLOCKED`, not to a compatibility layer.
Malformed or type-incompatible caller data is a legitimate build failure whose
adaptation is in scope; if adaptation needs a semantic decision, stop under the
ambiguity tolerance. The expected result is the target state reached in one
coherent change set.

### Invariants and lemmas

- INV-single-declaration: in the target state the application declares exactly
  one method with the approved new signature; no overload, alias, or second
  declaration preserves the old parameter list. Linked to REQ-declaration and
  REQ-no-compat.
- INV-no-stale-call: in the target state no repository-owned call site invokes
  the old signature; any remaining textual match is a deliberate historical
  record listed in the evidence. Linked to REQ-callers.
- INV-no-compat-construct: the change contains no construct listed in
  REQ-no-compat. Linked to REQ-no-compat.
- INV-behaviour-preserved: the method and the three modules produce the recorded
  baseline observable results and error behaviour for the covered inputs.
  Linked to REQ-behaviour.
- INV-scope: the changed path set equals the expected path set within the
  tolerance for tests and live documentation. Linked to REQ-scope.
- L-static-exhaustiveness: if the full build succeeds, and the dynamic audit
  finds no resolved-by-name invocation, then every call site uses `S_new`.
  Depends on AXIOM-build-complete and L-dynamic-audit.
- L-dynamic-audit: either the audit enumerates every dynamic invocation found
  by name, registration, and reflection searches, or it records that the
  language and frameworks in scope support no such path, with evidence. It does
  not establish the internal correctness of third-party frameworks.
- L-behaviour-equivalence: if the method body is unchanged apart from parameter
  threading, and each caller supplies the same values as the baseline for the
  mapped arguments, the observable behaviour is unchanged. This is a claim
  tested by characterization tests, not proved.
- L-scope: the diff path set matching the expected set, with all changed hunks
  classified, implies no unrelated change. This is a review lemma, not a
  substitute for reading the diff.

### Axioms (trusted, not verified here)

- AXIOM-build-complete: the project's build or typecheck compiles the
  declaration and all three modules together. Evidence: the red-stage failure
  names each affected caller. If a module is excluded from the default build,
  the verification commands are extended or the work is escalated; the axiom is
  not assumed.
- AXIOM-dynamic-scope: the dynamic-invocation finding recorded at `EP-M0`
  describes the actual language, framework, and repository in scope. Pending
  evidence until then.
- AXIOM-test-runner: the project's test command executes tests for all three
  modules. Evidence: the `EP-M1` baseline run lists tests from each.
- AXIOM-no-external-consumers: the scenario's "used only by three modules"
  statement, audited at `EP-M0` against package exports, publication metadata,
  and documented extension points.
- AXIOM-deterministic-baseline: the covered tests are deterministic enough to
  compare before and after. Any flaky or order-dependent test is recorded and
  excluded from behavioural evidence, with the exclusion justified.

Third-party internals are not verified here. Repository-owned configuration and
integration logic is checked at the real interface through the build and tests.

### Methods per obligation

- Obligation: INV-no-stale-call and L-static-exhaustiveness.
  Method: full-project build or typecheck plus a repository-wide name search.
  Rationale: a static build is exhaustive over statically resolved call sites,
  and the search covers string-based and reflective uses that the build cannot
  see. Domain: all repository-owned source at the recorded base revision plus
  the change. Artefact: the recorded build command and search command.
  Evidence: at red, the build fails naming each of the three callers for the
  intended reason; at green, the build passes and the search returns only the
  new form or listed historical records. Non-vacuity: the red failure is the
  primary demonstration; after green, temporarily reverting one caller must
  fail the build for that module, then the fault is reverted and green is
  re-established.
- Obligation: INV-single-declaration and INV-no-compat-construct.
  Method: declaration inspection, diff review, and targeted searches for
  alias, overload, deprecation, adapter, facade, wrapper, and dual
  implementation patterns. Rationale: these are review properties whose
  presence is directly observable in the diff; the search is a memory aid, not
  a proof. Domain: all changed files.
  Artefact: the review checklist entry in `EP-M2` and the recorded search
  commands. Evidence: one declaration; searches return no prohibited construct;
  review sign-off recorded. Non-vacuity: during review, a scratch copy
  containing one artificial overload and one alias is checked; the review must
  flag both; the scratch copy is deleted and the check re-run clean.
- Obligation: INV-behaviour-preserved and L-behaviour-equivalence.
  Method: characterization or approval tests, parameterized where the input
  partitions are finite, plus the existing suite. Rationale: the behaviour is
  meant to be unchanged, so the baseline is the oracle; the skill accepts
  approval tests where Red-Green-Refactor does not apply to unchanged
  behaviour. Domain: the recorded baseline scenarios for each caller, including
  at least one success and, where the method can fail, one error path per
  affected module.
  Artefact: test files for the three modules; at least one test per caller that
  invokes the method and asserts an observable result. Evidence:
  E-M1-baseline captured before the edit; the same tests pass after it.
  Non-vacuity: each caller has a witness test; a seeded mutation of the method
  body (for example, returning a different value on the covered path) must fail
  at least one test; the mutation is reverted and green re-established.
- Obligation: INV-scope.
  Method: `git diff --name-only` and `git diff --numstat` against the base
  revision, with each hunk classified by purpose. Rationale: mechanical and
  complete for the working tree. Domain: the whole change set.
  Artefact: the expected path set recorded at `EP-M0` and the E-M3-diff
  transcript. Evidence: E-M3-diff matches the expected path set and the
  budgets. Non-vacuity: the expected path set is written down at `EP-M0` before
  the change, so an unexpected path is detectable rather than normalised after
  the fact.

### Formal verification decision

No model checking, state-machine method, property prover, or formal proof is
planned. The change introduces no new state, ordering, concurrency, arithmetic,
or data invariant; its only universal claim is that no stale call site remains,
which a complete static build plus a dynamic-invocation audit establish for the
stated scope. A prover would add nothing that the compiler does not already
decide for statically resolved calls, and would leave dynamic dispatch
unverified. This decision is recorded as `D8`. Residual gaps: dynamic invocation
outside the audited mechanisms; external consumers outside the scenario premise;
semantic drift beyond the characterized inputs.

### `EP-M1` characterization baseline for the three calling modules

Add tests only. Run the existing suite and record the baseline result. For each
of the three modules, confirm there is a test that invokes the method's call
path and asserts an observable result; where coverage is absent, add the
smallest characterization test that records the current behaviour, including an
error path where the method can fail. Characterization tests are expected to
pass before and after the change; they are the behavioural oracle, not a
red-green pair. If writing a test requires changing production code, stop and
escalate.

Demonstrate non-vacuity: apply a temporary seeded mutation to the method body on
the covered path, confirm at least one characterization test fails for the
intended reason, revert the mutation, and confirm green. Record the transcript.
Run the repository's test and lint gates for the touched test files, commit the
tests, and record the commit identifier.

Acceptance evidence: E-M1-baseline (test results before the production change)
and E-M1-seed (mutation rejected, fault reverted). Recovery: the tests are
additive and can be reverted without affecting production behaviour.

### `EP-M2` atomic signature replacement and caller updates

First change only the declaration to the approved new signature. Run the focused
build and record the failure: it must name each of the three calling modules for
the intended reason. This is the red stage; do not commit it.

Update each caller with the minimal adaptation: pass the approved arguments,
handle the result as before, preserve visibility, and change nothing else. Do
not add an overload, alias, deprecation marker, adapter, or wrapper. Run the
focused build and the module tests until green. Run the repository-wide search
for the old form and classify every remaining match; the only acceptable
remaining matches are deliberate historical records, listed individually.

Demonstrate non-vacuity for the stale-call invariant: temporarily revert one
caller's update, confirm the build fails for that module, restore the update,
and confirm green. Record both transcripts. Review the complete diff against the
compatibility checklist: exactly one declaration; no prohibited construct;
no unrelated hunk; every changed path accounted for.

Land the declaration and all three caller updates as one commit (or one squashed
merge if the repository's conventions force intermediate commits) so that no
usable repository state exposes both call forms. Gate the commit with the
repository's format, lint, typecheck, and test commands, run sequentially.

Acceptance evidence: E-M2-red, E-M2-green, E-M2-search, E-M2-seed, E-M2-review,
and the commit identifier. Recovery: revert the commit to return to the
baseline; never leave a red tree on a shared branch.

### `EP-M3` documentation update, gates, and delivery closure

Search live documentation, examples, and generated reference material for the
old signature and update every live statement. Do not rewrite historical
records, such as completed plans or release notes for past versions; list them

conventions require one, and phrase it as an internal interface change with no

Run the complete gate sequence sequentially with logs captured under `/tmp`,

regressions, without waiving any gate. Reconcile discoveries: if implementation

Update `Progress`, `Outcomes & retrospective`, and the revision note. Mark the

Acceptance evidence: E-M3-docs, E-M3-gates, E-M3-diff, and the final status

characterization tests are additive and independently revertible. The red state

recorded base revision or finish the callers before yielding. The single
signature commit is revertible as a unit. Every seeded fault is explicitly
reverted and the green state re-established before the milestone closes. Gate

normal branching, commits, and reverts is required. If the tree is dirty from
unrelated work at `EP-M0`, stop and resolve ownership before proceeding rather
