# API surface compatibility assessment: internal method signature replacement

Status: Draft decision record, awaiting user approval. This record proposes a
compatibility approach; it does not approve implementation.

Date: 2026-11-21.

Companion: `execplan-replace-internal-method-signature.md`, in the same
directory as this record.

## 1. Scope

The change request is: a released version 2 application has an internal public
method used only by three modules. Replace its signature and update the
modules.

This record classifies the method's API surface and release lineage, names the
consumers, and settles whether any source-API compatibility obligation applies.
It does not choose the new signature, which the method owner approves, and it
does not design a persisted-data or wire-format migration, because the supplied
scenario names none.

## 2. Classification

| Question | Answer |
| --- | --- |
| Surface kind | Application-internal interface declared `public` |
| Release lineage of the surface | Not a published 1.0+ API contract |
| Consumers | Three internal modules |
| Persisted or wire-format encoding | None identified |
| Applicable exclusion | Private APIs, including application-internal public declarations |

Basis for each row. The scenario says the method is internal and used only by
three modules of the same application. Release 2 is the application's release
number; the method is not described as published outside the application, and
the release number of the enclosing application does not convert an internal
declaration into an external contract. The consumer count and the absence of a
persisted or wire-format encoding are stated by the scenario and must be
verified by repository-wide audit at reconnaissance. The applicable exclusion
is quoted in §7.

The four policy exclusions are independent. This surface falls in the first
category, so the assessment does not need to rely on the test-only, pre-1.0, or
unreleased-API categories. The governing instruction is to evaluate the surface
and its release lineage, not merely whether the branch sits ahead of a tag.
Here the surface is application-internal at every release of the application.

## 3. Compatibility approach

Decision: none.

The signature is replaced and all three calling modules are updated within one
coherent change. No alias, deprecated entrypoint, overload, facade type,
adapter, wrapper, dual implementation, or temporary shim is added. The
prohibited constructs are not merely unnecessary here; the governing policy
directs that they must not be prescribed for this class of surface.

The compatibility question, "compatible with whom or what?", has no external
answer. The only consumers are three modules of the same application, and this
change updates them together. No deployed peer, persisted record, or wire
format encodes the signature. Compatibility would not be required if the work
landed as one atomic change, so it is not introduced to manufacture an
intermediate plateau.

## 4. Persisted data and wire formats

This is a separate obligation from source-API compatibility, and the supplied
scenario identifies none. If reconnaissance finds that the signature
participates in serialization, remote invocation, stored callbacks, or any
other deployed encoding, that is a real migration question. Model the deployed
state and the outcome to preserve explicitly; do not use it to justify keeping
the obsolete source interface. Escalate before proceeding.

## 5. Conditions that require reclassification

The classification must be revisited if any of the following appears:

- an external consumer, such as a published SDK, plugin interface, or
  documented extension point used by third parties;
- membership of the method in a separately released package's formal API
  contract;
- a deployed peer or persisted record that encodes the signature;
- a project policy that explicitly commits to the method's current form.

If one appears, stop, record the evidence, and assess the surface against the
released 1.0+ rules: name the real external consumer and the existing
commitment, then choose a deliberate compatibility or migration approach. Do
not keep the internal label once the evidence contradicts it.

## 6. Conflicts

No inherited conflict exists: no terms of reference, technical design, ADR, or
other artefact supplied with this request demands source compatibility. If one
is later found to demand a shim, record the conflict for explicit upstream
resolution rather than implementing the shim or silently rewriting history.
