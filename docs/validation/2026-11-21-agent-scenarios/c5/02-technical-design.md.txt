## 1. Problem and context

A function was shipped in version 2.1 and is therefore part of a released
contract. An explicit compatibility commitment covers it, and at least one
external consumer is deployed against it. The current branch is ahead of the
release tag and contains unreleased work. The change request does not state
what the new behaviour is, which part of the contract changes, or the exact
terms of the commitment; those remain open (TOR-OPEN-001 and TOR-OPEN-002).

The design question is consequently twofold. First, what compatibility
obligation attaches to this function, given the branch position. Second, what
approach satisfies that obligation for each class of change. The specific
change, once supplied, selects a row in the decision table in §3.6; it does not
alter the classification itself.

## 2. Scope

In scope: the released function's public source contract, its in-repository
callers, its documentation, its deprecation or migration path, and the release
gate for removing the old entry point.

Out of scope: unrelated public surfaces; package-wide compatibility policy; the
choice of new behaviour (an intake input); and persisted-data or wire-format
migration except as a separate assessment required by §5.5.

Goals and non-goals: TOR-GOAL-001, TOR-GOAL-002, TOR-NONGOAL-001, and
TOR-NONGOAL-002 in the constraint record.

### 3.2 Verdict

The function is a released 1.0-or-later source contract with a known deployed
external consumer and an explicit compatibility commitment. It falls outside
every prohibited category in the governing policy: it is not a private or
application-internal interface, not a test-only surface, not pre-1.0, and not
an unreleased change ahead of the latest tag. Compatibility or a deliberate
migration is therefore both required and permitted. The design must name the
consumer, the obligation, and the approach, as the architecture contract
requires.

### 3.3 Why the branch position does not change the classification

Release lineage is a property of the symbol, not of the branch tip. The branch
being ahead of the tag means that edits made on the branch have not yet been
released. It does not withdraw the 2.1 contract from consumers who already have
it, and it does not convert the shipped function into an unreleased API. The
policy is explicit: evaluate the surface and its release lineage, not just
whether the branch is ahead of a tag, and an edit to an already released 1.0+
API does not make that existing contract unreleased.

The rule cuts both ways. Symbols introduced on the branch after the tag, and
present in no release, are unreleased. They may be changed atomically with all
callers and must not acquire a source compatibility layer. The design therefore
classifies per surface rather than per branch.

### 3.4 The atomicity test and the named obligation

The ExecPlan rules ask whether compatibility would be required if the work were
made as one atomic change. Here it would: the deployed consumer is outside the
repository's release control, so an atomic commit still cannot deploy the
consumer. The compatibility path answers "compatible with whom or what?" – with
the external consumer deployed against the 2.1 contract, under the explicit
commitment recorded in TOR-CONSTRAINT-001 and TOR-CONSTRAINT-002.

Two boundaries follow. First, the obligation covers the committed public
surface, not every declaration that happens to be exported. It does not require
compatibility paths for in-repository callers, which adopt the new entry point
in the same change. Second, it does not require a permanent dual
implementation: the commitment's own removal terms bound the deprecation
window.

### 3.5 Compatibility decision

The default approach, pending the change contract and the commitment text, is:

1. Freeze the existing entry point's observable contract for the commitment's
   lifetime. Capture that contract as executable characterization evidence at
   the 2.1 baseline before changing anything.
2. Deliver the new behaviour through a new entry point whose addition does not
   change the meaning or resolution of any existing call.
3. Deprecate the old entry point with documentation and, where the language and
   consumer build policy permit, a machine-readable marker. If a new warning
   would break a consumer that treats warnings as errors, use documentation-only
   deprecation and record the choice.
4. Publish a migration guide and, where practical, an automated migration aid.
5. Remove the old entry point only in a release that the commitment permits,
   with the notice it requires, supported by exported-symbol and release
   evidence.
6. If the intended change is an internal refactor with an unchanged observable
   contract, no new entry point is needed; the change lands atomically behind
   the existing contract and is discharged by equivalence evidence alone.

### 3.6 Decision table by change class

| Change class                                                        | Effect on the 2.1 contract          | Approach                                                                                                                                     |
| ------------------------------------------------------------------- | ----------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| Internal refactor; observable contract identical                    | None                                | Change in place; update all in-repository callers atomically; discharge equivalence evidence.                                                |
| Additive capability; existing semantics unchanged                   | None                                | Add the new entry point or optional surface; leave the old contract untouched; deprecation unnecessary unless the old path is superseded.   |
| In-place behavioural or signature change at the old entry point     | Breaking                            | Do not change in place. Add the new entry point, freeze and deprecate the old one, publish the migration, remove at the commitment-permitted release. |
| Mandatory fix that cannot preserve the old observable behaviour     | Breaking but obligatory             | Escalate to the commitment owner. Options are an advisory with a coordinated consumer update, or a commitment deviation. Record the decision; do not ship silently. |
| Change to a symbol that exists only on the branch, in no release    | None; surface is unreleased         | Change the interface and every caller together; no compatibility layer.                                                                     |

### 3.7 Rejected alternatives

- Changing the function in place and asking the consumer to update in the same
  window: rejected as the default because deployment lag prevents an atomic
  switch, and the explicit commitment forbids relying on one. It remains
  permissible only if the commitment explicitly allows it and the consumer
  confirms a coordinated upgrade.
- A permanent dual implementation: rejected. The commitment bounds the
  deprecation window; an indefinite second path is maintenance cost without a
  named obligation.
- Declaring the function unreleased because the branch is ahead of the tag:
  rejected. It misclassifies the surface and would convert a committed external
  contract into an in-place break.
- Adding compatibility machinery for in-repository callers or branch-only
  symbols: rejected as compatibility theatre. The obligation is per surface and
  is answered by the deployed consumer and the commitment.
- A package-wide compatibility policy: rejected as scope expansion
  (TOR-NONGOAL-001).

## 5. Design

### 5.1 Capturing the 2.1 contract

Before any edit, the maintainers enumerate the observable contract elements of
the released function. At minimum: symbol and signature; argument and return
types; accepted and rejected input classes; error or exception types and the
conditions that raise them; side effects and their ordering; idempotence;
resource ownership; concurrency guarantees; documented performance bounds; and
any serialised or wire representation. Each element becomes a characterization
obligation in TDD-OBL-001. Elements that cannot be established from the 2.1
artefact and its documentation are recorded as gaps, not assumed.

### 5.2 Structure

The design uses two paths where the change is not presentationally transparent:

- The existing entry point remains, with its 2.1 semantics. Leaving the old
  implementation untouched gives the simplest equivalence argument at the cost
  of duplication. Delegating both entry points to a shared core removes the
  duplication but requires a compatibility adapter and the adapter lemma
  L-ADAPTER: the adapter maps every input in the documented 2.1 domain to the
  frozen 2.1 behaviour, and the characterization suite exercises that mapping.
  Choose the frozen implementation unless duplication is material; record the
  choice and its equivalence evidence.
- A new entry point exposes the new contract. Its addition must not change the
  resolution or meaning of existing calls. In languages with overloading,
  default arguments, or implicit conversions, adding an overload can silently
  capture existing call sites; where that risk exists, use a distinct name.

### 5.3 Deprecation and migration

Deprecation communicates direction without withdrawing the contract.
Documentation is mandatory. A machine-readable marker is preferred where it
does not change build outcomes for the consumer. A consumer that compiles with
warnings treated as errors would otherwise be broken by the announcement
itself, which defeats the commitment; in that case the marker is omitted and
the migration guide becomes the notice channel.

The migration guide names the old entry point, the new entry point, the mapping
between them, the behavioural differences, and the removal release. Where the
mapping is mechanical, an automated aid reduces consumer effort and the risk of
a mistranslated call. The deployed consumer is invited to run its
representative workload against the new entry point before the removal release.

### 5.4 Failure modes

- Wrapper drift: the old path gradually adopts new semantics. Detected by the
   characterization suite, which runs against the old path on every change and
   must fail on a seeded mutation.
- Undocumented consumer reliance: the consumer breaks although the documented
  contract is preserved. This is residual risk under TOR-ASSUMPTION-001; only
  consumer acceptance evidence reduces it.
- Deprecation-induced build failure: a new warning breaks a warning-as-error
  consumer. Mitigated by the marker policy in §5.3.
- Overload capture: a new overload changes which function an existing call
  resolves to. Mitigated by a distinct new symbol or a resolution test.
- Partial release: the new entry point ships without the migration guide, or
  the guide describes a symbol that is not yet released. Mitigated by a release
  checklist that treats them as one deliverable.
- Early removal: a later maintainer removes the old path before the commitment
  permits. Mitigated by TDD-OBL-005 and its release gate, not by memory.
- Permanent dual path: the deprecation is never concluded. Mitigated by naming
  the removal release when the commitment is read.

### 5.5 Persisted and wire formats

Source compatibility does not cover data written by earlier deployed versions
or communication with a deployed peer. If the function produces or consumes
persisted data or a wire format, the design requires a separate assessment of
existing records, deployed peers, conversion and rollback, and acceptance
evidence. That assessment neither authorises nor forbids a source-level
compatibility path; the two obligations are independent. Whether the function
does so is `[OPEN]`.

obligations below are design-level because they establish the compatibility
boundary itself. Each carries its own non-vacuity condition; a passing suite
that never exercises the boundary is not evidence.

TDD-OBL-001 discharges L-ADAPTER when the delegated-adapter structure is
chosen; where the frozen implementation is chosen, L-ADAPTER is vacuous because
the old code is unchanged. The ExecPlan records which structure was chosen.

Trusted axioms: AXIOM-COMMITMENT (the exact commitment terms, TOR-OPEN-002);
AXIOM-CONSUMER (the consumer's usage profile, TOR-OPEN-003); AXIOM-TOOLCHAIN
(the language's deprecation, warning, and overload-resolution behaviour). The
design does not verify the consumer's internals or the toolchain; it verifies
repository-owned behaviour against those boundaries.

## 7. Handoff

Selected IDs: TOR-CONSTRAINT-001 to TOR-CONSTRAINT-003, TOR-GOAL-001,
TOR-GOAL-002, TOR-ASSUMPTION-001 to TOR-ASSUMPTION-003; GAP-001 to GAP-006;
TDD-OBL-001 to TDD-OBL-007.

Compatibility assessment: released 1.0-or-later committed source contract with
a deployed external consumer; compatibility or deliberate migration required;
not exempt as an unreleased change.

Acceptance boundaries: equivalence evidence covers the documented 2.1 domain,
not undocumented consumer reliance; the release gate covers exported symbols at
release time, not the consumer's runtime deployment; consumer acceptance must be
obtained separately.

Unresolved decisions: the change class and new contract (TOR-OPEN-001); the
commitment terms and removal schedule (TOR-OPEN-002); the consumer profile
(TOR-OPEN-003); the function's identity (TOR-OPEN-004); the deviation authority
(TOR-OPEN-005).

Readiness: ready for implementation planning only after TOR-OPEN-001 to
TOR-OPEN-004 are closed. The ExecPlan at `03-execplan.md` is a draft that
records these blockers; design acceptance would not bypass its approval gate.
