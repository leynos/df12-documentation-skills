## Purpose / big picture

A function was shipped in version 2.1, an explicit compatibility commitment
covers it, and an external consumer is deployed against it. The team wants to
change the function. Today the change has no specified content and no
implementation plan; the risk is that an implementer edits the shipped function
in place and breaks a consumer that cannot upgrade in lockstep.

After this work, an existing consumer can keep calling the released entry point
and observe the same documented behaviour it had in 2.1, while new callers use
a new entry point that provides the new behaviour. The old entry point is
deprecated, documented, and removed only at a release the commitment permits.
Terms used here: the *contract* is the observable behaviour of the function
under its documented preconditions, including errors and side effects; a
*characterization test* pins observed behaviour rather than a written
specification; the *commitment* is the explicit compatibility promise whose
text is outstanding (TOR-OPEN-002).

Observable acceptance, once the change is supplied: calling the existing entry
point with a 2.1 example produces the recorded 2.1 result, and the repository's
gates pass; calling the new entry point with the agreed example produces the
agreed new result. The work closes no roadmap item; none was supplied.

## Constraints

Hard invariants. Violation requires escalation, not a workaround.

- The existing entry point must preserve its documented 2.1 observable
  contract for the lifetime the commitment requires. No semantic change may
  hide behind the same name.
- The new entry point must not change the meaning or resolution of any existing
  call. In a language with overloading, default arguments, or implicit
  conversions, this constrains naming and signature design.
- In-repository callers of the old entry point must be updated in the same
  change where the surface is not externally committed. No source compatibility
  path is to be created for them.
- No compatibility machinery may be added for symbols that exist only on the
  branch and in no release tag.
- The old entry point may be removed only at a release that the commitment
  permits, with the notice it requires.
- Unrelated public surfaces, package-wide compatibility policy, and dependency
  manifests are out of scope.
- No new dependency is authorised. Any need for one is an escalation.
- Implementation begins only after explicit user approval of this plan, unless
  standing instructions already authorise execution.
- ExecPlan files are excluded from every size count, including this file when
  added or updated.

## Risks

- Risk: the consumer relies on undocumented 2.1 behaviour.
  Severity: high. Likelihood: medium.
  Mitigation: obtain consumer acceptance evidence and a representative
  workload before removal; record the residual risk.
- Risk: the commitment is stricter than assumed, for example a promise never to
  remove the entry point.
  Severity: high. Likelihood: medium.
  Mitigation: read the commitment text before `EP-M2`; keep the frozen
  implementation approach until then.
- Risk: a deprecation warning breaks a consumer that treats warnings as errors.
  Severity: medium. Likelihood: medium.
  Mitigation: documentation-only deprecation if the consumer build policy
  requires; prove with a warning-as-error fixture.
- Risk: the new entry point captures existing calls through overload
  resolution.
  Severity: medium. Likelihood: low.
  Mitigation: use a distinct symbol where the language permits ambiguity; add
  a resolution test.
- Risk: the old path drifts towards the new semantics.
  Severity: medium. Likelihood: medium.
  Mitigation: run the characterization suite against the old path on every
  change; seed a mutation in a negative control.
- Risk: the 2.1 baseline cannot be reconstructed because the tag, tests, or
  build instructions are unavailable.
  Severity: high. Likelihood: low.
  Mitigation: recover the tag and build before any edit; if impossible, stop
  and escalate to the release authority.
- Risk: a useful new entry point is delayed by a contentious name or signature.
  Severity: low. Likelihood: medium.
  Mitigation: record naming as a decision within `EP-M2`; do not block the
  equivalence work on it.

## Decision log

- D1. Decision: classify the function as a released 1.0-or-later committed
  source contract, not as an unreleased change, despite the branch being ahead
  of the tag. Rationale: release lineage is a property of the symbol; an edit
  to a released API does not unpublish its contract. The exemption covers
  symbols present in no formal release tag. Date/Author: 2026-11-21, authoring
  agent.
- D2. Decision: adopt the additive approach as the default – freeze the old
  entry point, add a new entry point, deprecate, migrate, and remove only at a
  commitment-permitted release. Rationale: a deployed consumer cannot be
  updated atomically with the package, so compatibility would be required even
  for one atomic change. The rejected alternative, an in-place break with a
  coordinated consumer upgrade, is permissible only if the commitment allows it
  and the consumer confirms. Date/Author: 2026-11-21, authoring agent.
- D3. Decision: no compatibility path for in-repository callers or branch-only
  symbols. Rationale: the obligation answers "compatible with whom or what?" –
  the deployed external consumer under the commitment – and does not extend to
  callers the change can update atomically. Date/Author: 2026-11-21, authoring
  agent.
- D4. Decision: capture the baseline at the 2.1 release tag, not at the current
  branch tip. Rationale: the branch contains unreleased changes; a baseline
  taken from it would pin behaviour the consumer never had. Date/Author:
  2026-11-21, authoring agent.
- D5. Decision: no formal proof or model checking is planned unless
  reconnaissance shows the function is stateful, concurrent, or
  protocol-bearing. Rationale: the obligations are contract equivalence over a
  documented input domain and API-surface constraints, for which
  characterization plus property-based differential testing are proportionate.
  Date/Author: 2026-11-21, authoring agent.
- D6. Decision: keep the plan at `DRAFT` and do not implement. Rationale: four
  intake facts are missing (the change itself, the commitment text, the
  consumer profile, and the function identity), and the approval gate has not
  been passed. Date/Author: 2026-11-21, authoring agent.
- D7. Decision: treat the size budgets as provisional pending the repository
  survey. Rationale: isolation prevented counting existing files and reading
  comparable plans; invented precision would be misleading. Date/Author:
  2026-11-21, authoring agent.

## Verification plan

### Abstract model

Let `D` be the documented input domain of the released function at the 2.1
baseline, including malformed inputs that the contract says are rejected. Let
`old_2_1(x)` be the observable result of the released entry point at the 2.1
tag for `x` in `D`, where the result comprises the return value, the error or
exception behaviour, side effects, and ordering. Let `old_new(x)` be the same
observable result after the change. Let `new(x)` be the observable result of
the new entry point. Preconditions: `x` satisfies the documented preconditions
of `D`; the 2.1 baseline is built from the release tag. Violated preconditions
are part of the contract: if 2.1 rejects them, equivalence requires the same
rejection class.

### Invariants and lemmas

- `INV-EQUIV`: for every `x` in `D`, `old_new(x) = old_2_1(x)`. Linked to
  `REQ-PRESERVE`.
- `INV-ADDITIVE`: the release exposes the new symbol and changes no existing
  signature, resolution, or documented meaning. Linked to `REQ-ADDITIVE`.
- `INV-WARN`: the chosen deprecation mechanism does not change the consumer's
  build outcome. Linked to `REQ-DEPRECATE`.
- `INV-REMOVAL-GATE`: the old symbol is present in every release the commitment
  does not permit it to be removed from. Linked to `REQ-REMOVAL-GATE`.
- `L-FROZEN`: if the old implementation is left untouched, `INV-EQUIV` follows
  from the unchanged code plus the characterization suite. If the old path is
  delegated to a shared core, `L-ADAPTER` states that the adapter is the
  identity on `D`; it requires both tests and code inspection.
- `L-CONSUMER`: the consumer's exercised calls lie within `D`, or are covered
  by captured regressions. This lemma depends on `AXIOM-CONSUMER` and is not
  discharged by the package's own suite.

### Axioms (trusted, not verified here)

- `AXIOM-COMMITMENT`: the exact terms of the compatibility commitment. Source:
  the commitment document, currently unread (TOR-OPEN-002). The plan's removal
  gate depends on it.
- `AXIOM-CONSUMER`: the consumer's usage profile and deployment lag. Source:
  consumer evidence, currently absent (TOR-OPEN-003).
- `AXIOM-TOOLCHAIN`: the language's deprecation, warning, and overload
  resolution behaviour. Source: the language and toolchain documentation. The
  design verifies repository-owned choices against the real toolchain, not the
  toolchain's internals.

### Methods per obligation

- Obligation `INV-EQUIV` / `TDD-OBL-001`.
  Method: characterization tests captured from the 2.1 tag plus property-based
  differential testing over generated inputs in `D`; parameterized boundary
  classes for empty, minimal, maximal, and malformed inputs.
  Rationale: equivalence is defined over an input space, which examples alone
  cannot establish.
  Domain: `D` and the documented rejection classes.
  Artefact: `<repo-relative characterization test path>` and
  `<repo-relative property test path>`.
  Evidence: baseline suite passes against the 2.1 revision; after the change it
  passes against the old entry point; a seeded mutation makes it fail for the
  intended reason.
  Non-vacuity: one witness per documented class, plus a negative-control
  mutation of the old path that the suite rejects.
- Obligation `INV-ADDITIVE` / `TDD-OBL-003`, `TDD-OBL-007`.
  Method: exported-symbol and documentation diff between releases, plus a
  resolution fixture that calls every existing signature.
  Rationale: source compatibility is a surface property not established by
  behavioural tests alone.
  Domain: the package's public export list at the 2.1 tag and at the change.
  Artefact: `<repo-relative export-diff script or test>`.
  Evidence: the diff shows only the new symbol; the fixture compiles and
  resolves each existing call to the same target; changing a signature makes
  the check fail.
  Non-vacuity: the check must be run against a deliberately altered signature
  in a scratch revision and reject it.
- Obligation `INV-WARN` / `TDD-OBL-004`.
  Method: build a representative consumer fixture with warnings treated as
  errors under the chosen marker policy.
  Rationale: a deprecation announcement must not itself break the commitment.
  Domain: the consumer's compiler or linter policy, represented by the fixture.
  Artefact: `<repo-relative consumer fixture>`.
  Evidence: the fixture builds before and after the announcement; a deliberate
  breaking warning makes it fail.
  Non-vacuity: the fixture must import and call the old entry point.
- Obligation `INV-REMOVAL-GATE` / `TDD-OBL-005`.
  Method: release checklist plus inspection of exported symbols in the release
  artefact, gated on the version and the commitment terms.
  Rationale: the obligation spans releases and is not a runtime property.
  Domain: each release the commitment covers.
  Artefact: `<repo-relative release check>` or a documented checklist step.
  Evidence: the check fails if the symbol is absent before the permitted major,
  demonstrated on a fixture release; it passes on a permitted release.
  Non-vacuity: exercise both the prohibited and permitted cases.
- Obligation `L-CONSUMER` / `TDD-OBL-006`.
  Method: consumer acceptance run against a representative workload.
  Rationale: only the consumer can show that documented-contract preservation
  is sufficient for it.
  Domain: the consumer's exercised calls.
  Artefact: consumer acceptance report, owned by the consumer operator.
  Evidence: the workload passes on the new entry point before removal.
  Non-vacuity: the workload must include at least one call that exercises the
  changed behaviour.
- Obligation `TDD-OBL-002`, `REQ-ADDITIVE` new behaviour.
  Method: parameterized and property tests over the contract supplied under
  TOR-OPEN-001.
  Rationale: the new contract is not yet known; once supplied, its input classes
  determine the method.
  Domain: the new contract's domain.
  Artefact: `<repo-relative new-contract test path>`.
  Evidence: a red test fails for the missing behaviour; the implementation
  makes it pass.
  Non-vacuity: each new behaviour class has a witness and at least one
  rejection case.

### Formal verification decision

No model checking or formal proof is planned at drafting time. The obligations
are contract equivalence over a documented input domain and API-surface
constraints; characterization plus generated differential tests give
proportionate rigour, and a formal proof would first require a formal model of
an unspecified language contract. This decision is recorded as `D5`. If
execution reconnaissance shows the function is stateful, concurrent, or
protocol-bearing, stop and revisit the obligation set and this decision before
`EP-M2`; state-machine model checking may then be warranted.

The concrete signatures are intake items (TOR-OPEN-004). The shape the plan
