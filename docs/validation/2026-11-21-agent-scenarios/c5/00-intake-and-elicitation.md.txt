# Change to a released 2.1 function – intake and elicitation note

Status: working note (phases 0–1 of the terms-of-reference workflow), not an
approved artefact.

Date: 2026-11-21.

Audience: maintainers and the release authority of the package that ships the
function, plus the author of the technical design.

## Input

> Change a function shipped in version 2.1 with an explicit compatibility
> commitment and a deployed external consumer. The current branch is ahead of
> the tag.

## Gating questions

The elicitation protocol asks one question per turn, in dependency order. The
first question is:

> TOR-OPEN-001: What is the intended change to the function – its new or
> changed contract relative to version 2.1?

The second is:

> TOR-OPEN-002: What is the exact text of the compatibility commitment, and
> which change classes, versions, notice periods, and removal conditions does
> it cover?

This authoring run has no interactive user to answer them. The elicitation
therefore exits with the questions recorded, as the protocol permits, rather
than manufacturing answers. The remaining questions, their gating effects, and
their resolution criteria are in the constraint record.

## Planned artefacts

1. A terms-of-reference constraint revision recording the commitment and the

2. A technical design that classifies the surface, chooses the compatibility or
   migration approach, and states the design-level verification obligations.
3. A draft ExecPlan for the implementation, held at `DRAFT` under the skill's
   approval gate.

No implementation is authorised by any of these documents.
