## 1. Status change and reason

Change the header status from `IN PROGRESS` to:

`BLOCKED (RFC alias demand conflicts with df12 pre-1.0 policy; explicit resolution required)`

The plan is executing a rename for which an inherited RFC demands an alias.
The surface is a published 0.8 source API, so df12 policy prohibits source-API
compatibility machinery, and the one named downstream consumer is not an
exception. Two courses are unavailable: adding the alias violates the
governing policy, and proceeding without it silently violates the RFC's
inherited commitment. The execplans contract requires an executing plan that
cannot follow the approved design to record the deviation in `Decision log`,
set `BLOCKED`, and await explicit acceptance. The technical-design contract
requires inherited conflicts to be exposed for explicit upstream resolution.

`BLOCKED` is correct rather than `IN PROGRESS` because implementation must
stop now. The conflict is not a mechanical difference. `DRAFT` is wrong: the
plan was approved and is executing. `COMPLETE` is impossible while the
deviation is unaccepted.

Immediate actions: stop before any further code change; do not publish or
release; do not add an alias; record the conflict; present the options to the
authority identified for `TOR-OPEN-002`. Work already in the tree is held
pending direction. This record does not order a revert.

## 2. Required edits to the existing plan

- The renamed surface is pre-1.0. The plan MUST NOT add an alias, deprecated
  entrypoint, facade, wrapper, dual implementation, compatibility adapter, or
  any other source-API compatibility machinery. A named external consumer does
  not create an exception.

  No milestone may keep the old name to make itself independently viable.

  authority.

  resolution creates a durable decision.

  authorization and require separate assessment.
