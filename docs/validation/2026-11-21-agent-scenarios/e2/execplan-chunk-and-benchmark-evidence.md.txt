## Purpose / big picture

The design claims that a chunked reader delivers a capture-only performance
gain. The evidence offered for that claim has two defects. First, increasing
the chunk size makes a test that is meant to exercise multiple chunks execute
only one iteration, yet the test still passes. Second, the benchmark measures
the echo path, in which captured bytes are written back to an output sink,
while the claim concerns the capture-only path, which performs no echo write.
A definition is useful here: a **chunk** is the block of bytes requested by one
iteration of the read-and-process loop, the **chunk size** is its maximum
length in bytes, and an **echo write** is a presentation write of captured
bytes.

After this work, a reader can observe two things. The multi-chunk test fails if
its configured chunk size collapses the fixture into a single iteration, and it
passes with an observed iteration count of at least two and a boundary-spanning
sentinel reproduced exactly. The benchmark reports a capture-only run and an
echo control as separate labelled measurements, so a capture-only claim is
supported only by a capture-only result. The production default chunk size and
echo behaviour remain unchanged unless a genuine defect requires a separately
approved change.

The work closes `GAP-001` and `GAP-002` from the design update at
`./tech-design-verification-update.md`, or it records that the claim cannot be
supported at the agreed scope.

## Risks

- Risk: The test passes again without exercising multiple chunks.
  Severity: high. Likelihood: medium. Mitigation: assert the observed iteration
  count and run the negative control that collapses it to one.
- Risk: The counter increments on underlying reads rather than loop iterations,
  so short reads inflate the count.
  Severity: medium. Likelihood: medium. Mitigation: instrument the loop entry,
  and cross-check the count against bytes processed and the boundary sentinel.
- Risk: Changing the fixture hides the boundary defect the test was meant to
  catch.
  Severity: high. Likelihood: medium. Mitigation: derive the sentinel from a
  real boundary and compare against an independent whole-buffer oracle.
- Risk: The benchmark still accidentally measures echo.
  Severity: high. Likelihood: medium. Mitigation: assert zero echo writes in the
  capture-only run and label the echo control separately.
- Risk: The threshold is quietly lowered or the workload changed after results.
  Severity: high. Likelihood: low. Mitigation: pre-register the threshold and
  forbid post-result changes in `Decision log`.
- Risk: The unsupported claim is repeated in downstream prose.
  Severity: medium. Likelihood: medium. Mitigation: mark it unsupported in the
  design and search for stale wording before completion.
- Risk: The repository cannot be located or the symbols do not exist as
  described.
  Severity: medium. Likelihood: medium. Mitigation: `EP-M0` reconnaissance; stop
  and escalate if the test or benchmark cannot be found.

## Verification plan

### Abstract model

Let `C` be the configured chunk size in bytes and `F` the fixture. Let
`n(F, C)` be the number of read-and-process iterations observed by the test.
Under full reads, `n = ceil(|F| / C)`; short reads can only increase `n`. The
obligation does not require an exact formula. It requires `n >= 2` when
`|F| > C`, together with exact reproduction of a sentinel whose bytes straddle
the boundary at offset `C`.

Let `P_capture` and `P_echo` be the two execution paths, and let `T(P)` be the
measured statistic for path `P`. The performance claim is a statement about
`T(P_capture)`. A result `T(P_echo)` is a different measurement and does not
discharge it.

The preconditions of `VO-001` are satisfiable by construction: choose a
fixture with `|F| > C` and place a sentinel so that it begins before offset `C`
and ends after it. The preconditions of `VO-002` are satisfiable only when the
harness can select the capture-only path and the echo path separately.

### Invariants and lemmas

- `INV-001`: For the approved `C` and `F`, the test observes `n >= 2`, and the
  processed output equals an independent whole-buffer oracle including the
  boundary sentinel. Linked to `REQ-001` and `VO-001`.
- `INV-002`: Any result offered for `CLM-002` is produced with
  `P = P_capture`; the echo run is a separately labelled control; and the
  capture-only run performs zero echo writes. Linked to `REQ-002` and
  `VO-002`.
- `INV-003`: A change to `C`, `F`, the path selector, the harness, the
  performance-relevant implementation, or the upstream design revision reopens
  `VO-001` and `VO-002`. Linked to `REQ-003` and `VO-003`.
- `L-001`: The test-only counter increments exactly once per loop iteration and
  is observable by the test. If it counts underlying reads instead, short
  reads can inflate `n`; the test must therefore instrument the loop entry and
  cross-check bytes processed.
- `L-002`: The oracle computes expected output from the whole fixture without
  using the chunked implementation under test, so agreement is not the
  implementation compared with itself.
- `L-003`: The capture-only selector excludes the echo write, and a zero-write
  assertion confirms exclusion rather than assuming it.
- `L-004`: The capture-only and echo runs hold the workload, input, environment,
  and protocol constant, so any difference is attributable to the selected
  path.

### Axioms (trusted, not verified here)

- `AXIOM-001`: The operating system and storage layer return the requested
  bytes or a short read reflecting end of file or pipe state. Source: the
  platform's documented read semantics, recorded in `EP-M0`. Boundary: the
  reader's chunk loop.
- `AXIOM-002`: The benchmark timer and process isolation have adequate
  resolution and stability for the observed effect. Repeats and dispersion
  evidence are required; the timer internals are not verified. Source: the
  harness's timing protocol, recorded in `EP-M0`. Boundary: the capture-only
  and echo comparisons.
- `AXIOM-003`: The test framework's documented strict expected-failure or
  panic-assertion mechanism reports an unexpected pass as a failure. Source: the
  framework's strict-mode contract, recorded in `EP-M0`. Boundary: the
  negative-control check in `EP-M1`.
- `AXIOM-004`: The existing echo behaviour is intended production behaviour and
  is not changed by this work. This is an assumption, not an approval to alter
  it. Source: the design's stated production behaviour, confirmed in `EP-M0`.
  Boundary: the echo control and all callers.

### Methods per obligation

`VO-001`:

- Obligation: `INV-001`, supported by `L-001` and `L-002`, and relying on
  `AXIOM-001` and `AXIOM-003`.
- Method: parameterized test over a small set of `(F, C)` pairs, with a
  test-only counter and an independent whole-buffer oracle.
- Rationale: finite, explicit cases cover the boundary and the one-iteration
  collapse without a new framework; a generated property over `C` is optional
  if the existing harness supports it.
- Domain: the approved `C`, one smaller `C`, and one `C >= |F|` for the negative
  control.
- Artefact: the located multi-chunk test plus the test-only counter.
- Evidence: red run fails on `n >= 2` with `n = 1`; green run passes with
  `n >= 2`; sentinel matches the oracle; negative control is rejected for the
  missing second iteration.
- Non-vacuity: the witness has `|F| > C`; the negative control has
  `C >= |F|` and must fail on the iteration assertion. An empty loop, a
  one-chunk fixture, or a permanently expected-failure marker is not evidence.

`VO-002`:

- Obligation: `INV-002`, supported by `L-003` and `L-004`, and relying on
  `AXIOM-002` and `AXIOM-004`.
- Method: two labelled benchmark runs with a pre-registered measurement record,
  repeated measurements, dispersion reporting, and a path assertion.
- Rationale: the question is empirical and protocol-shaped; separating the runs
  and asserting the selected path is proportionate. A formal model cannot prove
  which path the harness executed.
- Domain: the agreed workload and environment; capture-only and echo control.
- Artefact: the existing benchmark harness, with labels and a zero-echo
  assertion.
- Evidence: capture-only run transfers non-zero bytes and performs zero echo
  writes; echo control performs echo writes; capture-only result meets the
  pre-registered threshold with uncertainty; claim updated at measured scope.
- Non-vacuity: a benchmark that skips the path, processes zero bytes, or differs
  only in unrelated startup work is rejected. A temporary mutation in the
  capture path must change the measured result for the intended reason.

`VO-003`:

- Obligation: `INV-003`.
- Method: recorded trigger list checked at each milestone and before claim
  acceptance.
- Evidence: each trigger is followed by a re-run or an explicit unverified
  state in `Progress`.
- Non-vacuity: a deliberately collapsed `C` reopens `VO-001`; a relabelled
  benchmark path reopens `VO-002`.

### Formal verification decision

No model checking or formal proof is needed. The obligations concern whether a
test exercised a path and whether a benchmark measured the claimed path. Those
are empirical and protocol questions. The strongest useful methods are the
iteration-count witness with a negative control and a path-asserted benchmark
with an independent control. This decision is recorded as `D6`.
