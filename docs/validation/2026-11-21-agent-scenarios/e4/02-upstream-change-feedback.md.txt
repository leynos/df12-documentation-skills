### 2.4 Verification obligations at design level

The design states the discharge criteria; the ExecPlan holds the concrete
commands and artefact paths. Proposed obligations:

- `VO-ERRMAP`: every permitted outcome of `<SYM>@B` maps to exactly one
  documented repository outcome, with no panic, unwrap, silent discard, or
  unreachable branch. Method: exhaustive type checking or parameterized
  contract tests over the finite outcome classes.
- `VO-FAIL-B`: conditional on a permitted failure outcome. Method: a reachable
  witness at the real boundary or a faithful contract-level boundary, with a
  negative control that the check rejects when handling is wrong.
- `VO-NO-DEAD`: no production branch or test targets a state revision B cannot
  produce. Method: compiler or linter unreachable-pattern and dead-code
  reporting, plus review.
- `VO-FAIL`, revision A: withdrawn, not discharged. The design must not count a
  passing, ignored, filtered, or mock-forced test as evidence.

Non-vacuity is local to each obligation: show a satisfying witness, exercise
each permitted class, and include a negative control rejected for the intended
reason. An unreachable assertion is a verification failure, not a green result.
A mock that injects the removed failure would assert the disputed guarantee and
cannot discharge `VO-FAIL-B`.

### 2.5 Compatibility assessment

The dependency contract change is external to the repository. Update the
repository's callers and the interface together. Do not add aliases, facade
types, deprecated entrypoints, dual implementations, or temporary wrappers whose
purpose is to preserve the obsolete source interface of a private API, a
test-only API, a pre-1.0 API, or an unreleased change ahead of the latest formal
release tag. A necessary domain or external-protocol adapter is judged by its
purpose, not its name; preserving the obsolete interface is the prohibited
purpose.

Two surfaces need separate checks:

1. Repository API exposure. If `<FAILURE>` is part of a released 1.0+
   repository API, record the actual external consumer, deployed state, and
   commitment. No known consumer normally means no compatibility machinery,
   subject to explicit project policy. Do not decide this from the dependency
   change alone.
2. Persisted and wire formats. If `<FAILURE>` appears in stored records or in a
   protocol with a deployed peer, that is a separate migration question. The
   existence of deployed data does not justify an unrelated source-API shim.

If an inherited upstream document demands compatibility for a prohibited
surface, record the contradiction for explicit resolution. Do not silently add
a wrapper to satisfy it.
