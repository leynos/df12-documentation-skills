## 3. Reachability classification and required proof

Define `<F>` precisely: the branch, test, and acceptance claim that exist only
if `<SYM>` can produce `<FAILURE>` (or can be reached through the triggering
precondition). The event asserts that `<F>` is unreachable. Four classifications
have different consequences, and the plan must record which one applies before
retiring anything.

1. R1, type-impossible. Revision B's signature or type cannot carry
   `<FAILURE>`, and no constructor for it is reachable. Proof: the exact
   revision-B type, an exhaustive constructor or variant inventory, and a
   compile-time or compile-fail probe. Consequence: the old branch cannot
   compile or is statically unreachable; the old test cannot execute; both are
   removed together with every affected caller.
2. R2, contract-impossible. The type can represent `<FAILURE>`, but revision
   B's documented guarantee excludes producing it. Proof: the exact revision-B
   contract text, the absence of any provider path that contradicts it, and a
   repository-wide search showing that no repository-owned constructor,
   deserializer, error conversion, or test fixture produces `<FAILURE>` from
   external or persisted input. Consequence: unreachability rests on an external
   axiom, not on the type system. A retained branch is unverified defensive
   code, and a test that injects the variant through a fake would assert the
   disputed guarantee. Such a test is not acceptance evidence.
3. R3, precondition-impossible. Revision B validates or rejects the triggering
   input before `<SYM>` is called, so no permitted caller path reaches `<F>`.
   Proof: revision B's validation boundary, every caller, a search for bypasses,
   and confirmation that no other repository path constructs the trigger.
   Consequence: remove the call-site branch and verify that no other caller,
   feature combination, or configuration path reintroduces the trigger.
4. R4, unverified. The event asserts unreachability but no proof has been
   produced. Consequence: delete nothing. Keep the plan BLOCKED and run the
   probe.

The current classification is R4 with an asserted outcome. The stop is
mandatory regardless: revision-A acceptance evidence is stale, and the planned
failure path may no longer be capable of discharging `<VO-FAIL>`.

## 5. Disposition of the unreachable failure path

1. Withdraw, do not pass. An unreachable failure test is not evidence of
   success; it is evidence that the verification plan no longer matches the
   contract. Do not record it as passing, and do not convert it into an ignored
   test, an expected failure, a filtered property, or an empty loop.
2. Do not synthesize the failure. A mock, adapter, or shim that injects
   `<FAILURE>` tests a contract that revision B no longer provides. It would
   assert the disputed guarantee and would not prove that repository behaviour
   is correct against the real interface.
3. Do not preserve unreachable code. Do not add `allow(unreachable_patterns)`,
   an unreachable guard, a compatibility alias, a facade, a dual
   implementation, or a temporary wrapper to keep the old branch compiling.
   Update the callers and the interface together.
4. Re-source only where a real boundary remains. If the user-visible need
   behind `<F>` is independent of revision A's failure surface, move the
   requirement to a boundary where that failure remains reachable. Do not
   silently drop a user-visible guarantee with the dependency mechanism.
5. Replace the coverage. Record the total outcome set of `<SYM>` at revision B,
   map every permitted outcome to a repository outcome, and verify the mapping.
   If revision B is infallible, record that conclusion and justify why no
   non-trivial failure invariant remains. Verify that the error handling was
   removed atomically and that no caller now panics, unwraps, or discards a
   result silently.
6. Protect the replacement from vacuity. Exhibit a witness for each permitted
   outcome class, show that the replacement check can fail, and include a
   negative control, such as a deliberately seeded mis-mapping that the check
   rejects for the intended reason. Revert the seeded fault and remove any
   generated regression artefacts afterwards.
7. Preserve history. Record `<VO-FAIL>` and `<test-old>` as withdrawn with the
   reason, revision, date, and approving decision. Do not erase the
   revision-A result; label it historical.

## 6. Options and trade-offs

1. Option A: adopt revision B and retire `<F>`. The design records that the
   failure mode no longer exists, `<VO-FAIL>` is withdrawn, and `<VO-ERRMAP>`
   replaces it. This is the smallest coherent change when the requirement was
   derived solely from revision A's contract. It requires explicit acceptance
   to retire an approved acceptance item.
2. Option B: adopt revision B and re-source the requirement. If the need behind
   `<F>` traces to an upstream goal, constraint, or success criterion rather
   than to revision A's error surface, move the requirement to a reachable
   boundary and verify it there. This requires a design revision and new
   acceptance evidence, not a mock of the old contract.
3. Option C: pin revision A. This is permissible only if revision A remains
   supported, secure, and available, and if a project commitment permits the
   pin. It preserves the old failure path but records a support and security
   expiry risk. It does not avoid the need to update evidence citations.
4. Option D: preserve the test by forcing the old failure through a fake or
   shim. Rejected. It is compatibility theatre, it asserts a guarantee the
   dependency no longer provides, and its passing result would be vacuous.

Decision rule: ask whether `<F>` discharges an upstream requirement that is
independent of revision A's failure surface. If it does not, choose Option A.
If it does, choose Option B. Choose Option C only with evidence that revision A
remains supportable and with an explicit expiry owner. Never choose Option D.

No option is selected here. Selection belongs to the decision authority named
in §7.
