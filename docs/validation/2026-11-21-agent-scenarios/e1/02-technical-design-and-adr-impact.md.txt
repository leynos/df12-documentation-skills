## Baseline, target, and gap

Baseline: the observed implementation under the probe leaves workers alive
after the supervisor exits. This is evidence for the exercised path only. The
source revision, worker-spawn paths, cancellation implementation, and process
lifetime mechanism were not inspected, so the mechanism of the mismatch is
unknown.

Target: after cancellation completes, no supervisor-started worker in the
defined worker set is alive. Workers that were not cancelled continue running.

Gap record `GAP-WORKER-REAP-001`:

- Upstream requirement: `PROV-TOR-SUCCESS-001` via `PROV-ADR-001`.
- Baseline evidence: `EVID-PROBE-001`.
- Target state: zero surviving workers within deadline D.
- Missing capability or mismatch: either the implementation omits a termination
  step that the design requires, or the design's lifetime mechanism does not
  cover the worker set. Undetermined until `EP-M0`.
- Disposition: blocked, pending acceptance of decision D1 in the ExecPlan. It
  is not "already satisfied", "out of scope", or a roadmap task by default.
- Resolution owner: unknown.
- Unblock condition: explicit acceptance of either a defect-fix disposition
  with the existing architecture retained, or a design and ADR change naming
  the mechanism and scope.
- Verification obligation: the `VO-*` obligations below and the ExecPlan's
  `Verification plan`.

## Candidate design responses (proposed, none selected)

### A. Explicit worker registry and ordered shutdown

Mechanism: the supervisor records every worker it starts. On cancellation it
signals the workers, waits for a grace period, forcibly terminates survivors at
the deadline, and then exits.

Strengths: portable, explicit, directly observable, and independent of implicit
process ancestry.

Limits: covers only registered processes and only while the supervisor runs. A
supervisor crash or forced termination bypasses the mechanism unless the
promise excludes that case. Every worker-spawn path must register.

Verification: a coverage test for each spawn path, the integration liveness
test, and a mutation that removes the wait or termination step must fail.

ADR impact: compatible with the promise for cancellation if the ADR names the
shutdown discipline and deadline. It may need no architectural change if the
existing design already intends this discipline.

### B. Process group or session signal

Mechanism: workers remain in a supervisor-owned process group; cancellation
signals the group.

Strengths: covers descendants that remain in the group, with little code.

Limits: workers that detach, for example by calling `setsid`, escape. A shared
group can signal unrelated processes. Group membership must be guaranteed. A
supervisor crash is not covered.

Verification: assert group membership at spawn, test a detaching worker if it
is in the worker set, and test preservation of unrelated processes.

ADR impact: the ADR must record group ownership and the escape cases.

### C. Operating-system-enforced lifetime

Mechanism: for example Linux parent-death signal (`PR_SET_PDEATHSIG`), a cgroup
kill, or a Windows job object with kill-on-close, chosen per supported platform.

Strengths: the platform enforces worker death even when the supervisor is
terminated abruptly, subject to the mechanism's documented semantics.

Limits: platform-specific, may require worker cooperation or privileged
configuration, and behaves differently under containers and service managers.
It introduces platform code paths and a platform test matrix.

Verification: per-platform integration tests, including forced supervisor
termination if that case is in scope, with unsupported platforms recorded as
residual gaps.

ADR impact: substantial. The ADR decision changes from an implicit assumption
to an explicit enforced mechanism.

### D. Narrow the promise

Mechanism: none. This is a requirement and ADR change, not a design response.

Effect: the ToR and ADR state that cancellation does not guarantee worker
termination, or guarantees it only under narrower conditions.

Precondition: explicit acceptance by the decision authority. Never adopt it
merely because the probe observed survivors.

Verification: the revised promise still needs a measurable acceptance
criterion.

No option is selected. The choice depends on the documented cancellation model,
the supported platforms, and whether the existing design's mechanism is sound
but unimplemented. `EP-M0` must establish the cause before the owner chooses.

## Verification obligations

- `VO-TERMINATION`: A real-process integration test starts a supervisor with
  workers, cancels it through the documented operation, and observes that all
  worker processes are gone within D after supervisor exit. Method:
  parameterized integration test. Rationale: the disputed property is real
  operating-system process liveness, which a unit mock cannot establish.
- `VO-PRESERVATION`: Workers remain alive before cancellation, so the test
  cannot pass by killing workers unconditionally.
- `VO-COVERAGE`: Every supervisor-owned spawn path registers or protects its
  workers. A worker started through a bypass path is detected.
- `VO-RACE`: Cancellation concurrent with worker start or exit neither leaves a
  survivor nor hangs. Method: scripted interleavings, or a state-machine model
  if the receiving repository supports one.
- `VO-SCOPE`: If descendants or abrupt supervisor termination are in scope,
  test those cases. Otherwise record them as residual gaps rather than silent
  exclusions.

Non-vacuity arguments and negative controls are specified in the ExecPlan's
`Verification plan`. No verification has been performed; these are planned
obligations, not passing results.

## Axioms and dependencies

- `AXIOM-OS-PARENT-EXIT`: An operating system does not terminate a parent's
  children merely because the parent exits. Without an explicit mechanism,
  children survive and are reparented. Source: platform process semantics; on
  Linux the `prctl(2)` parent-death-signal documentation describes the relevant
  mechanism. The supported platform set is open (`TOR-OPEN-PLATFORM-04`).
- `AXIOM-LIVENESS-OBSERVATION`: The chosen liveness check reports process
  existence reliably for the test's lifetime. PID reuse is controlled by
  matching process identity, not by PID alone.
- Dependency: none identified. The implementation must not add a dependency
  without authorization.
