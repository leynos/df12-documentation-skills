## Purpose / big picture

An operator runs a supervisor: a process that starts, monitors, and stops
worker processes for one supervised unit of work. A worker is a process that
the supervisor starts to perform that work. Cancellation is the documented
operation by which the operator asks a running supervisor to stop. The terms of
reference (ToR) and the architecture decision record (ADR) promise that
cancelling a supervisor stops its workers.

The supplied integration probe contradicts that promise. The operator cancelled
the supervisor, the supervisor exited, and workers remained alive. A reader
should treat the supervisor's exit code as irrelevant here: the disputed claim
is about the liveness of the worker processes themselves.

After the change, repeating the same cancellation and observing the worker
processes, not only the supervisor, shows that every supervisor-started worker
has terminated within the agreed deadline. Workers continue to run while the
supervisor runs, and cancellation keeps its documented observable contract. No
behaviour beyond the accepted disposition of decision D1 is intended to change.

The outstanding decision is whether the probe exposes a defect within the
existing architecture or falsifies the design and ADR mechanism. Until that
decision is accepted, this plan cannot be approved for implementation.

## Risks

- Risk: the probe did not use the documented cancellation operation, so it does
  not exercise the promise.
  Severity: high. Likelihood: medium.
  Mitigation: confirm the probe's preconditions from its transcript and
  reproduce it under `EP-M0` before treating the promise as falsified.
- Risk: workers detach or are reparented when the supervisor exits, so an
  implicit parent-child lifetime assumption fails.
  Severity: high. Likelihood: high.
  Mitigation: establish the actual process parentage, group membership, and
  signal handling in `EP-M0`; choose a mechanism that covers the defined worker
  set.
- Risk: a test passes because the worker already exited for an unrelated
  reason, not because cancellation worked.
  Severity: high. Likelihood: medium.
  Mitigation: assert the worker's identity is alive immediately before
  cancellation, and match process start time or cgroup membership rather than
  PID alone.
- Risk: timing assumptions make the test flaky.
  Severity: medium. Likelihood: high.
  Mitigation: poll until deadline D with bounded intervals, record the observed
  shutdown latency, and avoid unbounded sleeps.
- Risk: terminating a process group kills unrelated processes.
  Severity: high. Likelihood: low to medium, depending on mechanism.
  Mitigation: test preservation of a non-worker process and prefer an explicit
  worker set where group membership is not guaranteed.
- Risk: the repository is not the one implied by these records, so paths,
  symbols, and gates differ.
  Severity: medium. Likelihood: medium.
  Mitigation: resolve the receiving repository and its gate sequence in
  `EP-M0`; do not implement against placeholder names.
- Risk: an accepted fix misses a worker-spawn path.
  Severity: medium. Likelihood: medium.
  Mitigation: enumerate spawn paths, add one coverage test per path, and keep a
  mutation that bypasses the mechanism as a negative control.
- Risk: a scope change is smuggled in as a design detail.
  Severity: high. Likelihood: low.
  Mitigation: D1 requires explicit acceptance and an upstream revision for any
  change to the promise itself.

## Verification plan

### Abstract model

The model is intentionally small. It captures the promise's observable claim
without prescribing a mechanism.

```plaintext
W        = the set of worker processes started by one supervisor and within
           the agreed scope
D        = the agreed shutdown deadline (definition open; see
           TOR-OPEN-DEADLINE-02)
alive(p) = process p exists and matches the recorded process identity

Running(W) --cancellation--> Cancelling(W) --supervisor exits-->
SupervisorExited

Required: for every p in W, not alive(p) at SupervisorExited + D.
Preserved: with no cancellation request, each p remains alive.
```

Preconditions: the operator used the documented cancellation operation; each
`p` was started by the supervisor through a covered path; D is agreed; the
liveness observer is independent of the supervisor's exit status.

Malformed inputs and violated preconditions: a different cancellation
operation is outside the promise and the observation must say so rather than
claim a pass or a failure. A worker not started by the supervisor is excluded
from `W` and recorded. An undefined D makes the property untestable, so the
missing deadline gates acceptance rather than being invented.

### Invariants and lemmas

- `INV-WORKER-TERMINATION`: For every `p` in `W`, after cancellation completes
  and the supervisor has exited, `p` is not alive at `SupervisorExited + D`.
  Linked to `PROV-TDD-REQ-001`.
- `INV-PRESERVATION`: With no cancellation request and no independent worker
  failure, every `p` in `W` remains alive while the supervisor runs. This
  prevents a fix from passing the termination test by killing workers
  unconditionally.
- `INV-NO-ORPHAN-RACE`: Cancellation concurrent with worker start, worker exit,
  or repeated cancellation leaves no survivor and does not hang.
- `INV-IDEMPOTENT-CANCEL`: A second cancellation request neither fails
  spuriously nor prevents the first from completing; the post-condition still
  holds.
- `L-PROBE-CORRESPONDENCE`: Reproducing the supplied probe on the recorded
  baseline revision produces the survivor observation for the intended reason,
  so the red evidence is not vacuous.
- `L-REGISTRY-COVERAGE`: Every supervisor-owned worker-spawn path adds its
  worker to the set protected by the accepted mechanism. If this lemma fails,
  `INV-WORKER-TERMINATION` cannot be claimed for the full worker set.
- `L-LIVENESS-IDENTITY`: The liveness observer distinguishes the fixture worker
  from an unrelated process that reuses its PID.

### Axioms (trusted, not verified here)

- `AXIOM-OS-PARENT-EXIT`: An operating system does not terminate a parent's
  children merely because the parent exits. Children survive and are reparented
  unless an explicit mechanism enforces termination. Source: platform process
  semantics; on Linux, the `prctl(2)` parent-death-signal documentation
  describes the relevant mechanism. The platform set is open.
- `AXIOM-LIVENESS-OBSERVATION`: The chosen liveness check reports process
  existence reliably for the duration of a test when process identity is
  matched, not merely the PID.
- `AXIOM-REAL-PROCESS-TEST`: The integration fixture executes real supervisor
  and worker processes, not a mock that asserts the disputed guarantee.

### Methods per obligation

- Obligation: `INV-WORKER-TERMINATION`.
  Method: parameterized integration test over worker counts, including one and
  more than one worker, and over the worker-set cases accepted in D1.
  Rationale: process death is an operating-system observation; only a
  real-process test exercises it.
  Domain: the documented cancellation operation; workers started through each
  covered spawn path; descendants only if the scope decision includes them.
  Artefact: a focused integration test, exact path to be recorded before
  approval.
  Evidence: red on the baseline revision with the survivor's identity; green
  after the accepted fix; the worker is absent at `SupervisorExited + D`.
  Non-vacuity: the test asserts the worker identity is alive immediately before
  cancellation, and a seeded fault that skips the termination step or the wait
  must fail for the intended reason.
- Obligation: `INV-PRESERVATION`.
  Method: parameterized test observing worker liveness before cancellation.
  Rationale: a test that never sees a live worker, or a fix that kills workers
  at startup, would otherwise pass vacuously.
  Domain: one worker and multiple workers, sampled at intervals while the
  supervisor runs.
  Artefact: the same integration suite.
  Evidence: workers alive before cancellation on both baseline and fixed
  revisions.
  Non-vacuity: the liveness observer must report `alive` for the fixture's
  recorded identity; a mutation that terminates workers at spawn must fail.
- Obligation: `INV-NO-ORPHAN-RACE` and `INV-IDEMPOTENT-CANCEL`.
  Method: scripted interleavings, with barriers or synchronisation hooks; use a
  state-machine model check only if the receiving repository already supports
  one.
  Rationale: the properties are temporal, and a single sequential test does not
  cover them.
  Domain: cancel before start completes; cancel during worker exit; worker
  ignores the graceful signal; double cancellation; worker exits before the
  signal arrives.
  Artefact: deterministic interleaving tests, exact path to be recorded.
  Evidence: no survivor, no hang, and a completed shutdown for every scripted
  interleaving.
  Non-vacuity: each scripted case must reach its intended state, demonstrated
  by an assertion or trace; a case whose barrier never fires is a failure, not
  a pass.
- Obligation: `L-PROBE-CORRESPONDENCE`.
  Method: reproduction of the supplied probe under the recorded revision.
  Rationale: the red test must fail for the reason the input reports, not for
  an unrelated environmental cause.
  Domain: the probe's documented command, platform, cancellation path, and
  worker count.
  Artefact: a transcript appended to `Artefacts and notes`, with a scratch
  reproduction script if needed; the script is discarded or promoted
  deliberately.
  Evidence: the observed survivor identity and the supervisor exit status.
  Non-vacuity: the worker must be observed alive before cancellation; a probe
  that cancels nothing is rejected.
- Obligation: `L-REGISTRY-COVERAGE`.
  Method: static inspection of every spawn path plus one integration case per
  path.
  Rationale: a termination mechanism covers only the processes it knows about.
  Domain: every caller of the worker-spawn interface.
  Artefact: coverage tests and an inspection note naming each path and caller.
  Evidence: each spawn path produces a worker that is terminated by
  cancellation.
  Non-vacuity: a mutation that starts a worker through a bypass path must fail
  coverage detection.

### Formal verification decision

No formal proof or model check is planned at the design level. The central
claim is about real process liveness across an operating-system boundary.
Verifying a model would demonstrate properties of the model, not of the
platform's process semantics. Real-process integration tests with an
independent liveness observer provide proportionate rigour, and a state-machine
model check is reserved for cancellation interleavings if the receiving
repository already has the tooling. Residual gaps: unexercised platforms,
container runtimes, and service managers must be named rather than claimed.
This decision is recorded in D4.
