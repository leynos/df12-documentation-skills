## Purpose / big picture

The application stores records through a private API and writes them in a
representation that a shipped binary already used. We are changing both the
private API and the representation. The private API has no callers outside the
application, so it changes all at once. The bytes on disk cannot be recompiled,
so the new code must still read them.

Before the change, a record read from an existing store passes through the old
record type, and new records are written in the old representation. After the
change:

- reading a record the deployed binary wrote yields the new in-memory record
  model, with every old field accounted for;
- reading a record the new binary wrote yields the same model;
- writing always produces a self-describing version 2 record;
- a record the code cannot interpret stops the read with an error naming the
  problem, instead of silently dropping fields.

Terms used below:

- **Private API**: application-internal source interface. No consumer outside
  the application calls it.
- **Version 1 (v1) record**: bytes written by the already-deployed binary.
- **Version 2 (v2) record**: the target representation defined by
  `storage-record-v2.schema.json`.
- **Decoder**: a private function turning stored bytes into the record model.
  It is not a compatibility interface.
- **Upgrade-on-write**: a record changes representation only when the
  application rewrites it.

There is no source-API compatibility goal. The only compatibility obligation is
that existing records remain readable. This plan closes that obligation with a
decoder, not with a shim.

## Constraints

Hard invariants. Violation requires escalation, not a workaround.

- The private API changes atomically. The old record type, its functions, and
  its module path are deleted, and every caller is updated in the same
  milestone. No `Deprecated` marker, alias, facade, wrapper, adapter, dual
  implementation, or feature-flag branch may preserve the old interface.
- Exactly one in-memory record model exists. No v1-shaped type may be exported
  from the library or leak out of the codec.
- The v1 decoder lives in the codec, is not public API, and produces the new
  model. It may be removed once no v1 records remain.
- Reading a record never writes. No eager rewrite, compaction, or repair runs
  as part of a read.
- New writes are always v2 and always carry `schema_version: 2`.
- An unsupported version is an error. It never falls back to v1 decoding.
- Public, wire, network, CLI, and configuration surfaces do not change in this
  slice. No new runtime dependency and no new public interface are authorized.
- `storage-record-v2.schema.json` is normative for v2 definitions. Changing it
  changes this plan and the design.
- Do not weaken, skip, or delete an existing test to make the change pass.
- Existing historical planning and design documents stay untouched.
- No implementation, including the read-only reconnaissance milestone, begins
  until the user approves this plan.

## Risks

- Risk: the v1 field layout has a field named `schema_version`, breaking the
  classification rule. Severity: medium. Likelihood: low. Mitigation:
  `TDD-GAP-002` confirms the layout before coding; the rule is revised in the
  design if a collision exists.
- Risk: real v1 fixtures cannot be obtained, leaving the strongest obligation
  unverified. Severity: high. Likelihood: medium. Mitigation: capture samples
  from a non-production copy early; if impossible, keep `TDD-VER-002` planned
  and do not claim deployed readability.
- Risk: the rollback requirement emerges after version 2 writes begin.
  Severity: high. Likelihood: medium. Mitigation: resolve `TDD-OPEN-001` before
  `EP-M2`; if rollback is required, stop and redesign the migration policy.
- Risk: an old binary still writes v1 records concurrently with the new one.
  Severity: high. Likelihood: unknown. Mitigation: resolve `TDD-GAP-004` before
  `EP-M2`; mixed-version writers are outside the verified boundary.
- Risk: the append primitive is not atomic, so a crash leaves a partial record.
  Severity: medium. Likelihood: unknown. Mitigation: confirm the primitive in
  `EP-M0`; expand `TDD-VER-006` to a real durability test if it is absent.

## Decision log

- D1. Decision: no source-API compatibility for the private API.
  Rationale: the API has no external consumer and every caller changes in the
  same milestone. An alias or wrapper would answer no "compatible with whom or
  what?" and would keep the old abstraction alive.
  Date/Author: 2026-11-19, authoring agent.
- D2. Decision: classify by the presence of `schema_version`, and treat any
  value other than 2 as unsupported.
  Rationale: the discriminator travels with the record, so no side metadata is
  needed; refusing fallback prevents a future version from being read as v1.
  Rejected: a separate sidecar index, which can desynchronise from the records.
  Date/Author: 2026-11-19, authoring agent.
- D3. Decision: upgrade-on-write.
  Rationale: smallest obligation that satisfies the goal; no bulk mutation and
  no downtime. Rejected: eager rewrite, which turns reads into writes and
  needs backup and interruption handling. Rejected: keep writing v1, which
  leaves the representation unreshaped.
  Date/Author: 2026-11-19, authoring agent.
- D4. Decision: fail closed on a truncated tail; repair only by a documented
  operator procedure after a backup.
  Rationale: automatic repair risks deleting a record that a complete rewrite
  could have recovered; an offset-bearing error is actionable.
  Date/Author: 2026-11-19, authoring agent.
- D5. Decision: provisional tolerances pending `EP-M0`.
  Rationale: no baseline survey was possible; presenting invented precision as
  a measured estimate would be false. The numbers are marked provisional and
  require re-approval.
  Date/Author: 2026-11-19, authoring agent.

## Verification plan

### Abstract model

A stored record is a byte string. Classification maps each string to exactly
one of: `V1`, `V2`, `Malformed`, or `Unsupported(n)`. Decoding maps `V1` and
`V2` to `Record` or a typed error. Encoding maps `Record` to a `V2` byte
string. The model domain is the set of v1 values observable in captured
fixtures plus generated v2 model values.

Preconditions: a record is a single stored unit; the store hands the codec the
complete bytes of one record, or the remaining bytes when the record is
truncated. Violations are handled by the failure table in the design §7, not by
undefined behaviour.

### Invariants and lemmas

- `INV-classify` (`TDD-VER-001`): classification is total and single-valued.
- `INV-v1-decode` (`TDD-VER-002`): every captured v1 record decodes to the
  model without error.
- `INV-field-coverage` (`TDD-VER-003`): every field of every captured v1
  record has exactly one mapping class.
- `INV-roundtrip` (`TDD-VER-004`): `decode_v2(encode_v2(r))` equals `r` for
  every model value `r`.
- `INV-atomic-api` (`TDD-VER-005`): no old-API symbol remains and the build
  succeeds.
- `INV-fail-closed` (`TDD-VER-006`): a truncated tail is reported, never
  decoded, and complete records before it still decode.
- `L-fresh-writes` (`TDD-REQ-003`): `INV-roundtrip` plus the encoder's fixed
  `schema_version` implies every fresh write is classified `V2` without side
  metadata.

### Axioms (trusted, not verified here)

- `AXIOM-json`: the JSON parser implements RFC 8259 for the used subset.
- `AXIOM-append`: the store's append primitive is atomic per record. Confirm at
  `EP-M0`; if false, it becomes a repository obligation and this plan changes.
- `AXIOM-fixtures`: captured fixtures represent the deployed binary's output.
  Evidence is the capture procedure and provenance; if unavailable,
  `TDD-VER-002` remains planned.

### Methods per obligation

- Obligation: `INV-classify`.
  Method: parameterized tests over the four classes plus a property test over
  generated objects with and without `schema_version`.
  Rationale: the input space is a small tagged partition; enumeration covers
  it directly.
  Domain: absent version; version 1; version 2; version 3; non-object JSON;
  invalid JSON; empty bytes.
  Artefact: `tests/codec/classification` in the repository's test layout.
  Evidence: red before the classifier exists (`missing function` or a failing
  assertion); green with one case per class.
  Non-vacuity: each class has a named witness; the negative control makes the
  classifier treat every object as V2 and must fail on the v1 witness.
- Obligation: `INV-v1-decode` and `INV-field-coverage`.
  Method: golden-fixture tests over captured records, with a test-data mapping
  table.
  Rationale: fixtures are the only evidence about what the shipped binary
  actually wrote; a hand-written example proves only what the author believed.
  Domain: every captured fixture, plus absent optionals, empty payload,
  non-ASCII text, and boundary integers.
  Artefact: `tests/fixtures/records-v1/` plus `tests/codec/v1_mapping`.
  Evidence: red on the first fixture before the decoder exists; green with a
  recorded fixture count and per-field assertions.
  Non-vacuity: the mapping coverage test fails when a fixture field has no
  mapping row (seeded by adding an unmapped field); a fixture set of one
  trivial record is rejected as insufficient.
- Obligation: `INV-roundtrip` and `L-fresh-writes`.
  Method: property test with an independent schema-validation oracle.
  Rationale: the invariant spans generated values and optional fields.
  Domain: generated model values covering every optional field and boundary
  numbers.
  Artefact: `tests/codec/roundtrip`.
  Evidence: red with an encoder stub; green with classification evidence
  showing every optional field was generated.
  Non-vacuity: comparing two outputs of the same encoder is not an oracle; the
  test validates the encoded bytes against the schema and compares decoded
  model values.
- Obligation: `INV-atomic-api`.
  Method: compile plus a symbol search that must match at least once on the
  pre-change baseline.
  Rationale: a compile alone proves only that the new code compiles; the
  absence check proves the old surface is gone.
  Domain: the old type and function names recorded in `EP-M0`.
  Artefact: `tests/api/old_symbol_absent` or the repository's equivalent static
  check.
  Evidence: pre-change match count recorded; post-change count zero; build
  passes.
  Non-vacuity: the search pattern is run against the pre-change revision and
  recorded as matching, so the zero result is meaningful.
- Obligation: `INV-fail-closed`.
  Method: fixture with the final bytes removed, plus a failure-injection test
  for a failed append.
  Rationale: the only realistic corruption is an interrupted final write.
  Domain: zero bytes removed, one byte, half the record, whole record.
  Artefact: `tests/store/truncated_tail`.
  Evidence: red before truncation handling; green with a typed error and the
  preceding complete records readable.
  Non-vacuity: the fixture actually lacks bytes; a test that writes only
  complete records exercises nothing relevant.

No proof or model check is planned. Each obligation is a total function over a
small tagged space or an idempotence property; parameterized tests, fixtures,
and property tests are proportionate. Stronger methods would still leave the
filesystem axiom unproved.

### Formal verification decision

Formal verification is not used. Recorded in D2/D3 terms: the risk is data
interpretation, not concurrency or arithmetic; fixtures and generated values

## Idempotence and recovery

Re-running the decoder and encoder tests is safe; they use fixtures and
generated values, not live stores. Running the application against a real store
is not part of any test in this plan; if a manual check is needed, copy the
store first. A failed append leaves at most a trailing partial record; recovery
is the documented truncation of that final record after a backup, never an
automatic repair. A partial implementation can be reverted to the prior
milestone; after `EP-M2` writes begin, restoring v1-only behaviour requires the
pre-change backup.

## Interfaces and dependencies

Language-neutral port contract. Specialise the syntax to the repository's
language at `EP-M0` without changing the semantics.

```plaintext
classify(bytes) -> V1 | V2 | Malformed | UnsupportedVersion(n)
decode_v1(V1) -> Record or DecodeError
decode_v2(V2) -> Record or DecodeError
encode_v2(Record) -> bytes        # always schema_version 2
```

Ownership: the codec owns classification and both decoders; the store owns
record boundaries and append; callers own no knowledge of stored formats. The
record model is defined once and imported by both decoders.

Error contract: every failure is a typed value naming the class and the record
offset; errors never carry a partially decoded record. Do not add a public
`V1Record` type or a public decode entrypoint.

Dependencies: none. Do not add a JSON library, migration framework, or schema
tool unless `Constraints` is amended and approved.
