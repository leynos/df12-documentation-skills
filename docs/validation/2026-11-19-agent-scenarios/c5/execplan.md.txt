## Purpose / big picture

A function shipped in version 2.1. An external consumer runs it in a deployed
environment, and the project promised that consumer compatibility. The working
branch is ahead of the release tag. The request is to change the function.

Today the function's 2.1 contract is published and in use. After the work, a
maintainer can deliver the requested change while the committed consumer either
keeps working unchanged (additive evolution) or moves through a planned,
evidenced migration (deliberate migration). The observable difference is
concrete: the frozen 2.1 consumer fixture compiles and produces its recorded
outcomes against the supported release; the new behaviour is available to its
intended callers; and any retired path is removed only after migration evidence.

The branch being ahead of the tag is not a reason to skip compatibility. The
2.1 contract is released; only the edit is unreleased. `TDD-DEC-001` records
that classification and its consequence.

This plan delivers one of two coherent outcomes. The evidence recorded in
`EP-M0` selects which:

- Additive evolution, where baseline call shapes and behaviour are untouched;
  or
- Deliberate migration, where the baseline is deprecated, the named consumer
  migrates, and the baseline is removed at an approved release.

The two are alternatives, not sequential milestones. `EP-M3` is removal work
only on the migration branch; on the additive branch it is documentation and
commitment-record closure.

- Risk: the surface is misclassified as unreleased because the branch is ahead
  of the tag, so a breaking change ships to a live consumer.
  Severity: high. Likelihood: medium. Mitigation: `TDD-DEC-001` and the §4
  classification table govern; any "no compatibility needed" claim is reviewed
  against the 2.1 lineage.
- Risk: the compatibility commitment is stale or narrower than assumed.
  Severity: high. Likelihood: medium. Mitigation: quote it in `EP-M0`; if it
  has expired, return to `TOR-ASSUMPTION-001` and re-decide.
- Risk: the consumer cannot be identified or reached. Severity: high.
  Likelihood: medium. Mitigation: block migration work; an uncoordinated break
  is not an option.
- Risk: semantic drift on an unchanged call path. Severity: medium.
  Likelihood: medium. Mitigation: differential test against a recorded 2.1
  oracle with boundary and error classes.
- Risk: the deprecation path becomes permanent because removal is treated as
  cleanup. Severity: medium. Likelihood: high. Mitigation: `INV-MIGRATION`
  release-gate check; removal is acceptance work in `EP-M3`.
- Risk: the change alters a persisted or wire format not in scope.
  Severity: high. Likelihood: low. Mitigation: `TOR-OPEN-005` inventory before
  drafting the interface.

## Verification plan

### Abstract model

The contract is a partial function from an input class to an outcome (value,
error, or side effect), plus a source-level call shape. Baseline call shapes
must preserve the baseline outcome relation inside the committed window; new
call shapes must produce the specified new outcome. Malformed input is an
observable outcome. The model is the same one recorded in `tech-design.md` §9.1;
this plan discharges it, it does not re-derive it.

### Invariants and lemmas

- `INV-COMPAT-SOURCE`: every call site in the frozen 2.1 consumer fixture
  compiles unchanged against the supported release.
- `INV-COMPAT-BEHAVIOUR`: every baseline call shape observes the recorded 2.1
  outcome, or a documented deprecation diagnostic, for every input class in the
  committed domain.
- `INV-ADDITIVE`: baseline call shapes cannot reach the new behaviour, and the
  new behaviour does not alter the baseline relation.
- `INV-MIGRATION`: the baseline path is removed only when migration evidence
  names the consumer, the migrated version, and the approved removal release.
- `L-REMOVAL-SAFE`: `INV-MIGRATION` plus the approved removal release implies
  removal cannot break a committed consumer.

### Axioms (trusted, not verified here)

- `AXIOM-2.1-BASELINE`: tag 2.1 artefacts are the authoritative baseline.
- `AXIOM-COMPILER`: toolchain and semantic-versioning behaviour follow their
  documented contracts.
- `AXIOM-CONSUMER`: the consumer's declared version matches its deployment;
  checked at the boundary by consumer-owner evidence, not proved locally.

### Methods per obligation

- Obligation: `INV-COMPAT-SOURCE`.
  Method: compile the frozen 2.1 consumer fixture against the candidate
  release. Rationale: source compatibility is exactly a compile property.
  Domain: every recorded consumer call site. Artefact: fixture crate/package
  and a compile-only target, path recorded in `EP-M0`. Evidence: zero-edit
  compile; discharge when the fixture builds. Non-vacuity: a seeded signature
  mutation must fail with the expected symbol or type error.
- Obligation: `INV-COMPAT-BEHAVIOUR`.
  Method: parameterized tests for finite classes and property tests for the
  input range, compared against a recorded 2.1 oracle. Rationale: differential
  comparison catches drift that a rewritten expectation would hide. Domain:
  boundaries, ordinary inputs, malformed inputs, documented errors. Artefact:
  oracle fixture plus differential harness. Evidence: all classes match; the
  property run reports acceptable generator classification. Non-vacuity:
  reject excessive filtering; include at least one witness per class; a seeded
  semantic mutation must be caught.
- Obligation: `INV-ADDITIVE`.
  Method: property test over baseline call shapes plus interface inspection.
  Rationale: proves the new path is not silently reachable. Domain: all baseline
  shapes. Artefact: property suite. Evidence: no baseline shape invokes the new
  path. Non-vacuity: a seeded routing fault must be rejected.
- Obligation: `INV-MIGRATION`.
  Method: release-gate check against the migration record. Rationale: removal
  is a process decision with evidence, not a source property. Domain: the
  removal release. Artefact: checklist assertion or CI check. Evidence: refusal
  when evidence is absent. Non-vacuity: a no-evidence removal attempt must be
  refused.
- Obligation: `L-REMOVAL-SAFE`.
  Method: reasoning over the two preceding obligations. Rationale: the lemma
  connects evidence to action; it needs no separate tool. Domain: the removal
  release. Artefact: conformance note. Evidence: complete chain. Non-vacuity:
  exhibit a migrated version and the permitting release.

### Formal verification decision

No model checker or formal prover. The obligations are compile and differential
properties over a finite interface and generated inputs; the selected methods
are proportionate. The unresolved guarantee concerns external deployment
diversity, which no local proof establishes; `AXIOM-CONSUMER` records that
boundary. Recorded in `Decision log` D6.

Assigned: `REQ-CHANGE`, `REQ-COMPAT`, `INV-ADDITIVE`,

differential suite pass. Compatibility decision for this milestone: the

### `EP-M2` deliberate migration (selected when additive evolution is impossible)

Assigned: `REQ-CHANGE`, `REQ-COMPAT`, `REQ-CONSUMER`, `INV-MIGRATION`,
`INV-COMPAT-SOURCE`, `INV-COMPAT-BEHAVIOUR`.

Red: add a test asserting the baseline remains callable and emits a deprecation
diagnostic naming the replacement and removal release, plus a consumer migration
fixture that fails until the consumer's call sites are updated.

Green: add the deprecation diagnostic and the replacement surface; coordinate
the consumer update with its owner. The retained baseline path is compatibility
machinery justified by the named consumer and commitment; document both at the
deprecation site.

Refactor: remove duplication inside the implementation while preserving the
diagnostic and both externally observable behaviours.

Acceptance: baseline and consumer fixtures pass; the migration record names the
consumer version and the new call sites. Compatibility decision: the named
external consumer and explicit commitment require the retained path; the path
has a removal release.

`EP-M1` and `EP-M2` are alternatives. Do not run both.

### `EP-M3` removal and closure

Assigned: `REQ-CONSUMER`, `INV-MIGRATION`, `L-REMOVAL-SAFE`, `REQ-NO-SHIM`.

On the migration branch: add a release-gate check that refuses removal without
migration evidence, then remove the baseline path at the approved release and
update every in-repository caller and the changelog. On the additive branch:
record the commitment outcome, update the changelog, and confirm no deprecated
path was created.

Red: removal-attempt check fails when evidence is absent. Green: removal
proceeds and the full gate sequence passes. Acceptance: the release-gate
negative control is demonstrated; the migration record is complete; no old path
remains.

## Validation and acceptance

Behavioural acceptance:

- The frozen 2.1 consumer fixture compiles unchanged and reproduces its
  recorded outcomes against the supported release.
- Under additive evolution, a caller using only 2.1 call shapes cannot reach the
  new behaviour, and a caller using the new shape observes the specified result.
- Under migration, the baseline call site still works inside the window and
  emits a deprecation that names the replacement and removal release; the
  consumer is recorded as migrated before removal.
- An attempted removal without migration evidence is refused for the intended
  reason.
- A seeded signature break fails `INV-COMPAT-SOURCE`; a seeded semantic change
  fails `INV-COMPAT-BEHAVIOUR`. These negative controls are required evidence,
  not optional.

Quality criteria: focused tests pass; the recorded wider gates pass; no new
dependency; no unapproved public surface; no persisted-format change without an
explicit migration.

Quality method: run the recorded gate sequence and the release-gate negative
control, retaining transcripts under `/tmp` as the repository policy allows.
