## 1. Background and motivation

`LIB` is published at version 0.8 and has exactly one downstream consumer,
`CONSUMER` (`[KNOWN]` at the scope of the brief). The maintainers are renaming
the public name `OLD` to `NEW` (`[KNOWN]`). The rename is the current milestone
of an ExecPlan that is already executing (`[KNOWN]`).

An older RFC, `RFC-A`, governs the interface that carries `OLD`. It requires an
alias that keeps `OLD` callable while `NEW` is introduced (`[KNOWN]` as a
demand; the alias form is `[ASSUMED]`, see TOR-ASSUMPTION-003). The governing
df12 policy prohibits source-API compatibility machinery for pre-1.0 APIs, and
states that a named consumer does not create an exception
(TOR-CONSTRAINT-001).

The work exists now because the executing milestone forces the conflict into
the open. The plan cannot ship a coherent change while the status of `RFC-A` is
undecided. What changed in the world is not a market event; it is a naming
defect meeting an inherited commitment.

What is not known: why the rename is wanted, whether `NEW` is final, and who
owns `RFC-A` (TOR-OPEN-001, TOR-OPEN-002). These are recorded as open rather
than assumed.

If the change did not happen, `CONSUMER` would keep using `OLD`, and the
published 0.8 versions would remain available.

## 2. Domain

The domain is published library evolution: a pre-1.0 package exposes a
source-API surface that one external project imports. Pre-1.0 is the period in
which an interface can still change, and the governing policy treats
compatibility machinery for such an interface as out of bounds (`[KNOWN]`;
sources listed in §8.1).

Prior art is `RFC-A`, which recorded a requirement for the interface at an
earlier date. It is prior governance, not prior design. Its alias demand is the
conflicting commitment that this document records for explicit resolution.

Publishing a 0.8 artefact does not move the surface into the policy's
released 1.0-or-later category. The category is decided by the release lineage,
not by whether a version is downloadable.

## 5. Job to be done

Maintainer:

> When a public name is wrong and the package is still pre-1.0, a maintainer
> wants to replace `OLD` with `NEW` in a single release, so the package ships
> one current name and carries no obsolete surface to maintain.

Consumer:

> When a pre-1.0 dependency renames a symbol, `CONSUMER` wants a dated, exact
> statement of the break and its replacement, so they can update their call
> site in one edit without guessing whether `OLD` still works.

No multi-actor scenario probe is included. The flow has one producer and one
consumer, no lifecycle states, and no exceptional paths beyond the consumer
upgrading later. A scenario would restate these two job statements without
changing a decision.

## 6. Scope

### 6.1 Goals

- **TOR-GOAL-001.** After the release, the package's public surface exports
  `NEW` and does not export `OLD`. Observable through an exported-name
  inventory.
- **TOR-GOAL-002.** Every in-repository caller, test, example, and
  documentation reference uses `NEW`, and the repository gates pass.
- **TOR-GOAL-003.** `CONSUMER` receives, no later than the release, the exact
  replacement and a version to move to.
- **TOR-GOAL-004.** The `RFC-A` conflict is disposed of by an explicit,
  recorded resolution.

### 6.2 Non-goals

- **TOR-NONGOAL-001.** No alias, deprecated re-export, facade, wrapper, or shim
  preserves `OLD`. This exclusion is plausible because `RFC-A` demands exactly
  that, so a reasonable reader might expect it in scope. A consumer that needs
  `OLD` remains on a previously published 0.8 version.
- **TOR-NONGOAL-002.** No behaviour change under `NEW`. The rename changes the
  name, not what the symbol does.
- **TOR-NONGOAL-003.** No wider API redesign beyond the named symbol or
  symbols.
- **TOR-NONGOAL-004.** No rewrite of `RFC-A`. Readers seeking the old reasoning
  read `RFC-A` together with the separate resolution record.
- **TOR-NONGOAL-005.** No persisted-data or wire-format migration in this scope
  unless TOR-OPEN-003 finds such an obligation. A data or wire obligation, if
  found, is assessed separately and is not satisfied by a source-API shim.

## 7. Success criteria

- **TOR-SUCCESS-001.** The exported API inventory of the release candidate
  contains `NEW` and zero entries for `OLD`. Baseline: `OLD` is exported at 0.8
  (provisional, unverified). Measurement: inventory diff at the release
  candidate. Owner: `LIB` maintainers.
- **TOR-SUCCESS-002.** The repository gates pass in their documented order,
  provisionally `make check-fmt`, `make lint`, `make typecheck`, and
  `make test`. The exact commands must be confirmed from the repository's own
  instructions, which this task did not permit inspecting. None was run for
  this draft.
- **TOR-SUCCESS-003.** `CONSUMER` builds against the release candidate with no
  reference to `OLD` in its source. Evidence source: `CONSUMER`'s build; not
  available in this task, so open.
- **TOR-SUCCESS-004.** The changelog records the rename, its version, and the
  replacement, and the `RFC-A` resolution is recorded beside it.

Implementation acceptance is separate from outcome validation. A merged change
establishes TOR-GOAL-001 and TOR-GOAL-002 only. TOR-SUCCESS-003 needs consumer
evidence. None of these establishes adoption.

## 8. Constraints and assumptions

### 8.1 Hard constraints

- **TOR-CONSTRAINT-001.** The df12 policy prohibits source-API compatibility
  machinery for pre-1.0 APIs. A named consumer does not create an exception.
  Sources: `skills/terms-of-reference-doc/SKILL.md` (contract with downstream
  skills); `skills/terms-of-reference-doc/references/problem-contract.md`;
  `skills/tech-design-doc/references/architecture-contract.md`; the installed
  `execplans` skill. Evidence status `[KNOWN]`.
- **TOR-CONSTRAINT-002.** The interface and all affected callers change
  together, in one coherent change.
- **TOR-CONSTRAINT-003.** An inherited conflicting commitment is recorded for
  explicit resolution. It is neither obeyed silently nor overridden silently.
- **TOR-CONSTRAINT-004.** No shim is added and no history is rewritten.
- **TOR-CONSTRAINT-005.** The executing ExecPlan may not work around an
  unaccepted deviation; it records the deviation and enters `BLOCKED` until
  acceptance.
- **TOR-CONSTRAINT-006.** This document neither creates the compatibility
  requirement `RFC-A` asks for nor authorizes implementation.

### 8.2 Assumptions

Each assumption records its failure consequence and expiry.

- **TOR-ASSUMPTION-001.** The affected surface has no released 1.0-or-later
  contract; the affected name has never shipped under a 1.0 tag. `[KNOWN]` that
  the published version is 0.8; `[ASSUMED]` for the lineage of this specific
  symbol. Failure consequence: a released 1.0 contract would require a
  separate, sourced assessment, and this prohibition analysis reopens. Expiry:
  inspection of the release tags.
- **TOR-ASSUMPTION-002.** `CONSUMER` is the only downstream consumer. `[KNOWN]`
  at the scope of the brief; completeness is `[ASSUMED]`. Failure consequence:
  more parties need notice; the alias decision does not change. Expiry: a
  search of the package's dependents, or the maintainers' statement.
- **TOR-ASSUMPTION-003.** The `RFC-A` alias is a callable source-API alias,
  such as a deprecated re-export or a second name for the same item.
  `[ASSUMED]`. Failure consequence: if the RFC asks only for a documentation
  mapping from `OLD` to `NEW`, no compatibility machinery is at issue and the
  design may include that mapping. Expiry: reading `RFC-A`.
- **TOR-ASSUMPTION-004.** `OLD` does not appear in a persisted format, wire
  format, or configuration key that deployed data depends on. `[ASSUMED]`.
  Failure consequence: a separate persisted-data assessment is required; it
  still does not justify a source alias. Expiry: TOR-OPEN-003.
- **TOR-ASSUMPTION-005.** `CONSUMER` can update its call site on its own
  schedule, and previously published 0.8 versions remain installable.
  `[ASSUMED]`. Failure consequence: the release is sequenced with `CONSUMER`'s
  own release; the alias decision still does not change. Expiry: release
  planning.

### 8.3 Dependencies

- **`CONSUMER` upgrade.** Capability: replace `OLD` with `NEW` and depend on
  the new version. Provider: `CONSUMER` maintainers. Consumer: `LIB`
  maintainers needing outcome evidence. Unblock condition: `CONSUMER` builds
  with `OLD` absent. Scope: gates TOR-SUCCESS-003, not the implementation
  milestone.
- **`RFC-A` resolution.** Capability: an explicit decision that the alias
  requirement is superseded, or an explicit, recorded change to the governing
  policy. Provider: the decision authority named in TOR-OPEN-001. Unblock
  condition: a dated written record naming `RFC-A` and the superseded clause.
  Scope: gates release and the ExecPlan's return from `BLOCKED`.
- **Release authority.** Capability: publication of the breaking version.
  Provider: the publisher. Unblock condition: release approval. Scope: gates
  release.

## Appendix A – Glossary

- **Alias.** A second callable name for an existing item, left in place to
  preserve the old name. In this document it is the form of compatibility
  machinery that `RFC-A` demands.
- **Compatibility machinery.** Any construction whose purpose is to keep an
  obsolete source interface usable: aliases, deprecated re-exports, facades,
  adapters, dual implementations, or temporary wrappers.
- **Pre-1.0.** A release lineage below version 1.0. The governing policy
  prohibits source-API compatibility machinery for such APIs regardless of
  known consumers.
- **Plateau.** A coherent, validated repository state that is safe to continue
  from if later work is postponed. It does not require old and new interfaces to
  coexist.
