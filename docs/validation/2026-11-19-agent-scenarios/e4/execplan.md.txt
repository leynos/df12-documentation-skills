## Purpose / big picture

A queue of records must reach the ledger exactly once. `persist_batch` in
`crates/queue-store/src/persist.rs` accepts a batch, submits it to
`stream_ledger::Ledger::commit`, and reports the outcome to its caller.

Three terms are used throughout. An *epoch* is the ledger's monotonic generation
counter; a submission built against an older generation is *stale*. A *replan*
is the caller's recovery: rebuild the batch from the queue and submit it again.
A *batch* is the ordered set of records submitted in one call.

At dependency revision A the plan's observable outcome was this: a caller
persisting a batch whose epoch had moved receives `StoreError::Replan`, and no
record from that batch is written. The caller rebuilds and retries; the queue
does not lose the batch.

```rust
// revision A: the planned call shape
match ledger.commit(batch) {
    Ok(receipt) => Ok(receipt),
    Err(CommitError::StaleEpoch) => Err(StoreError::Replan),
    Err(other) => Err(other.into()),
}
```

Revision B changes that outcome's reachability, not just its spelling.
`CommitError::StaleEpoch` no longer exists, and `commit` now requires an
`EpochGuard` that the dependency itself refreshes. A stale epoch cannot reach
the submission point, so the branch above has no input that can reach it. The
observable purpose of the feature – "recover from a stale epoch" – is no longer
demonstrable through the dependency, and whether the `Replan` outcome remains
part of the store's contract is a design decision that this plan does not own.
That question is D2.

## Decision log

- D1. Decision: translate every `CommitError` variant into a `StoreError` in
  `persist_batch`, so a stale epoch surfaces to the caller as `Replan`.
  Rationale: an exhaustive translation keeps the dependency's error surface from
  leaking, and `Replan` is the only outcome the caller can act on.
  Date/Author: 2026-11-14, plan author (revision A).

- D2. Decision: PROPOSED, not accepted – record the revision B contract change
  as a deviation and stop. This entry proposes options; it does not choose one.
  Rationale: whether the store still owns a stale-epoch recovery behaviour is a
  requirement and design question. The plan can record the options and their
  costs; it cannot retire an upstream requirement on its own authority.
  Affected identifiers: `REQ-stale-epoch-recovery`, `GAP-replan-unreachable`,
  `INV-replan-on-stale`, `L-translation-total`, `EP-M1`, `EP-M2`, `EP-M3`, and
  the compatibility classification of `StoreError::Replan`.
  Option A – retire the failure path. Delete the translation arm and its test;
  replace the obligation with `AXIOM-ledger-epoch-safety` plus a boundary check
  at the real interface. Cost: `StoreError::Replan` loses its only producer and
  should be removed; the technical design and Terms of Reference must state that
  epoch recovery is delegated to the dependency. Evidence at completion: a
  documented `v2.5.0` guarantee and a test proving the store accepts the real
  guard interface.
  Option B – preserve the behaviour under repository ownership. Have the store
  acquire and validate the guard in its own critical section, so a stale guard
  is rejected before `commit` and `Replan` stays reachable. Cost: new
  repository-owned precondition logic, a new invariant (`L-guard-validity`), a
  seeded fault that must be rejected, and a design change. This is a larger
  change than the plan's approved scope.
  Option C – pin `v2.4.1`. Rejected as written: it preserves an obsolete
  dependency interface with no named consumer, deployed peer, or compatibility
  commitment. It would become admissible only if such a commitment is named and
  sourced.
  Required upstream action: the technical design owner updates the recovery
  requirement and the affected verification obligation; the Terms of Reference
  owner confirms whether the user-visible `Replan` outcome remains a success
  criterion. Until both respond, the plan stays BLOCKED.
  Date/Author: 2026-11-19, plan author (revision B).

- D3. Decision: do not re-declare `CommitError::StaleEpoch` locally, and do not
  add an adapter that reconstitutes the old error shape.
  Rationale: the variant belongs to an external interface; a local replica would
  assert a guarantee the dependency no longer makes and would satisfy the
  compiler without satisfying the contract.
  Date/Author: 2026-11-19.

- D4. Decision: mark every revision-A result for the affected symbols as stale,
  and keep it with its revision label rather than overwriting it.
  Rationale: freshness rules treat a changed external contract and a moved
  symbol as expiry triggers. A green result from an earlier tree is not current
  evidence, but it remains useful history.
  Date/Author: 2026-11-19.

## Verification plan

### Abstract model

States: the store holds a batch and a ledger connection. A call to
`persist_batch` either succeeds, fails without writing, or (revision A only)
fails with a stale-epoch signal that the caller answers by replanning.

At revision A the model contained a transition labelled `stale-epoch` from the
submission state to the replan state, enabled by the dependency returning
`CommitError::StaleEpoch`.

At revision B that transition is removed from the dependency's own transition
relation: an `EpochGuard` can only be constructed for a current epoch, and the
error constructor that produced the transition no longer exists. The state the
planned test targets is therefore unreachable in the model. This is the vacuity
finding: an obligation whose antecedent is unsatisfiable is not discharged by a
check that never exercises it.

### Invariants and lemmas

- `INV-batch-atomic`: for every failed persist, the ledger contains no record
  from the batch. Unaffected by revision B. Linked to `REQ-batch-atomic`.
- `INV-replan-on-stale`: for every batch submitted against a stale epoch, the
  store returns `StoreError::Replan` and writes nothing. SUSPENDED at revision
  B: no admissible input witnesses the antecedent. Linked to
  `REQ-stale-epoch-recovery`.
- `L-translation-total`: the mapping from `CommitError` to `StoreError` is
  total over the dependency's error variants. At revision B the variant set
  shrank, so the lemma's domain shrank; the lemma remains provable by
  exhaustiveness, and the lemma as written at revision A no longer describes the
  contract.

Proposed under D2 option B, not approved:

- `L-guard-validity`: every call to `commit` passes a guard acquired and
  validated in the repository's own critical section, so a guard retained across
  an epoch refresh is rejected before submission.
- `INV-no-dropped-batch`: for every batch accepted by `persist_batch`, exactly
  one of success or a surfaced replayable outcome occurs.

### Axioms (trusted, not verified here)

- `AXIOM-ledger-epoch-safety` (new at revision B): a call to
  `stream_ledger::Ledger::commit` carrying a valid `EpochGuard` cannot fail for
  a stale epoch, because the failure is excluded by the dependency's type and
  documented contract. Source: the `v2.5.0` contract as reported. Repository
  boundary that depends on it: `persist_batch`. This axiom must be checked
  against the real interface, not a mock; a mock that asserts the guarantee
  would prove nothing about it.
- `AXIOM-cargo-lock`: the resolved dependency version is the one the manifest
  requires. Non-trivial here only because a lockfile drift would silently change
  the contract again.

### Methods per obligation

- Obligation: `INV-batch-atomic`.
  Method: parameterized test over failure classes reachable at the pinned
  revision.
  Rationale: finite, enumerable partition.
  Domain: every `CommitError` variant present at the pinned revision.
  Artefact: `crates/queue-store/tests/persist.rs`.
  Evidence: `cargo test -p queue-store --test persist batch_atomic` fails before
  the change and passes after.
  Non-vacuity: at least one witness per variant; a seeded fault that writes a
  partial batch must be rejected.

- Obligation: `INV-replan-on-stale`.
  Method: none available at revision B. Suspended.
  Rationale: the state machine transition that the test exercised is absent from
  the dependency's contract. A parameterized test, a property test, and a
  bounded model check all share the same unsatisfiable antecedent, so none can
  discharge the obligation. Recording a pass would be vacuous.
  Domain: empty at revision B; non-empty at revision A.
  Artefact: `tests::persist::stale_epoch_replans` (revision A, now unusable).
  Evidence: at revision A the red failure was `expected Replan, got Ok(_)`. At
  revision B the red cannot be produced, which is an escalation trigger, not a
  pass.
  Non-vacuity: fails – no satisfying witness exists. This is the finding, not an
  omission.

- Obligation: `L-translation-total`.
  Method: type-level exhaustiveness plus a parameterized test.
  Rationale: the compiler proves totality over the variant set; the test pins
  the intended mapping per variant.
  Domain: the `CommitError` variants present at the adopted revision.
  Artefact: the `match` in `persist_batch` and
  `tests::persist::error_translation_is_total`.
  Evidence: removing a match arm fails to compile; the test enumerates each
  variant.
  Non-vacuity: every variant in the domain has a witness; if the domain is empty
  the obligation is vacuous and must be withdrawn, not passed.

- Obligation: `L-guard-validity` (proposed, option B only).
  Method: state-machine property test over refresh and submit interleavings.
  Rationale: the property is temporal and the repository owns the orchestration.
  Domain: guard acquisition, refresh, and submission orderings; bounded to two
  concurrent submissions.
  Artefact: `crates/queue-store/tests/guard_validity.rs`.
  Evidence: a seeded fault that retains a guard across a refresh must be
  rejected for the intended reason.
  Non-vacuity: the fault is reachable by construction; if the dependency offers
  no way to observe a stale guard, record the exception rather than fabricate a
  witness.

### Formal verification decision

No prover and no model checker. The disputed property is reachability of a
state that the dependency's type excludes. A prover would restate
`AXIOM-ledger-epoch-safety` rather than establish anything about repository
code, and a model would have no reachable target state – exactly the vacuity the
skill forbids. Type-level absence plus a real-boundary check is proportionate.
This decision is recorded in D2 and D4 and would be revisited under option B,
where `L-guard-validity` is genuinely temporal.

### Suggested BDD features

Proposed path: `crates/queue-store/tests/features/persist.feature`.

Feature: Batch persistence across ledger epochs

  Scenario: A batch is written once
    Given an empty ledger at the current epoch

  Scenario: A stale epoch forces a replan

the plan later is idempotent: the translation milestone rewrites one `match`, and
re-running the test suite is safe at any point. Recovering from BLOCKED means
recording the accepted option in D2, reconciling the upstream design and Terms
of Reference, and then resuming `EP-M1` before `EP-M3`.
