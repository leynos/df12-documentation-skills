## Purpose / big picture

The capture path reads input in fixed-size chunks. A chunk is the number of
bytes the reader consumes per iteration; a multi-chunk operation is one that
spans more than one chunk. Two pieces of evidence are currently treated as
proving more than they do.

First, a test intended to exercise multi-chunk behaviour passes after the chunk
size was increased. The fixture is now no larger than one chunk, so the capture
loop executes one iteration. The test is green, but it never crosses a chunk
boundary. A reader could observe this by counting loop entries: it sees one
where the test's name promises at least two.

Second, a benchmark reports a performance gain for an echo workload. This plan
uses echo to mean the path that captures input and then replays or returns it;
`EP-M0` confirms the actual composition against the code. The design attributes
the result to a capture-only change. The benchmark therefore exercises a
different execution path from the one named in the claim. A gain on echo is not
evidence for a gain in capture alone.

After this work, a multi-chunk test at the configured size observes at least
two capture iterations and crosses a boundary. A capture-only benchmark records
zero echo invocations and positive captured bytes, and reports a fixed
workload, a control, the environment, the measurement protocol, uncertainty,
and a pre-registered threshold. The design either supports its claim with that
evidence or states that the claim is unverified. A reviewer can observe success
by reading the test transcript, the benchmark path assertion, and the revised
design sentence; none of them relies on a passing count alone.

The work closes the evidence-scope gaps in the design amendment
`capture-path-verification-amendment.md`. It does not assert that the
capture-only gain is false or that multi-chunk behaviour is broken. Both are
unverified until the obligations below are discharged.

## Risks

- Risk: The fixture was enlarged, not the chunk size, and the reported cause is
  misattributed.
  Severity: medium. Likelihood: medium. Mitigation: `EP-M0` records the actual
  chunk size and fixture length, and `EP-M1` reproduces the one-iteration
  observation before changing either.
- Risk: Short reads or an extra end-of-file read make the iteration count
  non-deterministic, so an exact-count assertion is flaky.
  Severity: medium. Likelihood: medium. Mitigation: assert a lower bound of two
  for a payload strictly larger than two chunks; assert exact counts only where
  the harness controls the read pattern.
- Risk: The harness counts iterations from inside the code under test, making
  the oracle circular.
  Severity: high. Likelihood: medium. Mitigation: observe reads at the harness
  boundary, or use a test probe that records calls independently of the loop
  counter.
- Risk: The capture-only benchmark still executes echo work through a shared
  helper, so the path assertion passes on paper but not in execution.
  Severity: high. Likelihood: medium. Mitigation: instrument the echo stage and
  assert zero invocations per accepted sample; use a separate echo control that
  must fail the capture-only assertion.
- Risk: Benchmark noise, cache state, or frequency scaling produces a spurious
  gain or loss.
  Severity: medium. Likelihood: high. Mitigation: record the environment, fix
  the protocol, repeat samples, report uncertainty, and compare against a
  pre-change control under the same conditions.
- Risk: A green capture-only measurement is treated as proof of a causal
  mechanism the benchmark did not isolate.
  Severity: high. Likelihood: medium. Mitigation: restrict the claim to the
  measured path and workload; do not claim a mechanism without an ablation or
  profile.
- Risk: The design prose is updated before the evidence is accepted.
  Severity: medium. Likelihood: low. Mitigation: `EP-M3` updates prose only
  after `OBL-EVID-001` and `OBL-EVID-002` are discharged and the threshold
  outcome is accepted.

## Verification plan

### Abstract model

Let `C > 0` be the chunk size in bytes and `L >= 0` the payload length in bytes.
For a reader that processes one buffer per successful read, the observed number
of loop entries `n` satisfies `n >= ceil(L / C)` when reads are full. Short
reads may raise `n`; an explicit end-of-file read may add one. For `L > 0`, a
multi-chunk claim requires `n >= 2` and at least one boundary crossing.

For the benchmark, let the path selector `p` be `capture` or `echo`. A measured
sample `s` carries `capture_bytes(s)`, `echo_invocations(s)`, and a timing
statistic `T(s)`. A sample is admissible for the capture-only claim only when
`p = capture`, `capture_bytes(s) > 0`, and `echo_invocations(s) = 0`. The claim
compares `T` on the capture path against the pre-change control on the same
path. It does not compare capture against echo.

Malformed inputs and violated preconditions: if `C = 0`, the reader must reject
the configuration or the harness must refuse the case; the test must not
silently produce an infinite or zero-iteration loop. If the benchmark cannot
assert its path, the sample is rejected rather than reported.

### Invariants and lemmas

- `INV-VER-001`: every case of the multi-chunk test observes `n >= 2` and
  crosses at least one chunk boundary. Linked to `TDD-VER-001` and
  `OBL-VER-001`.
- `INV-EVID-001`: every sample contributing to the capture-only statistic has
  `capture_bytes > 0` and `echo_invocations = 0`. Linked to `TDD-PERF-001` and
  `OBL-EVID-001`.
- `INV-EVID-002`: the workload, control, environment, protocol, uncertainty
  method, and threshold are recorded before measurement and unchanged in the
  reporting revision. Linked to `OBL-EVID-002`.
- `INV-DOC-001`: every design sentence about performance names its path and
  matches the current discharge state. Linked to `TDD-DOC-001` and
  `OBL-DOC-001`.

- `L-VER-001`: `n >= 2` implies at least one iteration processed a chunk after
  the first read, so the multi-chunk path was exercised. Depends on
  `AXIOM-READER`.
- `L-EVID-001`: an admissible capture sample with zero echo invocations and

  Established by path construction, not measurement.
- `L-DOC-001`: prose that names the echo path cannot support a capture-only
  sentence. Follows from `L-EVID-002` and the definition of evidence scope.

### Axioms (trusted, not verified here)

- `AXIOM-INSTR`: the harness counters record actual invocations and bytes.
- `AXIOM-TIMER`: the benchmark timer measures the stated resource with
  documented resolution.
- `AXIOM-ENV`: the recorded hardware, operating system, runtime, and cache state
  are stable within the reported bounds.
- `AXIOM-READER`: one loop body execution corresponds to one successful read.
  `EP-M0` confirms this against the code; if it is false, the model and the
  test's lower-bound assertion are revised before `EP-M1` proceeds.

Third-party libraries and the operating system are trusted as documented
interfaces. The repository-owned harness logic, path selection, and threshold
handling are verified at their real boundary, not against a mock that assumes
the disputed property.

### Methods per obligation

`OBL-VER-001` – multi-chunk non-vacuity.

- Method: parameterized test over finite boundary classes.
- Rationale: the input space that matters is small and explicit. A parameterized
  test names each class and fails with the observed count.
- Domain: `L <= C` (control, expect rejection of a multi-chunk claim),
  `C < L <= 2C` (expect `n >= 2`), `L = kC + 1` for a small `k` (remainder
  boundary), and `L >> C` (many iterations). Choose `L = 2C + 1` as the primary
  witness.
- Artefact: the existing multi-chunk test, augmented with a harness-owned read
  or iteration observer. Path recorded in `EP-M0`.
- Evidence: red – the new `n >= 2` assertion fails at the current fixture and
  chunk size with observed `n = 1`. Green – the same assertion passes after the
  fixture or chunk size is corrected, with the observed count printed.
- Non-vacuity: the `L = 2C + 1` witness produces at least three reads under
  full-read assumptions. The `L <= C` case is a negative control and must fail
  the multi-chunk assertion. A temporary mutation that clamps the chunk size to
  at least `L` must also be rejected, then reverted.

`OBL-EVID-001` – capture-only path.

- Method: instrumented benchmark with a path assertion plus a control run.
- Rationale: the defect is path scope, which a timing number alone cannot
  reveal. The instrumentation makes the path observable.
- Domain: capture-only entrypoint and echo entrypoint under the same input
  generation, chunk size, and environment.
- Artefact: the benchmark harness, with counters for captured bytes and echo
  invocations. Path recorded in `EP-M0`.
- Evidence: red – the current echo benchmark fails the capture-only assertion
  because `echo_invocations > 0`. Green – the capture-only run passes with
  `echo_invocations = 0` and `capture_bytes > 0`.
- Non-vacuity: each accepted sample exhibits positive captured bytes. The echo
  control must fail the same assertion for the intended reason. A sample with
  zero captured bytes is rejected rather than treated as fast.

`OBL-EVID-002` – frozen performance record.

- Method: record inspection against the performance claim table, pinned to a
  revision.
- Rationale: the claim is uninterpretable without workload, control,
  environment, protocol, uncertainty, and threshold.
- Domain: the benchmark report and the pre-registration commit or revision.
- Artefact: the completed record in the design amendment, with the revision
  that fixed the threshold.
- Evidence: red – the current record fails on the missing fields. Green – all
  fields are populated and the reporting revision matches the pre-registered
  threshold.
- Non-vacuity: the current record is the negative control; a record with a
  threshold changed after measurement is also rejected.

`OBL-DOC-001` – prose reconciliation.

- Method: trace review from each performance sentence to its evidence.
- Rationale: the design overclaims because prose and evidence were not
  reconciled. A trace review makes the mismatch visible.
- Domain: every sentence in the design that states or implies a gain,
  mechanism, or path.
- Artefact: the revised amendment section and, if a design document exists, its
  performance section.
- Evidence: red – the current sentence attributing an echo result to capture
  alone has no supporting obligation. Green – every sentence names a path and a
  discharged obligation, or marks itself unverified.
- Non-vacuity: the current sentence is the negative control and must be
  rejected by the review.

### Formal verification decision

No model checking or formal proof is used. The properties are finite boundary
classes and instrumented measurement scope, not protocol invariants,
concurrency, or arithmetic safety. A proof would not address the failure mode,
which is a mismatch between the measured path and the claimed path. This
decision is recorded as `D5`.

Residual gaps accepted by this method:

- Short reads can make the observed count exceed the model; the test asserts a
  lower bound where the harness does not control reads.
- The benchmark measures throughput on one environment; it does not establish a
  universal gain.
- No causal mechanism is established unless a separate ablation or profile is
  performed. The claim is limited to the measured path and workload.

## Validation and acceptance

Acceptance is behavioural, not structural:

1. The multi-chunk test fails at the current configuration with observed
   iteration count 1 and passes after correction with an observed count of at
   least 2. The green transcript prints the count.
2. The capture-only benchmark report asserts zero echo invocations and positive
   captured bytes for every accepted sample. The echo control fails the same
   assertion.
3. The performance record contains workload, control, environment, protocol,
   uncertainty, and a threshold fixed before measurement. The threshold is
   unchanged in the reporting revision.
4. The design prose names the measured path and matches the claim's state.
   `TDD-PERF-001` is supported only if the threshold is met.

Quality criteria:

- Tests: the focused multi-chunk test passes; the negative control is rejected;
  the repository gate sequence passes or its baseline failures are recorded.
- Verification: `OBL-VER-001`, `OBL-EVID-001`, `OBL-EVID-002`, and
  `OBL-DOC-001` are discharged with transcripts; no obligation remains
  undischarged without an accepted deferral.
- Lint and typecheck: the recorded gate commands pass.
- Performance: the capture-only statistic and uncertainty are reported against
  the pre-registered threshold. A shortfall is escalated, not waived.
- Security: no new trust boundary or dependency is introduced.

Quality method: the red, green, and negative-control transcripts above, plus
the sequentially run gates with logs.

The currently reported passing results are not acceptance evidence. They may
appear in `Artefacts and notes` as the red-state observations only.

## Idempotence and recovery

The test edits are idempotent: re-running the focused test does not change the
tree. The temporary single-read fault is applied only for the negative control
and must be reverted immediately; re-run the green test afterwards.

Benchmark runs are repeatable but not deterministic. Re-run the recorded
protocol; if results are noisy, report the uncertainty and retain all samples
rather than selecting a favourable one. If a milestone fails, revert that
milestone's changes and re-apply from its red step. Do not reset unrelated work
in a shared worktree.

If the environment changes or the code is rebased, re-run `OBL-VER-001` and
`OBL-EVID-001`; earlier green results are not current evidence.

implementation and call that agreement.
