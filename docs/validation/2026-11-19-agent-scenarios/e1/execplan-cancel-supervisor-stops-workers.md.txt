## Purpose / big picture

A supervisor process starts one or more worker processes. An approved Terms of
Reference (ToR) and an Architecture Decision Record (ADR) both promise that
cancelling the supervisor stops its workers. An integration probe observed
workers still alive after the supervisor exited.

This plan exists to resolve that contradiction in one of two ways: either the
implementation is changed to honour the promise, or the promise is explicitly
and authoritatively changed. It does not authorise either yet. Its immediate
purpose is to record the contradiction accurately, preserve the approved intent,
and hold execution until the decision authority chooses a resolution.

Define terms as used here:

- **Supervisor**: the process that starts and manages worker processes.
- **Worker**: a process started by the supervisor, directly or through a
  process group.
- **Cancel**: the operator action, command, signal, or API call that asks the
  supervisor to stop.
- **Supervisor exit**: the supervisor process is no longer alive.
- **Alive**: a process exists that a process-table check can find, including a
  zombie or orphan. The precise check is part of the open question in
  `Decision log` D2.

Observable example, using `kill -0` as a liveness check:

```plaintext
Current observed behaviour (probe result supplied with the task):
  1. Start a supervisor with at least one worker.
  2. Cancel the supervisor.
  3. The supervisor exits.
  4. kill -0 <worker-pid> succeeds -> the worker is still alive.

Target behaviour under option O1 (honour the promise):
  1-3. As above.
  4. kill -0 <worker-pid> fails -> no worker started by that supervisor lives.
```

The plan preserves normal cancellation, normal worker shutdown, and existing
supervisor exit semantics other than the point at issue. It deliberately does
not preserve any observed orphan behaviour as a requirement.

## Verification plan

### Abstract model

Model only what the promise needs. A supervisor `S` has lifecycle states
`starting`, `running`, `cancelling`, and `exited`. It owns a finite set of
workers `W(S) = {w1 ... wn}` that it started. `alive(w, t)` is true when a
process-table liveness check finds `w` at time `t`.

`cancel(S)` is an operator action. `exit(S)` is the event that `S` is no longer
alive. Under the promise as literally stated, with no grace period:

```plaintext
INV-CANCEL-TERMINATES:
  for every w in W(S):
    after exit(S), not alive(w, t) for every t >= exit_time(S)
```

Malformed or ambiguous inputs: an undefined grace period, an unknown worker
census, or a liveness check that counts or ignores zombies are not handled by
guessing. They are open questions (D2) that block verification.

### Invariants and lemmas

- `INV-CANCEL-TERMINATES` (above): the required liveness/safety property.
  Established by `LOCAL-TDD-REQ-CANCEL-STOPS-WORKERS`.
- `INV-CANCEL-REACHES-WORKERS`: during cancellation, every worker in `W(S)`
  receives a termination request, or is already not alive. This is a necessary
  condition for the promise; it does not by itself establish termination.
- `INV-SUPERVISOR-WAITS`: if the design requires the supervisor to wait, `S`
  does not reach `exited` while any worker in `W(S)` is alive. This is a
  candidate design invariant, not assumed without reading the design.
- `L-SIGNAL-SUFFICES`: a delivered termination request causes a cooperative
  worker to exit. This is an external/worker assumption, not repository logic.
- `L-NO-LOSS`: the worker census used by the check equals the set the
  supervisor actually started. Without this lemma the probe could pass or fail
  vacuously by looking at the wrong processes.

### Axioms (trusted, not verified here)

- `AXIOM-PROBE-OBSERVATION`: the supplied probe accurately observed the
  workers it reports. Source: the scenario's integration probe. Boundary: the
  probe harness and process-table check. Scope limit: command, output,
  timestamps, and census are not supplied.
- `AXIOM-PROBE-GOVERNS-PROMISE`: the probe observes at a time and over a
  worker set that the promise governs. Source: none yet; this is unverified,
  and resolving D2 is the test. If false, the probe is not a counterexample.
- `AXIOM-OS-PROCESS-SEMANTICS`: the platform delivers signals, reparents
  orphans, and reports liveness as documented. Source: platform contract.
  Boundary: the supervisor's use of process groups and reaping. Not proved
  here; exercised against the real platform in the integration test.

### Methods per obligation

- Obligation: `INV-CANCEL-TERMINATES`.
  Method: integration/behavioural test that starts a supervisor and a known
  worker census, cancels, waits for supervisor exit, then checks every worker
  with a process-table liveness check. Combine with a parameterized test over
  worker counts and worker states.
  Rationale: the property is about real process lifetime and exit ordering,
  which unit tests with mocks cannot establish. The supplied probe is the
  same shape, so the method is known to reach the defect.
  Domain: 0, 1, and N workers; workers already exited; a worker slow to exit;
  a worker that ignores the first termination request.
  Artefact: `[OPEN]`; use the repository's existing integration-test path.
  Evidence: red command fails with a live-worker assertion while the defect
  exists; green command passes after the fix. Discharge: every generated case
  observes no live worker after supervisor exit, within the D2 definition.
  Non-vacuity: the supplied probe is the negative witness that the assertion
  can fail. Add a seeded fault (skip termination or skip waiting) and require
  the test to fail for the intended reason; revert it afterwards. Include a
  positive control with a worker that exits normally.

- Obligation: `INV-CANCEL-REACHES-WORKERS`.
  Method: parameterized test or instrumentation of the cancellation path.
  Rationale: separates "the request was never sent" from "the worker did not
  exit", which have different fixes.
  Domain: each worker spawn mode the supervisor supports.
  Artefact: `[OPEN]`.
  Evidence: each worker receives the request or is already dead.
  Non-vacuity: at least one worker is alive at cancellation; assert the
  observation is non-empty.

- Obligation: `L-NO-LOSS`.
  Method: the test harness records the supervisor's own worker list before
  cancellation and checks exactly that list afterwards.
  Rationale: prevents a passing test that checks an empty or unrelated set.
  Artefact: `[OPEN]`.
  Evidence: the recorded set is non-empty and matches the started workers.
  Non-vacuity: require `|W(S)| >= 1` in every case that claims the invariant;
  a zero-worker case is a separate boundary, not evidence for the promise.

- Obligation: `INV-SUPERVISOR-WAITS` (only if the design adopts a wait
  requirement).
  Method: bounded state-machine model check of the cancellation protocol,
  cross-checked against the shared transition function.
  Rationale: exit ordering and signal escalation are temporal properties that
  example tests cover poorly.
  Domain: states `running`, `cancelling`, `draining`, `exited`; transitions for
  signal, worker exit, timeout, and escalation.
  Artefact: `[OPEN]`; model and transition function path.
  Evidence: model checker reports no reachable state where `exited` holds and
  a worker is alive; bounds admit the shortest cancellation.
  Non-vacuity: show the `exited` state is reachable and the bad state would be
  reachable without the wait transition (mutation).
  Residual gap: the model abstracts real process timing; the integration test
  remains the boundary check.

### Formal verification decision

No formal proof is planned for the initial fix. The obligation is a
finite-process lifecycle property best established by integration tests over a
parameterized partition, with a state-machine model only if the design adds a
multi-step cancellation protocol. The supplied probe already demonstrates that
the integration method reaches the defect. A model or proof would add strength
for ordering under concurrency but would not remove the need to test the real
process boundary. Record the final choice in `Decision log` at approval.


revised measurement conditions, plus upstream documents that state the weaker
or qualified guarantee without ambiguity.

- Tests: the focused regression test fails for the intended reason and passes

- Lint and typecheck: repository targets pass.
- Performance: no claim and no benchmark planned.
- Security: no new surface; no scan required beyond the normal gates.

Quality method: the repository's gate sequence, run sequentially, plus the
integration test transcript.

## Idempotence and recovery
