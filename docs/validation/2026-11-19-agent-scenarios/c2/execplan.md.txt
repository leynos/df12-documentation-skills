## Purpose / big picture

The repository exposes a helper that only its tests call. The helper's shape is
being changed. The brief suggests keeping the old tests compiling through a
compatibility shim.

After this change, one helper interface exists, every test calls it, and the old
interface is gone – not deprecated, not aliased, not forwarded. The tests still
assert what they asserted before, or a recorded disposition explains why a
particular assertion no longer applies. A reader can confirm the outcome by
building the tree, running the suite, and searching for the old name and finding
nothing.

Terms used here:

- *Helper*: the callable under change. Its real name, path, and signature are
  written into `EP-M0` below; this plan uses `<helper>` until then.
- *Call site*: any expression that invokes the helper or names it. Before the
  change these are tests; `EP-M0` proves that.
- *Test-only surface*: a callable exposed for the test suite, with no consumer
  outside the repository. This classification is what prohibits a shim.
- *Disposition*: the recorded fate of one pre-change test – migrated, rewritten,
  or retired with a reason.
- *Shim*: any alias, forwarding function, `deprecated` entrypoint, facade, dual
  implementation, or temporary wrapper that lets old call text keep working.

The user-visible outcome is small: the suite runs unchanged in meaning and the
codebase no longer carries an interface kept alive for tests alone. The
deliberate change is that old test call text stops compiling; that is the point,
not a regression.

## Constraints

These are hard invariants. A conflict is an escalation, not a workaround.

1. No compatibility machinery of any kind for the old helper: no alias, no
   `deprecated` forwarding entrypoint, no facade type, no dual implementation,
   no `cfg`-selected old path, no migration wrapper. The prohibition comes from
   the test-only classification in `TOR-CONSTRAINT-001`, not from a preference.
2. Every call site is migrated in the same change. No committed state contains
   both the old and the new interface. Do not commit between adding the new
   surface and deleting the old one.
3. No change to observable helper behaviour, no new public API, no new
   dependency. Any feature flag may be added only if an existing test location
   cannot compile without one, and that triggers escalation first.
4. No test is deleted or weakened without a disposition recorded in this plan.
   "It would not compile" is not a disposition.
5. Visibility is not widened beyond what the current test locations require.
   Narrowing is permitted and preferred.
6. Do not modify unrelated modules, fixtures, or tests.
7. `EP-M0` is read-only reconnaissance. No production edit begins until its
   inventory is recorded and its classification gate passes.
8. Implementation begins only after the user approves this plan. Silence is not
   approval.

## Risks

1. Risk: silent coverage loss while migrating tests.
   Severity: high. Likelihood: medium. Mitigation: the disposition record makes
   every test account for itself, and the seeded-fault control proves the
   migrated suite can still fail.
2. Risk: a test depends on incidental detail of the old shape rather than on
   behaviour, so mechanical migration is impossible.
   Severity: medium. Likelihood: high. Mitigation: rewrite such a test to assert
   the behaviour it stood in for, and record the original assertion.
3. Risk: a non-test caller exists despite the brief.
   Severity: high. Likelihood: low. Mitigation: `EP-M0` searches the whole tree;
   a hit stops the plan rather than adding a compatibility path.
4. Risk: the helper is reachable from a released artefact by a consumer outside
   the repository.
   Severity: high. Likelihood: low. Mitigation: manifest and release-tag audit
   in `EP-M0`; a positive result sets the plan to `BLOCKED` for reassessment.
5. Risk: the plan's placeholders mislead an implementer who skips `EP-M0`.
   Severity: high. Likelihood: medium. Mitigation: `EP-M0` is a gate, and every
   later step names the fact it needs from it.
6. Risk: the repository's gates are slower than expected under shared compile
   admission. Severity: low. Likelihood: medium. Mitigation: run gates
   sequentially, allow a longer timeout, and read captured logs rather than
   re-running blindly.
7. Risk: the exact symbols or toolchain differ from the placeholder shapes in
   `Concrete steps`. Severity: low. Likelihood: high. Mitigation: `EP-M0`
   replaces every command shape with the repository's documented one.

## Decision log

- D1. Decision: reject the suggested compatibility shim.
  Rationale: the surface is test-only, so compatibility machinery is prohibited;
  no external consumer exists to serve; and the only thing preserved would be
  the old call text of tests. The alternative – keeping a forwarding function –
  was rejected as overhead with no beneficiary. The rejection is recorded in the
  terms of reference as `CR-1`.
  Date/Author: 2026-11-19, authoring agent (proposal, not approval).

- D2. Decision: preserve test intent, not test text.
  Rationale: migrating a call keeps its assertion fixed, which is the strongest
  available evidence that behaviour is unchanged. Rewriting is reserved for
  tests that assert shape. Retaining the old shape so the text survives inverts
  the dependency between tests and production code.
  Date/Author: 2026-11-19, authoring agent.

- D3. Decision: one coherent change, no intermediate dual interface.
  Rationale: compatibility would not be required if this landed atomically, so
  none is introduced to create a plateau. The alternative – add, migrate, then
  delete across commits – was rejected because it leaves a committed state with
  two interfaces.
  Date/Author: 2026-11-19, authoring agent.

- D4. Decision: no model checking or formal proof.
  Rationale: the change introduces no algorithm, protocol, state machine, or
  concurrency. The live risk is a missing assertion, which a disposition record
  plus a seeded fault addresses. A prover would not find an assertion nobody
  wrote.
  Date/Author: 2026-11-19, authoring agent.

- D5. Decision: provisional tolerances pending `EP-M0`.
  Rationale: no survey of the tree was possible under the authoring isolation
  rule, and no historical plan could be read. The budgets are sized for a
  helper plus its call sites and must be confirmed at the gate. An undersized
  budget is an escalation, not a re-baseline.
  Date/Author: 2026-11-19, authoring agent.

## Verification plan

### Abstract model

The model is two finite lists and a correspondence between them. List `B` is
the set of assertions in the pre-change suite, each tagged with the test that
makes it and the behaviour class it exercises. List `A` is the post-change
suite. A mapping `f` assigns each element of `B` either a test in `A`, a named
covering test, or a retirement with a reason. The change is correct when `f` is
total, the tree compiles without the old symbol, and a seeded behavioural fault
is rejected.

Preconditions: the helper is called only from tests; the suite runs green
before the change. If either is false, stop and escalate. Malformed input is not
a concern; the model reasons about source text and test outcomes, not runtime
data.

### Invariants and lemmas

- `INV-absence` – After the change, no reference to `<old-symbol>` resolves in
  the tree, and no alias or forwarding entrypoint carries its role. Linked to
  `TDD-REQ-001`, `TDD-REQ-002`, `TDD-REQ-004`.
- `INV-coverage` – The mapping `f` is total over `B`: every pre-change test has
  exactly one disposition, and each retirement names a covering test or shows
  the obligation obsolete. Linked to `TDD-REQ-003`.
- `INV-visibility` – The helper is reachable from no context that could not
  reach it before. Linked to `TDD-REQ-005`.
- `L-behaviour` – If the helper's observable result changes for an input the
  suite exercises, at least one migrated test fails. This lemma is what turns
  `INV-coverage` from a claim about intent into a claim about detection.

### Axioms (trusted, not verified here)

- `AXIOM-build` – The compiler resolves every reference in the compiled set and
  fails on an unresolved symbol. Source: the language's documented semantics.
  Boundary: the repository's build configuration must actually compile the test
  target; `EP-M0` confirms the command does.
- `AXIOM-runner` – The test runner reports failure for a failed assertion and
  counts only executed tests. Boundary: confirm that `EP-M0`'s focused command
  runs the named test rather than selecting zero tests.
- `AXIOM-search` – The search tool matches identifier occurrences in tracked
  source under the stated globs. Boundary: corroboration only; the build is the
  primary check.

No third-party internals are assumed. The repository's own build and test
configuration is exercised directly rather than mocked.

### Methods per obligation

`INV-absence`

- Obligation: no residual reference to or role for the old symbol.
- Method: delete the surface and build; corroborate with an identifier search.
- Rationale: the compiler is an exhaustive checker over the compiled set, which
  is stronger than a search over source text.
- Domain: the whole test target and the production target.
- Artefact: the tree itself.
- Evidence: the build succeeds only with the old surface removed; `EP-M0`'s
  search returns no matches afterwards.
- Non-vacuity: in a scratch change, re-add one reference to the deleted symbol
  and confirm the build fails and the search hits it. Revert. Without this,
  "no matches" could mean the search's globs were wrong.

`INV-coverage`

- Obligation: the mapping `f` is total and no assertion is dropped silently.
- Method: structural review of a disposition table against `EP-M0`'s complete
  test list.
- Rationale: the property is about the correspondence between two lists, which
  a human reviewer can check exhaustively for a suite of this size; no generator
  would produce a better oracle.
- Domain: every test in `EP-M0`'s list.
- Artefact: the disposition table in this plan.
- Evidence: no blank rows; each retirement names a covering test; the reviewer
  signs off in `Artefacts and notes`.
- Non-vacuity: the table must contain at least one migrated test for each
  behaviour class the suite exercises, and at least one boundary or failure case
  if one exists. A table of happy-path migrations only is a coverage failure,
  not a pass.

`L-behaviour`

- Obligation: a behavioural change in the helper is detected by the suite.
- Method: seeded fault plus focused test run.
- Rationale: it directly tests sensitivity, which is the property the migration
  claims; reading the tests cannot establish it.
- Domain: one exercised input per behaviour class, or one representative input
  if the classes share a code path.
- Artefact: a temporary patch to `<helper-file>`, reverted after the run.
- Evidence: at least one migrated test fails, and the failure names the affected
  assertion.
- Non-vacuity: the fault must touch logic a migrated test claims to observe. If
  no test fails, record the class as insensitive and return to `INV-coverage`
  rather than accepting the migration.

`INV-visibility`

- Obligation: no new reachability.
- Method: comparison of the module and manifest structure before and after, plus
  a compile witness for any retained export.
- Rationale: visibility is a build-level property; the compiler demonstrates
  whether a test can reach the symbol.
- Domain: the helper's module, the crate or package manifest, and the test
  locations.
- Artefact: the `EP-M0` inventory and the post-change manifest diff.
- Evidence: any retained export has a test that fails to compile without it.
- Non-vacuity: if no test needs the export, narrowing must be performed; a
  retained export with no witness is a failure of this obligation.

### Formal verification decision

No formal method is used. See `D4`. The strongest risk is an assertion nobody
wrote, which no prover addresses. The selected methods are proportionate to a
refactor of one internal callable.

Proposed only; adding a BDD framework requires separate authorisation. If the

## Idempotence and recovery

`EP-M0` is read-only and safe to repeat. `EP-M1` is a single commit that can be
reverted as a unit; reverting restores the baseline interface and suite. The
seeded fault in `EP-M2` must be reverted with `git checkout -- <helper-file>`
and confirmed with `git diff --stat`; a fault left in the tree is the most
likely way to corrupt a later result. Gates are re-runnable; the working tree is
clean between runs. No data migration or deployment is involved, so no rollback
beyond a code revert is required. Leave no scratch branches, temporary patches,
or generated files behind.

## Interfaces and dependencies

At the end of `EP-M1` there is exactly one callable surface for the helper. Its
signature is fixed by `EP-M0`'s reading of the callers; the design requires it
to accept the information every current call provides and to return what every
current assertion inspects. The executing agent chooses the concrete parameter
and return types and records them in `Context and orientation`. Shape, in
generic form:

```plaintext
<minimum visibility> fn <helper>(<parameters>) -> <result>
```

Rules for that surface:

1. One entry point. No overload, trait method, or constructor accepting the old
   argument shape.
2. The body is moved from the old helper, not reimplemented, unless a
   reimplementation is provably identical for every exercised input; in that
   case record the reasoning.
3. A doc comment says the surface exists for tests.
4. No `allow(dead_code)` or equivalent suppression.

Ownership: the helper's module owns the implementation; tests own the call
sites. Reuse policy: do not add a parallel utility in another module, and do not
reparse or re-derive inside tests what the helper already provides.

Dependencies: none authorised. The change uses the language's standard library
and the repository's existing test framework only. A new test dependency, BDD
runner, or feature flag requires escalation before use.
