## Purpose / big picture

The library is published at version 0.8. Its API rename is the current
milestone of an ExecPlan that is already executing. A downstream consumer uses
the old interface. An old RFC requires the rename to preserve an alias for the
old API name. The governing df12 policy prohibits source-API compatibility
machinery for pre-1.0 APIs, and a published 0.8 release remains pre-1.0.

The intended observable outcome is that a caller of the library uses one name,
the new one, and the library build, tests, and API surface agree. For example,
a consumer that previously called `old_api_name` calls `new_api_name` after the
change, and no exported alias, deprecated entrypoint, facade, wrapper, or shim
keeps `old_api_name` alive. The placeholders `old_api_name` and `new_api_name`
stand in for the actual identifiers, which were not supplied; replace them
with the repository's real symbols before executing.

This plan is blocked before that outcome is claimed. The old RFC's demand is an
inherited commitment. The policy prohibits satisfying it with an alias, but the
plan may not silently omit it either. Only the RFC's decision authority, or the
policy owner acting within their authority, can resolve the conflict. Until that
resolution is recorded and the deviation is accepted, implementation does not
resume.

The deliberately changed behaviour is the removal of the old source name. The
release notes and migration guide must say so. Persisted data and wire formats
are not known to be affected; if they are, they require a separate migration
assessment and are not covered by the source-API decision.

## Constraints

Hard invariants that must hold throughout implementation. These are not
suggestions; violation requires escalation, not a workaround.

- The governing df12 policy prohibits source-API compatibility machinery for
  private APIs, test-only APIs, pre-1.0 APIs, and unreleased changes ahead of
  the latest applicable formal release tag. The 0.8 surface is pre-1.0. A
  published 0.x release does not make it a 1.0+ contract, and one named consumer
  does not create an exception.
- The rename must change the interface and every affected caller together. The
  repository must not be left in a state that needs both the old and the new
  source names to work.
- Do not add an alias, deprecated entrypoint, facade, wrapper, shim, dual
  implementation, compatibility adapter, or migration layer for the old source
  name.
- Do not remove, delete, or rewrite the old RFC. Its status changes only through
  its owner's decision. Do not declare it obsolete on the plan's own authority.
- Do not implement the rename while `TOR-CONFLICT-001` is open, and do not
  resume until the deviation is explicitly accepted. A blocked plan is the
  correct state, not a problem to route around.
- Only the authorized rename may change the public interface. Any other public
  API change requires escalation.
- No new dependency is authorized. If one is needed, stop and escalate.
- Existing approved file, code, configuration, and documentation budgets remain
  in force. This revision does not invent or raise them. If the original plan's
  numeric budgets cannot be recovered, stop before execution.
- The plan is already executing, but approval of this blocked revision and of
  the proposed deviation is still required before work resumes.

If satisfying the objective appears to require violating a constraint, do not

## Decision log

  and therefore within the policy prohibition on compatibility machinery.
  Rationale: version 0.8 is below 1.0; publication does not create a 1.0+
  contract; the named consumer is expressly not an exception. The rejected
  alternative was to treat the published 0.8 release or the one consumer as an
  implicit compatibility commitment.
  Date/Author: 2026-11-19, authoring agent (proposed; not approved).

- D2. Decision: do not implement the alias, deprecated entrypoint, facade,
  wrapper, shim, dual implementation, or compatibility adapter.
  Rationale: every such device is source-API compatibility machinery for a
  pre-1.0 surface and is prohibited. The rejected alternatives were an alias
  for the old name, a temporary wrapper, and a dual implementation; each
  violates the same constraint and would create an obsolete interface to
  maintain.
  Date/Author: 2026-11-19, authoring agent (proposed; not approved).

- D3. Decision: do not silently proceed with the rename while omitting the
  RFC's alias requirement.
  Rationale: the RFC is an inherited commitment. The governing documents
  require the conflict to be exposed for explicit resolution; they do not
  authorize a unilateral deletion or an undeclared omission. The rejected
  alternative was to treat the policy as self-executing and continue without
  telling the RFC's owner.
  Date/Author: 2026-11-19, authoring agent (proposed; not approved).

- D4. Decision: set the plan status to `BLOCKED` and escalate the conflict.
  Rationale: the conflict cannot be resolved by the plan. The RFC's decision
  authority can retire or supersede the alias requirement; the policy owner can
  interpret or amend the policy. Options considered: (a) the RFC is retired or
  superseded, in which case the rename resumes atomically without an alias;
  (b) the policy is amended, in which case a fresh compatibility assessment is
  required; (c) the rename is deferred, in which case the plan remains blocked;
  (d) the alias is implemented anyway, which is rejected as a policy violation.
  This is an escalation, not a removal of the RFC and not a deferral of its
  requirement to a later milestone. The RFC remains in force until its owner
  decides otherwise.
  Date/Author: 2026-11-19, authoring agent (proposed; not approved).

- D5. Decision: resume only after the RFC resolution is recorded and the

  Rationale: the approval gate and the deviation rule both require explicit

  Date/Author: 2026-11-19, authoring agent (proposed; not approved).

- D6. Decision: preserve the original plan's identifiers, budgets, and commands;

## Outcomes & retrospective

The plan is not complete. The current outcome is that the conflict surfaced
before the alias was implemented. No alias was added, the RFC was not deleted
or rewritten, and the plan was blocked rather than allowed to drift.

The main lesson is that compatibility classification belongs in intake, before
the rename milestone begins. An inherited RFC is not a waiver, a published 0.8
release is not a 1.0 contract, and a named consumer does not create an
exception. A blocked plan with a recorded conflict is the correct outcome when
the alternative is a prohibited compatibility layer or a silent violation.

Remaining work is the RFC resolution, acceptance of this terms of reference and
the deviation, recovery of the original plan facts, and then the atomic rename,
consumer migration, and release closure. The plan must not be set to `COMPLETE`
while the conflict or the deviation remains unrecorded or unaccepted.

## Verification plan

Implementation and verification are planned together. The rename is mechanical,
but the policy boundary is not: the plan must demonstrate the absence of
compatibility machinery, not merely the presence of the new name.

### Abstract model

The relevant state is the source tree, its exported API surface, and the
consumer's build. Inputs are the old identifier and the new identifier.
Precondition: the compatibility classification is pre-1.0, the RFC conflict is
resolved, and the deviation is accepted. The transition renames the definition
and every affected caller. The expected postcondition is that the new name is
the only source name, no alias preserves the old name, and the build, tests, and
consumer checks pass.

Allowed occurrences of the old name are the changelog, the migration guide, and
untouched historical documents such as the RFC. Any other source occurrence is a
failure. Malformed or partial states are handled by refusing to continue: a
half-renamed tree is not a plateau.

### Invariants and lemmas

- `INV-NO-ALIAS`: no alias, deprecated entrypoint, facade, wrapper, shim, dual
  implementation, or compatibility adapter exposes the old name. Linked to
  `REQ-NO-ALIAS`.
- `INV-ATOMIC`: every in-repository caller uses the new name; no mixed old/new
  source state remains. Linked to `REQ-ATOMIC-RENAME`.
- `INV-NO-OLD-NAME`: no source occurrence of the old name remains outside the
  allowed documentation exceptions. Linked to `REQ-ATOMIC-RENAME`.
- `INV-CONSUMER`: the known downstream consumer builds against the renamed
  release, or an accepted migration note exists. Linked to
  `REQ-CONSUMER-MIGRATION`.
- `INV-RFC-GATE`: implementation does not resume while `TOR-CONFLICT-001` is
  open; a written resolution exists before resumption. Linked to
  `REQ-RFC-RESOLUTION` and `REQ-NO-SILENT-OMISSION`.

Lemmas:

- `L-NO-COMPAT`: if `INV-NO-ALIAS` holds, the released surface contains no
  source-API compatibility machinery for the old name. This connects the
  absence check to the policy obligation.
- `L-ATOMIC-COHERENCE`: if `INV-ATOMIC` and `INV-NO-OLD-NAME` hold, the
  repository is in one coherent source-API state and does not require both
  names to function.

### Axioms (trusted, not verified here)

- `AXIOM-VERSION`: 0.8 is pre-1.0 under the project's versioning scheme.
  Source: release tag or versioning policy, revision not supplied. Boundary:
  the compatibility classification.
- `AXIOM-CONSUMER-SET`: the one named consumer is the complete known external
  consumer set. Source: contract, registry, or maintainer survey, not supplied.
  Boundary: the migration scope.
- `AXIOM-POLICY`: the governing df12 policy is the applicable constraint.

- `AXIOM-RFC`: the old RFC contains the alias demand and remains in force until

- `AXIOM-TOOLCHAIN`: the repository's build and test commands faithfully
  exercise the affected interface. Source: repository configuration, not

- `AXIOM-CONSUMER-BUILD`: the consumer's build actually calls the renamed
  symbol. Source: consumer code, not supplied. A consumer that never used the
  symbol is not evidence of migration.

### Methods per obligation

- Obligation: `INV-NO-ALIAS` (no compatibility machinery for the old name).
  Method: static API-surface inspection plus repository search. Rationale: the
  surface is finite and the property is an absence; a targeted search plus an
  exported-symbol diff is proportionate.
  Domain: all exported symbols and all source paths, with documentation
  exceptions listed explicitly.
  Artefact: the API diff and the search pattern, paths to be recovered.
  Evidence: the search and inspection report zero alias matches; a seeded
  temporary alias is detected and then removed.
  Non-vacuity: the seeded alias must be rejected for the intended reason. A
  search that cannot match the seeded case is a failed check.

- Obligation: `INV-ATOMIC` (every caller uses the new name).
  Method: compile the tree and run the focused test suite.
  Rationale: the compiler and tests exercise the real callers; no model is
  needed for a mechanical rename.
  Domain: all in-repository callers and the affected test fixtures.
  Artefact: the build and test logs.
  Evidence: the build fails before the rename with the new name missing or the
  old caller unresolved, then passes after the rename.
  Non-vacuity: add a temporary caller that uses the old name and confirm the
  build rejects it, or use a compile-fail test; remove the temporary caller
  afterwards.

- Obligation: `INV-NO-OLD-NAME` (no source occurrence outside documentation).
  Method: exhaustive repository search with explicit exclusions.
  Rationale: the property is a finite absence over the source tree.
  Domain: all tracked source paths, excluding the changelog, migration guide,
  and historical documents.
  Artefact: the search command and its exclusion list.
  Evidence: zero matches after the rename. Seed one occurrence and confirm the
  search finds it, then remove the seed.
  Non-vacuity: the seed must be found. An empty result with a broken pattern or
  an over-broad exclusion is not evidence.

- Obligation: `INV-CONSUMER` (the consumer can adopt the new name).
  Method: integration check against the consumer's real build, or review of an
  accepted migration note where the consumer is updated separately.
  Rationale: a mock of the consumer would not establish that the real caller
  migrated; the real interface is the relevant boundary.
  Domain: the one known consumer and its build.
  Artefact: the consumer CI result or the accepted note.
  Evidence: the consumer build passes against the renamed release, or the note
  is accepted by the consumer's authority.
  Non-vacuity: confirm the consumer calls the renamed symbol. A build that does
  not exercise the symbol proves nothing about migration.

- Obligation: `INV-RFC-GATE` (no resumption while the conflict is open).
  Method: document and status review at the milestone boundary.
  Rationale: the obligation is procedural and evidentiary, not executable.
  Domain: the RFC record, the policy record, and the plan status.
  Artefact: the cited resolution and the accepted deviation.
  Evidence: the plan remains `BLOCKED` until both exist.
  Non-vacuity: the resolution must name the alias requirement and the policy
  basis. A generic approval that does not mention the conflict does not
  discharge it.

### Formal verification decision

No model checking or formal proof is planned. The material obligations are a
finite source-tree absence, a compile-and-test property, and a document gate.
The selected methods can fail when the implementation is wrong: a seeded alias,
a seeded old-name occurrence, or a caller left on the old name is rejected.
Stronger methods would add cost without covering the policy question, which is
resolved by an authority, not by a prover. This decision is recorded as D7.

### `EP-M1` atomic rename

Assigned requirements and gaps: `REQ-ATOMIC-RENAME`, `REQ-NO-ALIAS`,
`GAP-PLAN-FACTS`, and the compatibility half of `GAP-RELEASE-LINEAGE`.

Status: blocked at the gate. Do not begin or continue implementation until
`GAP-RFC-CONFLICT` has a written resolution and the deviation is accepted.

Steps after the gate opens:

1. Recover the original plan facts, including the actual symbol names, paths,
   toolchain, commands, budgets, and any existing working-tree edits.
2. Inspect the latest applicable formal release tag and record it. Confirm that
   no already released 1.0+ contract is involved.
3. Write the smallest red check: a consumer or test that calls the new name, or
   a compile-fail check that rejects the old name. Run it and record the
   expected failure.
4. Rename the definition and every affected caller in the same change. Do not
   add a second name.
5. Remove the last old-name source occurrence. Update tests and generated
   callers as required.
6. Run the focused check, then the repository gates. Run them sequentially.
7. Run the API-surface and old-name searches with their negative controls.
8. Commit the coherent state. Do not leave a half-renamed tree.

Acceptance evidence: the build and focused tests pass; the old-name search is
empty outside the allowed documentation; the alias search is empty; the seeded
negative controls are rejected for the intended reason; the API diff shows only
the authorized rename.

Conformance check for `EP-M1`:

- `REQ-ATOMIC-RENAME` and `REQ-NO-ALIAS` are satisfied.
- The design, if one is later recovered, is still followed.
- The upstream assumptions (pre-1.0 version, no 1.0+ contract) remain valid.
- No unapproved public interface or dependency change has appeared.
- No unapproved trust boundary or persisted-format change has appeared.
- Trace links and acceptance evidence are current.

Recovery: revert the rename commit and restore the last green state. Do not
