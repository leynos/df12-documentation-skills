## Purpose / big picture

The application is released at version 2. One method, declared `public`, is
called only by three modules in the same application. After this change, the
method has the approved new signature and all three callers use it; the old
signature no longer exists. A maintainer can then read each call site and see
the current contract, without an obsolete overload or wrapper remaining as a
trap.

Before:

```plaintext
<method-name>(<current-parameters>) -> <current-return>
```

After:

```plaintext
<method-name>(<new-parameters>) -> <new-return>
```

The user-visible behaviour of the application is unchanged unless the approved
change request says otherwise. No external interface, persisted record, or
wire message changes as part of this work. This work closes no roadmap item;
it executes the sponsor's change request carried forward from
`01-terms-of-reference.md`.

## Constraints

Hard invariants. Violating one requires escalation, not a workaround.

- The only authorised interface change is the method named in the approved
  change request. No other public surface changes.
- No source-API compatibility machinery: no overload, alias, deprecated
  entrypoint, facade, adapter, wrapper, dual implementation, or defaulted
  parameter kept so the old call shape compiles. The method is an
  application-internal public surface, and df12 policy prohibits compatibility
  machinery for it (`TOR-CONSTRAINT-001`).
- The definition and all three callers change together. No intermediate
  state exposes both signatures.
- The change must not alter persisted records or wire formats. If it would,
  stop and escalate to a separate migration assessment.
- No dependency is added or upgraded.
- Unrelated refactoring in the affected files is out of scope. Keep the diff
  to the method, the three callers, and the tests the change requires.
- Do not read or edit historical, completed ExecPlans as part of the change.
- Implementation begins only after the user approves this plan. It has not
  been approved.

## Risks

- Risk: an external or cross-package consumer exists despite the brief.
  Severity: high. Likelihood: low. Mitigation: `EP-M0` inventories the call
  sites and searches for re-exports and published entrypoints; stop if one is
  found.
- Risk: the method is invoked reflectively, through a serializer, or by name
  in configuration, so the compiler and a text search miss a caller.
  Severity: high. Likelihood: medium. Mitigation: `EP-M0` searches for the
  dynamic idioms of the language and reviews registration points.
- Risk: the new signature changes behaviour, not just shape. Severity: medium.
  Likelihood: medium. Mitigation: resolve `TOR-OPEN-001` before approval; add
  tests for the intended behaviour rather than assuming preservation.
- Risk: a parameter or return value is persisted or sent to a peer.
  Severity: high. Likelihood: low. Mitigation: `EP-M0` serialisation review;
  escalate to a separate migration if found.
- Risk: the provisional tolerances are too tight for the real callers.
  Severity: low. Likelihood: medium. Mitigation: `EP-M0` corrects them before
  approval.
- Risk: a reviewer requests a deprecation shim. Severity: medium. Likelihood:
  low. Mitigation: cite `TOR-CONSTRAINT-001`; record a conflict and escalate
  rather than implement one.

## Decision log

- `D1` Decision: classify the method as a private API for compatibility
  purposes because it is an application-internal interface declared `public`,
  and the three callers are its only known consumers.
  Rationale: contract scope follows consumers and commitments, not the
  `public` keyword or the application's version number. The df12 prohibition
  applies to this category. Alternatives that preserve the old interface have
  no consumer to be compatible with and would be compatibility theatre.
  Date/Author: 2026-11-19, authoring agent.

- `D2` Decision: change the definition and all three callers atomically; add
  no shim.
  Rationale: the change is a single coherent edit; a compatibility window
  would be an invented promise. Date/Author: 2026-11-19, authoring agent.

- `D3` Decision: insert `EP-M0` as a reconnaissance gate before any code edit.
  Rationale: the authoring session could not inspect the repository, so a
  self-contained plan requires an explicit step that records the symbol,
  paths, base revision, toolchain, dynamic-invocation inventory, and
  serialisation boundary. It changes no production code.
  Date/Author: 2026-11-19, authoring agent.

- `D4` Decision: provisional tolerances rather than invented budgets.
  Rationale: the ExecPlan skill requires budgets set after surveying the
  affected code; that survey was impossible here. `EP-M0` confirms them
  before approval. Date/Author: 2026-11-19, authoring agent.

- `D5` Decision: verify by compiler enforcement plus exhaustive search, not
  model checking or proof.
  Rationale: the property is whole-program source consistency within a small
  scope. A stronger method would restate the compiler's rules and still miss
  dynamic dispatch; targeted dynamic-path review is the proportionate check.
  Date/Author: 2026-11-19, authoring agent.

- `D6` Decision: keep no compatibility default parameter.
  Rationale: a default whose purpose is to let the old call shape compile is
  the prohibited shim in another spelling. If the approved new signature
  genuinely has an optional parameter, that is a design fact to record, not a
  migration device. Date/Author: 2026-11-19, authoring agent.

- `D7` Decision: no Mermaid diagram, so nixie is not run.
  Rationale: the change is three call edges from one definition; prose and
  tables state it completely. Date/Author: 2026-11-19, authoring agent.

## Verification plan

### Abstract model

Let `R` be the set of source locations that refer to the method: the
definition `d`, the three callers `m1`, `m2`, `m3`, and any tests. A referrer
is conforming when it uses the new signature; a caller must also supply
arguments of the new types in the new order and consume the new return. The
target program has every referrer conforming and no remaining old-signature
entrypoint. The malformed states are a referrer with the old argument list or
an invocation that the inventory of `R` misses. The latter is handled by the
`GAP-DYNAMIC` check rather than by the model.

### Invariants and lemmas

- `INV-CALLSITES-001` No live source location refers to the old signature
  after the change. Links to `REQ-COMPLETE-001`.
- `INV-COVERAGE-001` The referrer inventory is complete: the search finds all
  syntactic references, and no dynamic path invokes the method. Links to
  `REQ-COMPLETE-001`.
- `INV-BEHAVIOUR-001` For each named caller-visible outcome, the post-change
  result equals the pre-change result for the same inputs. Links to
  `REQ-BEHAVIOUR-001`.
- `L-COMPILE-001` If every referrer is statically resolved, the old signature
  is removed, and the build succeeds, then every referrer uses the new
  signature. Depends on `AXIOM-COMPILER`.
- `L-COVERAGE-001` If the search finds all syntactic occurrences and no
  dynamic invocation exists, `R` is complete. Depends on `AXIOM-SEARCH` and
  the `GAP-DYNAMIC` result.

### Axioms (trusted, not verified here)

- `AXIOM-COMPILER` The language rejects a call with the wrong argument count,
  order, or type. Source: the language specification. Boundary: the affected
  modules. Fails if the language is dynamically typed.
- `AXIOM-SEARCH` The search tool reports every syntactic occurrence of the
  identifier. Boundary: the working tree.
- `AXIOM-TESTS` The test runner executes the named tests and fails on
  assertion error. Boundary: the configured framework.

### Methods per obligation

- Obligation: `INV-CALLSITES-001`.
  Method: exhaustive search plus compiler enforcement.
  Rationale: whole-program source consistency is directly observable by both.
  Domain: working tree, excluding vendored dependencies and recorded
  historical paths.
  Artefact: `EP-M2` search command and the build gate.
  Evidence: the search returns no live old-shape reference and the build
  passes.
  Non-vacuity: the same search must find the definition and all three callers
  before the change; that positive control proves the pattern is not empty.

- Obligation: `INV-COVERAGE-001`.
  Method: identifier search plus a review of dynamic idioms and registration
  points for `<language>`.
  Rationale: runtime dispatch cannot be enumerated generically; a targeted
  inventory is proportionate.
  Domain: reflect, serialiser, FFI, and dependency-injection surfaces named in
  `EP-M0`.
  Artefact: baseline inventory in `Artefacts and notes`.
  Evidence: no unexplained match; the inventory contains the three known
  callers.
  Non-vacuity: an inventory missing the three known callers is a failed
  strategy, not a clean result.

- Obligation: `INV-BEHAVIOUR-001`.
  Method: parameterized tests per caller, plus the affected existing tests.
  Rationale: the outcomes are a finite set, not a generated input space.
  Domain: the inputs already covered by the caller tests and boundary values
  for any new parameter.
  Artefact: `<test-paths>`.
  Evidence: the focused tests pass before and after the change; the expected
  case count is recorded.
  Non-vacuity: at least one case must fail if a caller passes arguments in the
  wrong order or drops a transformed value.

- Obligation: `L-COMPILE-001` and `L-COVERAGE-001`.
  Method: argument from the recorded build and search evidence.
  Rationale: separate experiments would restate their premises.
  Evidence: `EP-M2` records the build result, the search result, and the
  `GAP-DYNAMIC` outcome. If the language is dynamic, `AXIOM-COMPILER` is false,
  `L-COMPILE-001` does not apply, and runtime tests carry the obligation.
  Non-vacuity: the build must fail when one caller is deliberately left on the
  old signature (see `EP-M2` negative control).

### Formal verification decision

No model checking or formal proof. The property is static whole-program
consistency over four production locations, which the compiler and an
exhaustive search establish directly. Stronger methods would restate the
compiler's rules without covering dynamic dispatch, and the proportionate
response to dynamic dispatch is a targeted inventory, not a model. This is
`D5`.

### `EP-M1` atomic signature replacement

Assigned: `REQ-ATOMIC-001`, `REQ-CALLERS-001`, `REQ-BEHAVIOUR-001`,
`TOR-GOAL-001`, `TOR-GOAL-002`, `TOR-GOAL-004`.

Red: add or update the smallest test that calls the method with the new
signature and asserts its unchanged outcome. Run it. It must fail for the
intended reason: the new signature does not exist (a missing-symbol or arity
error in a static language, or an unexpected-argument error in a dynamic one).
Record the failure text.

Green: change the definition to `<new-signature>` and update all three callers
to supply the new arguments and consume the new return. Change nothing else.
Run the focused test and the affected caller tests; they must pass.

Refactor: clean up the edited regions without changing behaviour; rerun the
focused tests. The old signature must not survive in any form.

End state: the application builds, the focused tests pass, the old signature
is gone, and no compatibility construct exists. This plateau is coherent on
its own; a later milestone is not required for the repository to be usable.

Recovery: revert the milestone commit and re-apply. The step is idempotent
from a clean tree.

### `EP-M2` repository-wide verification

Assigned: `REQ-COMPLETE-001`, `REQ-NOCOMPAT-001`, `REQ-BEHAVIOUR-001`.

Acceptance: empty live search, no compatibility construct, the negative
control rejected for the intended reason, and the suite passing. Record the
transcripts.
