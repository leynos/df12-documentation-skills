## Purpose / big picture

A version 2 library exports a function that was added after the library's
latest formal release tag. Because the function appears in no tagged release,
it is an unreleased API change ahead of the latest formal release tag. The
library's released 1.0-or-later lineage does not make this particular symbol
released: the release tag, not the major version number, is the baseline.

The task is to rename that function before the next release, while the rename
still costs nothing to consumers. Today a caller writes the old name:

```plaintext
<old_name>(<arguments>)
```

After the change the same caller writes:

```plaintext
<new_name>(<arguments>)
```

with the same signature, visibility, attributes, and runtime behaviour. The old
name is removed from the source and from the exported namespace. It is not kept
as an alias, a deprecated entrypoint, a facade, or a wrapper. There is no
released contract to preserve, so retaining the old name would be compatibility
theatre and would leave the public surface describing a name that never
shipped.

The affected callers are renamed in the same coherent change. The change also
updates tests, documentation, examples, doc comments, and generated bindings or
API snapshots that name the symbol. It does not alter any symbol that exists at
the latest formal release tag.

The intended new name, the target repository, and the exact release tag have
not been supplied. They are recorded as unresolved inputs, not invented.

## Constraints

Hard invariants that must hold throughout implementation. Violation requires
escalation, not a workaround.

- The renamed symbol is unreleased: it was introduced after the latest formal
  release tag and is absent at that tag. Implementation must confirm this
  baseline before editing. If the symbol is present at the tag, stop and
  escalate; the compatibility rules for a released surface then apply instead.
- No source-API compatibility machinery. Do not add or retain an alias, a
  deprecated entrypoint, a facade, a wrapper, a dual implementation, or any
  other shim for the old name. The applicable df12 rules prohibit such
  machinery for unreleased API changes ahead of the latest formal release tag.
- Rename atomically. The definition, every caller, tests, documentation,
  examples, and generated artefacts that name the symbol change together. A
  milestone must be a coherent validated state, not an old-and-new bridge.
- Preserve behaviour. The signature, parameters, return type, visibility,
  attributes, error behaviour, and semantics are unchanged. Only the identifier
  changes unless the user explicitly authorizes more.
- Do not change any symbol that exists at the latest formal release tag. If the
  old or new name collides with a released symbol, stop and escalate.
- Do not change persisted data formats, wire formats, configuration keys, or
  serialized representations. If the identifier appears in such a format, stop
  and escalate; that is a separate migration question, not a rename.
- Do not rewrite released changelog entries or historical documents. Record the
  rename in a new entry for the upcoming, unreleased version.
- Do not authorize implementation. This plan begins execution only after the
  user approves it and supplies the intended new name.
- Authorized dependency changes: none.
- The ExecPlan file is excluded from every file and line budget below.

  downstream examples.
  Severity: medium. Likelihood: medium.
  Mitigation: search tracked content case-sensitively and word-wise, including

  old name before the edit.
- Risk: the rename is applied to a released symbol because the repository
  contains two similarly named functions.
  Severity: high. Likelihood: low.
  Mitigation: inventory the exported namespace and record each candidate's
  provenance relative to the tag.
- Risk: the rename changes behaviour through a trait implementation, overload,
  or dispatch rule rather than a plain call target.
  Severity: medium. Likelihood: low.
  Mitigation: `EP-M1` keeps the full test suite green and records any
  language-specific dispatch concern in `Decision log`.

## Verification plan

### Abstract model

Let `E_tag` be the set of exported identifiers at the latest formal release tag
`T`. Let `E_head` be the set at the working tree before the change. Let `R` map
the old identifier `old` to `new`. The change requires `old` not in `E_tag`, a
new tree in which `R(old) = new` is exported with the identical signature, `old`
is absent from the exported namespace and from tracked non-historical content,
and `E_tag` remains a subset of the new exported set with unchanged entries.

Preconditions: `EP-M0` confirms `old` is absent at `T`; the new name is
supplied and is a valid identifier not already exported; the repository is on a
non-main working branch. Malformed preconditions stop the change rather than
being repaired by guesswork.

### Invariants and lemmas

- `INV-NO-OLD-REF`: no tracked production source, test, documentation, example,
  or generated file references `old` after the change, excluding released
  changelog history and tagged revisions. Establishes `REQ-RENAME-NAME`.
- `INV-NEW-EXPORT`: `new` is exported with the same signature, visibility,
  attributes, and behaviour as `old`. Establishes `REQ-RENAME-BEHAVIOUR`.
- `INV-NO-ALIAS`: `old` is not exported under any alias or deprecated form.
  Establishes `REQ-RENAME-NO-ALIAS`.
- `INV-TAG-SURFACE`: every identifier in `E_tag` is exported unchanged.
  Establishes `REQ-RENAME-RELEASED-SURFACE`.
- `L-ALL-CALLERS`: every reference found in the `EP-M0` inventory is either
  renamed or recorded as historical. Connects `INV-NO-OLD-REF` to the actual
  call graph.
- `L-SEARCH-SOUND`: the reference search used for `INV-NO-OLD-REF` demonstrably
  finds the old identifier in a controlled positive case. Without this lemma a
  zero-hit search is vacuous.

### Axioms (trusted, not verified here)

- `AXIOM-COMPILER`: the compiler or interpreter resolves every static
  identifier reference, so a successful build with the new name and no old name
  means no static caller was missed. Dynamic lookup is outside this axiom and is
  covered by the inventory.
- `AXIOM-TAG`: the repository's formal release tag records the released source
  state. This is a project convention, not something this plan can prove.
- `AXIOM-SEARCH`: the tracked-file search tool reports textual matches for the
  paths and encodings used by this repository. Generated binary artefacts are
  outside the search and must be identified and regenerated.

### Methods per obligation

- Obligation: `INV-NO-OLD-REF` and `L-SEARCH-SOUND`.
  Method: exhaustive parameterized search over tracked files, with
  case-sensitive and word-boundary variants.
  Rationale: the identifier space is finite and the repository is fully
  searchable, so exhaustive enumeration is stronger than sampling.
  Domain: all tracked files; explicit exclusions limited to tagged revisions and
  released changelog sections.
  Artefact: the `git grep` commands in `Concrete steps`.
  Evidence: before the edit, the search reports at least one match for `old`;
  after the edit, it reports zero. The pre-edit match is the non-vacuity
  witness.
  Non-vacuity: a seeded reference to `old` in a scratch documentation file must
  be found; the file is removed afterwards. A search rooted at the wrong
  directory would find neither name and is rejected because the pre-edit search
  must find the old name and the post-edit search must find the new one.
- Obligation: `INV-NEW-EXPORT`, `INV-NO-ALIAS`, and `L-ALL-CALLERS`.
  Method: compile-time red/green test plus exported-surface inspection.
  Rationale: the compiler proves static call resolution; the surface check
  proves no residual alias is exported.
  Domain: the focused test calling the new name, and the package's public API
  surface as reported by its documentation or API-diff tool.
  Artefact: the red test in `EP-M1` and the surface command recorded in
  `EP-M0`.
  Evidence: the new-name test fails before the rename for the expected
  missing-identifier reason and passes afterwards; the surface listing contains
  `new` once and `old` zero times.
  Non-vacuity: the red failure must cite the missing new identifier, not an
  unrelated compile error.
- Obligation: `INV-TAG-SURFACE`.
  Method: parameterized diff of the exported surface at `T` against the new
  tree.
  Rationale: the released set is finite and directly comparable.
  Domain: the package's exported symbols at `T` and after the change.
  Artefact: `git show <tag>:<path>` plus the current surface listing.
  Evidence: the diff contains no removed or altered released symbol.
  Non-vacuity: the diff must show at least the unchanged released entries;
  an empty listing is a failure of the measurement, not a pass.
- Obligation: `INV-NEW-EXPORT` behavioural clause.
  Method: the repository's existing test suite, run unchanged except for
  renamed references.
  Rationale: this is a rename, so unchanged behaviour should keep the suite
  green; any failure is a regression signal.
  Domain: all tests covering the function and its callers.
  Artefact: the gate commands recorded in `EP-M0`.
  Evidence: the suite passes before and after; the only diffs in tests are
  renamed identifiers.
  Non-vacuity: at least one test must call the function; if none does, add a
  focused behavioural test before claiming coverage.

### Formal verification decision

No model checking or formal proof is warranted. The change introduces no new
state, transition, concurrency, arithmetic, or protocol behaviour. The
obligations are identifier-set and call-resolution properties, which exhaustive
search, the compiler, and the existing behavioural suite establish more cheaply
and with fewer abstractions than a model. The residual gap is dynamic lookup,
which the inventory must enumerate explicitly.

## Validation and acceptance

Acceptance is behavioural. After the change, a caller using `<new_name>` builds
and runs with unchanged results, a focused test that failed before the rename
passes, a search of tracked non-historical content finds no `<old_name>`, and
the exported-surface listing contains `<new_name>` once and `<old_name>` zero
times. The symbols exported at `<latest-formal-tag>` are byte-for-byte unchanged
in name, signature, and visibility.

Quality criteria:

- Tests: the full suite passes; the focused rename test fails before and passes
  after for the intended reason.
- Verification: `INV-NO-OLD-REF`, `INV-NEW-EXPORT`, `INV-NO-ALIAS`,
  `INV-TAG-SURFACE`, `L-ALL-CALLERS`, and `L-SEARCH-SOUND` are discharged with
  the evidence above.
- Lint and typecheck: the repository's configured commands pass.
- Performance: no change expected; no benchmark required for a rename.
- Security: no new input surface or trust boundary; no scan required beyond the
  normal gates.

Quality method: run the gate sequence from `Concrete steps` sequentially and
capture each transcript.

## Idempotence and recovery

The rename is idempotent at the file level: applying it again finds the new
name and no old name. Work on a dedicated branch. If a gate fails, revert the
most recent commit rather than layering a corrective alias. No database,
deployment, or persisted state is touched, so rollback is a Git revert. Remove
any seeded negative-control file before committing.
